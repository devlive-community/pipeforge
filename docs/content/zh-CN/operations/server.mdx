服务提供 REST API 并托管 Web UI。本版本中它是**无状态**的：校验和解释作业、描述已安装的插件、列出函数和错误码、对表达式求值。
保存作业、运行作业和保留运行历史随后续版本的元数据库一起提供；现有接口的路径和字段保持不变。

## 启动服务

构建后启动可执行 jar：

```bash
./mvnw -B -pl pipeforge-server -am package -DskipTests
java -jar pipeforge-server/target/pipeforge-server-0.1.0-SNAPSHOT-exec.jar
```

服务监听 `http://127.0.0.1:8080`。检查它是否可用：

```bash
curl -s http://127.0.0.1:8080/api/v1/version
```

## 从源码仓库启动

在 IDE 中或用 `./mvnw spring-boot:run` 启动的服务端没有可以加载的 `plugins` 目录。改用 `dev` 配置文件启动：
服务端会额外加载它所在源码仓库中的插件模块，直接使用它们的构建输出，不需要打包任何插件。

1. 在仓库根目录编译一次，让每个插件模块生成依赖列表（`target/pipeforge-plugin/classpath.txt`）：

   ```bash
   ./mvnw compile
   ```

2. 用该配置文件启动服务端。在 IntelliJ IDEA 中，把运行配置的 **Active profiles** 设为 `dev`；在命令行中：

   ```bash
   java -jar pipeforge-server/target/pipeforge-server-0.1.0-SNAPSHOT-exec.jar --spring.profiles.active=dev
   ```

服务端从工作目录找到源码仓库（工作目录是仓库根目录或 `pipeforge-server` 都可以），加载根目录下两层、带有
`src/main/plugin/plugin.yaml` 的每个模块，因此新增的插件无需配置就会被发现。日志中会列出找到的内容：

```text
Development mode: loading the plugin modules of /work/pipeforge
Development plugin fake@0.1.0-SNAPSHOT from /work/pipeforge/pipeforge-connectors/connector-fake
Plugin directory /work/pipeforge/pipeforge-server/plugins does not exist
Found 1 plugin(s) in /work/pipeforge
```

修改插件后，在 IDE 中构建并重启服务端即可；只有插件的依赖变化时才需要再次运行 `./mvnw compile`。尚未构建的模块会出现在
`GET /api/v1/plugins` 的 `unavailable` 中，并附带构建它的命令。源码仓库中的插件会替换 id 和版本相同的已安装插件包。

## Web UI

如果在打包服务之前先构建了 UI（`pnpm --filter @pipeforge/ui build`），`pipeforge-ui/dist` 中的构建产物会进入 jar，服务在 `/` 提供
[Web UI](../guides/web-ui)。`/api` 以外且不是文件的地址都会打开 UI，因此 UI 的页面可以直接收藏；未知的 `/api` 地址始终返回错误对象。`index.html` 以 `Cache-Control: no-cache` 返回，`/assets/` 下文件名带内容哈希的文件缓存一年，因此浏览器在下次加载时就会使用新版本的 UI。

## 配置

配置项是 Spring Boot 属性：写在 jar 旁边的 `application.yaml` 中、以 `--名称=取值` 传入，或者设置为环境变量（`PIPEFORGE_JOB_TIMEZONE`）。

| 配置项 | 默认值 | 含义 |
|---|---|---|
| `server.address` | `127.0.0.1` | 监听的网络接口 |
| `server.port` | `8080` | 端口 |
| `pipeforge.plugin.paths` | `plugins` | 存放插件包（zip 文件或解压后的目录）的目录 |
| `pipeforge.plugin.cache` | `work/plugin-cache` | zip 插件解压到的位置 |
| `pipeforge.plugin.dev.enabled` | `false` | 额外加载源码仓库中的插件模块；`dev` 配置文件会开启它 |
| `pipeforge.plugin.dev.root` | 从工作目录查找 | 开发模式使用的源码仓库根目录 |
| `pipeforge.job.timezone` | `UTC` | 没有设置 `env.timezone` 的作业使用的时区 |
| `pipeforge.job.defaults.*` | 无 | 节点选项的集群默认值，采用 env 写法，例如 `pipeforge.job.defaults.source.fetch-size` |

```yaml
pipeforge:
  plugin:
    paths: [/opt/pipeforge/plugins]
  job:
    timezone: Asia/Shanghai
    defaults:
      source.fetch-size: "5000"
```

插件在服务启动时加载，日志会列出每个插件目录的绝对路径和其中的插件数；无法使用的插件包会出现在 `GET /api/v1/plugins` 的 `unavailable` 中，并附带原因。

## 安全

服务目前还没有认证，因此只监听回环接口。不要把 `server.address` 设置为公网接口；如果其他人需要访问，请在前面放一个带认证的反向代理。
`${env:NAME}` 这类变量读取的是服务进程的环境变量。

## 日志与错误

服务把日志输出到控制台。由客户端原因导致失败的请求会收到带错误码的错误对象（见 [REST API](../reference/api#约定)）；只有内部错误（`PF-SYS-0001`）会连同堆栈一起记录日志。
