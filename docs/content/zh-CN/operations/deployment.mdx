一个集群由一个 **Master** 和任意数量的 **Worker** 组成（见[集群](../concepts/cluster)）。两者都在发行包中，发行包还包含
`pipeforge` 命令和 Web UI 服务。

## 安装

在集群的每台机器上解压 `pipeforge-<version>.tar.gz`。在源码目录中可以这样构建：

```bash
./mvnw -B -pl pipeforge-dist -am package -DskipTests
tar -xzf pipeforge-dist/target/pipeforge-0.1.0-SNAPSHOT.tar.gz
```

| 目录 | 内容 |
|---|---|
| `bin/` | `pipeforge`（命令）以及 `pipeforge-master`、`pipeforge-worker`、`pipeforge-standalone` 的 `.sh` 与 `.cmd` 脚本 |
| `conf/` | `pipeforge.yaml`、`master.yaml`、`worker.yaml`、`logback.xml`、`jvm.options` |
| `lib/` | 依赖库；`lib/logback/` 是集群进程的日志库，`lib/server/` 是服务 |
| `plugins/` | Master 提供的插件，以及你安装的[驱动插件](../concepts/plugins#驱动插件)：`fake`、`mysql`（驱动插件需单独安装）、`postgres`、`jdbc`（使用你安装的驱动）、`field-mapper`、`console`、`blackhole` |
| `logs/`、`run/`、`data/` | 首次启动时创建：日志、进程 ID、插件缓存 |

进程需要 Java 21 或更高版本；`JAVA_HOME` 选择运行时。

## 启动集群

所有进程都需要同一个集群令牌。在每台机器的 `conf/pipeforge.yaml` 中设置，或者用环境变量提供：

```bash
export PIPEFORGE_CLUSTER_TOKEN="$(openssl rand -hex 32)"
```

在 Master 所在的机器上：

```bash
bin/pipeforge-master.sh start
```

在每台 Worker 机器上，告诉 Worker Master 在哪里，以及其他进程如何访问它：

```bash
export PIPEFORGE_WORKER_MASTER_ADDRESS=master.example.com:6123
export PIPEFORGE_WORKER_HOST=worker-1.example.com
bin/pipeforge-worker.sh start --labels zone=east
```

Worker 向 Master 注册并提供 Slot，除非 `worker.slots` 另有设置，否则每个 CPU 核一个 Slot；它的日志中会出现
`Worker … offers 8 slot(s)`。在一台机器上试用时，`bin/pipeforge-standalone.sh start` 在一个进程中运行 Master 和 Worker。

## 管理进程

| 命令 | 作用 |
|---|---|
| `start` | 在后台启动进程并等待它运行；没有启动成功时，输出它最后的输出并以 1 退出 |
| `stop` | 停止进程：先发送 SIGTERM，60 秒后发送 SIGKILL |
| `status` | 进程运行时以 0 退出，否则以 3 退出 |
| `restart` | 先 `stop` 再 `start` |
| `run` | 在前台运行，供容器和 systemd 等服务管理器使用 |

`start`、`restart` 和 `run` 接受 `--set key=value` 和 `--labels key=value,...`。进程把自己的 ID 写入 `run/<role>.pid`，
日志写入 `logs/pipeforge-<role>.log`（每天或每 100 MB 换一个文件，保留 14 天）；日志开始之前的输出写入
`logs/pipeforge-<role>.out`。`PIPEFORGE_LOG_DIR` 可以修改日志目录。每个 Task 还会在 `logs/tasks/` 下写自己的日志
（见[日志](./logs)）。

在 Windows 上，`.cmd` 脚本提供除 `restart` 之外的相同命令；由于 Windows 没有 SIGTERM，`stop` 会立即结束进程。

## 配置

设置依次来自 `conf/*.yaml`、`PIPEFORGE_*` 环境变量和 `--set`；[配置参考](../reference/configuration)列出了每个设置及其默认值。
JVM 参数在 `conf/jvm.options` 中，每行一个；一行适用于所有进程，以 `master:`、`worker:` 或 `standalone:` 开头时只适用于对应进程。
`JAVA_OPTS` 为某一次启动追加参数：

```text
-XX:+UseG1GC
master: -Xmx2g
worker: -Xmx4g
```

Checkpoint 写入 `checkpoint.dir` 指定的存储，所有 Master 和 Worker 都必须能访问它：一个目录（使用 NFS 时在每台机器上路径相同），或者
`s3://bucket/prefix`。每个进程启动时都会检查它，见 [Checkpoint 存储](./checkpoint-storage)。此时 Master 还需要在 `conf/master.yaml` 中配置
`master.metastore.url`，即 Server 的[元数据库](./metastore#master)，用来记录 checkpoint。Worker 把 Task 的状态写入同一个存储。

## 端口与安全

| 端口 | 设置 | 谁来连接 |
|---|---|---|
| 6123 | `master.rpc.port` | Worker，以及提交作业的客户端 |
| 6125 | `worker.rpc.port` | Master，用于部署和取消 Task |
| 6124 | `worker.data.port` | 其他 Worker，用于读取 Task 的数据 |

每次调用都携带集群令牌；令牌不同的进程会被以 [`PF-CLUS-0005`](../reference/errors#pf-clus-0005) 拒绝。开启
`security.tls.enabled` 后，进程之间的 RPC 使用 `security.tls.*` 中的 PKCS#12 密钥库和信任库加密。这些端口只应在集群网络内部可达。

## 提交作业

Master 通过它的 RPC（[引擎协议](../development/engine-protocol)中的 `DispatcherService`）接收运行：它用自己的插件规划作业，
把 Task 放到 Worker 的 Slot 上，并跟踪运行。用户和脚本把作业提交给[服务端](./server#在集群上运行作业)，由它保存运行记录并与 Master 通信：
可以使用 `pipeforge run <文件>`（见[集群快速开始](../getting-started/cluster-quickstart)）、[Java 客户端](../development/java-client)、
REST API 或 Web UI。

## 备 Master

一个集群可以运行多个 Master：`cluster.name` 与[元数据库](./metastore#master)（`master.metastore.url`）相同的 Master 通过元数据库
`leader` 表中的租约选出一个主 Master。在不同的机器上以同样的方式启动它们即可，不需要其他设置。只有主 Master 接受注册、心跳和运行；
备 Master 对所有请求返回 [`PF-CLUS-0018`](../reference/errors#pf-clus-0018) `NOT_LEADER` 并给出主 Master，只提供插件包。

- 主 Master 每隔 `master.leader.lease`（默认 15 秒）的三分之一续约一次。
- 备 Master 在自己的时钟上看到租约一整个租约时长都没有变化时才接管，因此各台机器的时钟不需要一致。
- 无法续约的主 Master 在三分之二个租约时长后退位，早于任何备 Master 可以接管的时刻；即使连不上元数据库，它也会停止服务。
- 正常停止的 Master 会交出租约，备 Master 在三分之一个租约时长内接管。失去主 Master 身份的 Master 以退出码 1 退出；重新启动后它作为备 Master
  加入。
- 每个新的主 Master 使用下一个 leader epoch，所有发给 Worker 的请求都带着它。收到过新主 Master 请求的 Worker 会以 `PF-CLUS-0006`
  `RPC_STALE_EPOCH` 拒绝之前的主 Master 的请求，因此被隔离的 Master 无法再控制 Task。

| 配置项 | 文件 | 默认值 | 含义 |
|---|---|---|---|
| `master.host` | `master.yaml` | 本机的主机名 | Worker 和 Server 访问本 Master 的地址；备 Master 用它指出主 Master |
| `master.leader.lease` | `master.yaml` | `15s` | 租约在不续约时的有效时长 |
| `cluster.name` | `pipeforge.yaml` | `default` | 同一个集群的 Master 竞争它的租约 |

没有设置 `master.metastore.url` 时不选主：Master 单独以 epoch 1 运行。

**故障切换。** 把集群中所有 Master 都告诉 Worker 和 Server：`worker.master.address: master-1:6123,master-2:6123`，`pipeforge.master.address`
也设为同样的列表。它们一次只调用一个 Master；指出主 Master 的备 Master 会把它们转过去，没有应答的 Master 会让它们转向下一个。新的主
Master 接管时：

1. Worker 收不到旧主 Master 的心跳应答或被转走，然后向新的主 Master 注册。Worker 向 epoch 更大的主 Master 注册时，会取消之前的主
   Master 的 Task 并释放它预留的 Slot：新的主 Master 不知道它们。
2. Server 发现新的主 Master 不知道它正在运行的运行，于是以同一次尝试重新提交每个运行：从最近完成的 [checkpoint](../concepts/checkpoint)
   继续；还没有 checkpoint 且作业为精确一次交付时从头开始。checkpoint 编号接着该运行已有的编号，Sink 像任何一次重启之后一样提交和中止：
   在作业交付保证的范围内，目标中的行不丢也不重。
3. 没有可以继续的 checkpoint 的运行以 `PF-CLUS-0016` `RUN_LOST` 失败，`env.retry` 允许时会被重试。

使用默认设置时，一次切换大约需要一个租约时长加一个心跳超时，即 15 到 45 秒，另加运行重新启动的时间。


## 运维演练

**手动切换主 Master。** `pipeforge cluster failover` 请主 Master 交出租约（会先确认；`--yes` 跳过确认，不在终端上运行时必须指定）。
备 Master 在 `master.leader.lease` 的三分之一内接管，运行像任何一次[故障切换](#备-master)一样从最近的 checkpoint 在那里继续。旧的主 Master
以退出码 1 退出，由它的进程管理器（systemd 或 Kubernetes）重新启动为备 Master。可以用它逐台升级 Master：先升级一个备 Master，切换到它，
再升级旧的主 Master。没有元数据库的 Master 不选主，会以 `PF-CLUS-0019` 拒绝。

```bash
pipeforge cluster failover --yes
```

**下线 Worker。** `pipeforge cluster drain <worker>` 不再向 Worker 分配新的 Task：它的空闲 Slot 不再提供给任何运行，正在它上面运行的
Task 在原地运行到结束。指定 `--wait` 时命令一直等到上面不再有运行中的 Task（`--timeout`，默认 30 分钟；届时仍有 Task 在运行则以退出码
5 结束），之后就可以停止该 Worker 进行维护，而不会让任何 Task 失败。`pipeforge cluster workers` 把它标记为 `（下线中）`；
`pipeforge cluster uncordon <worker>` 让它重新接收新的 Task。ID 为 `cluster workers` 列出的 ID。

```bash
pipeforge cluster drain 6f1c2b7e-1d8a-4c55-9b0e-7a3f1e2d4c11 --wait --timeout 2h
```

主 Master 会在 Worker 重新注册时保持它的下线状态，但切换主 Master 后不会保留：请在新的主 Master 上再次下线。

## 排障

| 错误 | 原因与处理 |
|---|---|
| `PF-CONF-0011` `SETTING_INVALID` | 设置未知、类型不对，或者缺少 `cluster.token`。错误中给出键以及它来自哪个文件或变量。 |
| `PF-RES-0006` `PORT_IN_USE` | 端口被其他进程占用。请停止该进程或修改端口设置。 |
| `PF-CLUS-0005` `RPC_UNAUTHENTICATED` | 进程之间的集群令牌不同。 |
| `PF-CLUS-0001` `WORKER_LOST` | Worker 不再发送心跳；见[集群](../concepts/cluster#排障)。 |
| `PF-CLUS-0019` `FAILOVER_UNAVAILABLE` | 在不选主的 Master 上执行了 `cluster failover`：请为 Master 配置元数据库并启动备 Master。 |
| `PF-CLUS-0020` `WORKER_NOT_FOUND` | `cluster drain` 或 `uncordon` 指定的 Worker Master 不知道；请使用 `cluster workers` 列出的 ID。 |
| `PF-CLUS-0018` `NOT_LEADER` | Worker 或 Server 连到了备 Master。请把 `worker.master.address` 和 Server 的 Master 地址指向错误中给出的主 Master。 |

## 限制

- 下线只等待 Task 结束：通过 checkpoint 把流式 Task 迁移到其他 Worker 随流式作业一起提供。
- 运行只通过 Server 在新的主 Master 上恢复：不经过 Server、直接提交给 Master 的运行不会被恢复。
- 一次尝试已经运行的时间按 Server 记录的计入 `env.timeout.run`；被恢复的运行不会保留旧主 Master 正在为暂停所做的 savepoint。
- `standalone` 运行 Master 和 Worker；服务向集群提交作业之后才会加入其中。
- 元数据库、checkpoint 和隔离的设置随对应功能一起提供。
