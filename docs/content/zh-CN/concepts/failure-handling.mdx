## 概述

运行中的 Task 失败时，由 JobMaster 决定接下来怎么做。错误的**类型**决定重启是否有用，作业的**重启策略**（`env.restart`）
决定运行还能不能再重启一次、重启前等待多久。重启只涉及失败 Task 所在的 **Region**，它从最近完成的 [checkpoint](./checkpoint)
重新开始，运行的其余部分继续进行。

## 原理

每个错误都带有登记过的[错误码](./errors)，每个错误码都有类型：

| 类型 | 例子 | 运行如何处理 |
|---|---|---|
| 暂时性 | 连接断开（`CONN`）、资源不足（`RES`）、Worker 失联（`CLUS`）、插件标记为暂时性的 Source 或 Sink 错误 | 询问重启策略 |
| 数据 | 类型转换失败、违反约束、坏行过多（`DATA`） | 失败：坏行在 Task 内按[脏数据策略](./dirty-data)处理，带着数据错误到达 Master 的运行重来也会读到同样的行 |
| 致命 | 配置、计划、插件、认证、元数据和内部错误；没有被分类的 Source 和 Sink 错误 | 失败：重试也不会成功 |

类型来自错误码的登记或它的类别。插件可以为单个错误指定类型；所用的库抛出自己的异常时，插件用 `ErrorClassifier`
对它们分类（见[第三方库的错误](../development/api-overview#第三方库的错误)），例如 MySQL Sink 把厂商错误 1045 转换为
`PF-AUTH-0001`（致命），把死锁转换为暂时性的 `PF-SINK-0001`。没有被分类的异常会变成 `PF-SRC-0001`、`PF-SINK-0001`
或 `PF-PLUG-0007`，它们都是致命错误。

只有暂时性的失败会交给重启策略，也只有它们计入重启次数：

| 策略 | 重启方式 |
|---|---|
| `fixed-delay`（默认） | 一共重启 `restart.attempts` 次，每次等待 `restart.delay` |
| `exponential-backoff` | 不限次数；第一次等待 `restart.initial`，之后每次是上一次的 `restart.multiplier` 倍，最长 `restart.max`。与上一次失败相隔超过 `restart.reset-after` 时重新从 `restart.initial` 开始 |
| `failure-rate` | 只要最近 `restart.interval` 内（包括这一次）失败不超过 `restart.max-failures` 次，就等待 `restart.delay` 后重启 |
| `none` | 从不重启 |

### Region 重启

Region 是互相交换数据的一组 Task。最常见的批处理作业中，每个子任务从 Source 到 Sink 是一条链，各自成为一个 Region；
hash 或 rebalance 交换两侧的 Task 合为一个 Region。策略允许重启且运行做 checkpoint 时：

1. JobMaster 取消失败 Region 中的 Task，并放弃进行中的 checkpoint（它们已无法完成）。其他 Region 继续运行。
2. 这些 Region 的 Reader 在最近完成的 checkpoint 之后拿到的分片交回 Enumerator，由它再次分配。
3. 等待策略给出的时间（失联 Worker 上的 Task 至少等待两倍的取消超时，确保 Worker 已经 [fencing](./cluster)），并且 Region 中的
   Task 都已停止后，重新部署它们：Worker 失联的使用新的 Slot，每个 Task 带着它在该
   checkpoint 中的状态。Reader 从 checkpoint 记录的位置继续读取分片；Writer 拿到自己的状态，并 abort 在它之后预提交的内容。

Sink 已提交的内容保持提交：checkpoint 完成时提交它的待提交物，为失败的 checkpoint 预提交的内容与下一个完成的 checkpoint 一起提交。
因此两阶段提交的 Sink 在重启前后每行恰好写入一次；其他 Sink 会再次写入 checkpoint 之后的行（至少一次）。没有 checkpoint，
或者第一个 checkpoint 完成之前，Region 从分片的开头重新开始。

### 运行重试

运行整体失败时——重启次数已用完、失败不是 Task 的失败，或者运行不做 checkpoint——Server 可以为它开始**新的尝试**（`env.retry`）：
运行 ID 不变，变量、调度时间和插件版本也不变。失败的错误属于 `retry.on`（`CONN` 等错误类别、错误码，或者表示所有暂时性错误的
`TRANSIENT`）、运行还有重试次数（`retry.attempts`，默认 0）、并且距提交不超过 `retry.within` 时才会重试。运行先在 **`RETRY_WAIT`**
中等待退避时间——第一次为 `retry.backoff.initial`，之后每次乘以 `multiplier`，最长 `retry.backoff.max`——再重新排队。

| `retry.resume` | 新的尝试从哪里开始 |
|---|---|
| `auto`（默认） | 按 exactly-once 交付的作业（每个 Sink 都两阶段提交或幂等写入）从运行最近完成的 checkpoint 继续，没有时从头开始：两者都不会重复写入。按 at-least-once 交付的作业不重试，因为两者都可能重复写入；请设置 `checkpoint` 或 `restart`，或者手动重试 |
| `checkpoint` | 从最近完成的 checkpoint 继续，没有时从头开始 |
| `restart` | 从头开始 |

每次尝试都会记录状态、时间、错误以及它从哪个 checkpoint 开始，每次状态变化也标明所属的尝试。运行的计数——读取、写入、作为坏行跳过、
失败的行数以及耗时——跨尝试累计；每个采样保存所属尝试的指标。

## 快速上手

目标端不稳定、允许不限次数重启、每次等待更久的作业：

```yaml
env:
  restart:
    strategy: exponential-backoff
    initial: 10s
    max: 5m
```

## 配置

| 选项 | 默认值 | 含义 |
|---|---|---|
| `env.restart.strategy` | `fixed-delay` | `none`、`fixed-delay`、`exponential-backoff` 或 `failure-rate` |
| `env.restart.attempts` | `3` | `fixed-delay`：一共重启多少次 |
| `env.restart.delay` | `10s` | `fixed-delay` 和 `failure-rate`：每次重启前等待多久 |
| `env.restart.initial` | `1s` | `exponential-backoff`：第一次重启前等待多久 |
| `env.restart.max` | `5min` | `exponential-backoff`：最长等待多久 |
| `env.restart.multiplier` | `2` | `exponential-backoff`：每次等待是上一次的多少倍 |
| `env.restart.reset-after` | `1h` | `exponential-backoff`：这么久没有失败后等待时间重新开始 |
| `env.restart.max-failures` | `3` | `failure-rate`：时间窗口内允许的失败次数 |
| `env.restart.interval` | `5min` | `failure-rate`：时间窗口 |

[作业 DSL 参考](../reference/job-dsl#env)列出了每个选项的取值。所选策略用不到的 `restart.*` 选项会在计划作业时给出警告。

## 示例

十分钟内最多失败五次，每次间隔一分钟：

```yaml
env:
  restart:
    strategy: failure-rate
    max-failures: 5
    interval: 10m
    delay: 1m
```

第一次出错就失败，适合有人值守、手动重跑的作业：

```yaml
env:
  restart:
    strategy: none
```

## 行为与语义

- Task 的每次失败计一次；它所在 Region 的其他 Task 停止时报告的错误不再分类。导致运行失败的错误会取消所有 Task。
- JobMaster、Enumerator 或提交出错时运行失败：只有 Task 会重启。
- 不做 checkpoint 的运行不重启 Task：暂时性的失败也会让它失败。
- 致命错误和数据错误立即让运行失败，不消耗重启次数。
- `fixed-delay` 的次数在一次运行中不会恢复；`failure-rate` 会忘掉移出窗口的失败；`exponential-backoff` 不会用尽。

## 可观测性

JobMaster 在日志中记录每一次决定：错误、它的类型，以及策略是否允许重启、等待多久，或者已经不允许再重启。
重启时还会记录重启的 Task、交回 Enumerator 的分片以及 Task 恢复自哪个 checkpoint。

## 排障

| 问题 | 原因与解决 |
|---|---|
| 还有重启次数，连接错误却让运行失败 | 插件把它报告为 `PF-SRC-0001` 或 `PF-SINK-0001`，没有标记为暂时性。应由插件的 `ErrorClassifier` 转换这个异常 |
| Worker 失联或连接断开，还有重启次数，运行却失败了 | 运行没有做 checkpoint：在集群上设置 `checkpoint.dir`，并保持 `env.checkpoint.enabled` 开启 |
| 警告 `has no effect with restart.strategy` | 设置了其他策略的选项；删除它或者更换策略 |
| [`PF-CONF-0002`](../reference/errors#pf-conf-0002) `restart.max` | `restart.max` 小于 `restart.initial` |

## 限制

- 重启后的 Task 计数从零开始，因此运行的行数不包含它之前的尝试读写的行。
- 超过两倍取消超时仍不响应取消的 Task 会被放弃，但它的线程可能仍在运行，与 Region 的新尝试同时写入。
- 失败后回滚已写入的数据以及手动重试运行还不可用。
- `TRANSIENT` 是否匹配按错误码登记的类型判断，不考虑插件为某个错误指定的类型。
