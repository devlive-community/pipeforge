## 概述

作业[规划](./plan-and-explain)完成后，由引擎运行。本页说明运行时发生了什么：有哪些线程、一行数据如何从 Source 到达 Sink、
读和写如何重叠、作业如何取消，以及失败如何上报。

本地模式（单个进程）和集群使用同一套运行时：本地模式用进程内实现替代集群中通过 RPC 实现的接口，因此同一个作业在两种形态下行为一致。
Task 收到的描述使用与 Worker 从 Master 收到的相同的二进制格式（先写出再读回），因此每次本地运行也都在检查这个格式。
当前版本的引擎以本地模式运行。

## 原理

### 算子链与 Task

大多数数据集成作业不需要 shuffle：Source、它的 Transform 和 Sink 一对一相连，并行度相同。引擎把它们合并成一条**算子链**，
每个并行实例运行一个 **Task**。Task 内部的算子直接互相调用：一行数据走完整条链之后，Reader 才输出下一行，算子之间不做任何序列化。

```text
作业：src (p=2) → map (p=2) → out (p=2)

Task src-0：reader → map → writer        线程 task-src-0（+ writer-src-0）
Task src-1：reader → map → writer        线程 task-src-1（+ writer-src-1）
```

### 执行图与分区方式

在集群上，作业不一定是一条直线。Master 把计划转换为**作业图**：如果一个节点是前一个节点的唯一下游、不读取其他节点、
并行度相同，并且一对一地接收数据，它就并入前一个节点所在的链。链结束的地方由一条边决定数据如何分发到下一条链的各个实例：

| 分区方式 | 引擎何时选择它 |
|---|---|
| `forward` | 两侧并行度相同：实例 i 发给实例 i |
| `rebalance` | 并行度变化：数据轮询分发到所有实例 |
| `hash(keys)` | 并行度大于 1 的 Sink 可能收到更新或删除：同一主键（多表时为同一张表的同一主键）的变更总是按顺序到达同一个 Writer |
| `table`、`broadcast` | 引擎可以运行它们（`table`：按表名的哈希把每张表固定发给一个实例；`broadcast`：每行发给所有实例），但目前还没有规则会选择它们 |

`hash` 和 `table` 的哈希只取决于取值，因此在每个 Worker 上、每次运行中，同一个键都会到达同一个实例。

**执行图**把每条链按并行度展开为 Task。通过边相连的 Task 组成一个 **Region**；互不交换数据的 Task 属于不同的 Region，
一个 Region 失败不会影响其他 Region。各条链共享 Slot：每条链的实例 i 运行在 Slot i 中，因此作业需要的 Slot 数等于它的最大并行度。在集群上，每个 Task 都运行在调度器为作业在其 Worker 上预留的 Slot 中。

```text
cdc (p=1) → route (p=1) → doris (p=4)，含更新

链 cdc+route (p=1) ──hash(id)──► 链 doris (p=4)
Task：cdc[0]  doris[0] doris[1] doris[2] doris[3]    一个 Region，4 个 Slot
```

在计划层推导出哪些节点会产生更新或删除之前，无界的 Source 被视为可能产生，它之后的节点也一样：多余的 `hash`
只影响吞吐，缺少它却会打乱同一主键的变更顺序。

不以 Source 开头的链，它的每个 Task 从前一条链的 Task 读取数据；不以 Sink 结尾的链，它的每个 Task 把数据写给下一条链的 Task——
两端在同一个 Worker 上时在内存中交接，否则经过网络（见下文）。本地运行（`pipeforge run --local`）在进程中启动一个 Master 和一个 Worker，连接方式与集群相同：Worker 注册并发送心跳，调度器预留它的 Slot，
Task 通过同样的协议向 JobMaster 报告。只有一个 Worker 时，Task 在内存中交换数据。`--workers 3`（testkit 使用系统属性 `pipeforge.local.workers`）
启动三个 Worker，它们的 Task 像在集群上一样通过回环地址上的 TCP 交换数据；运行的输出和退出码不变。

### 拉模式分片

Source 的分片枚举器（SplitEnumerator）运行在 JobMaster 中。Reader 启动时请求一个分片，每读完一个分片再请求下一个；
枚举器回复下一个分片，或者“没有更多分片”。读得快的 Reader 自然多领分片，从而抵消数据倾斜。分片用 Source 的分片序列化器序列化后发给 Task，
与跨机器传输时完全相同。

### Mailbox

每个 Task 有一个线程和一个 **mailbox**。线程交替处理 mail（分片分配、取消，以及后续的 checkpoint 和定时器）和读取数据：

```text
循环：
  处理待处理的 mail
  reader.pollNext → transform → sink
  暂时没有数据？等待 mail，从 1 毫秒开始翻倍，最多 100 毫秒
```

事件和数据在同一个线程中处理，因此算子不需要加锁，状态快照也总是一致的。

### 异步写缓冲

开启写缓冲（默认开启）时，Sink 在自己的线程中写入，读和写可以重叠：

```text
Task 线程：… → 攒批 ──► 有界队列 ──► 写线程：SinkWriter
                     满了就阻塞
```

目标端比源端慢时，队列被填满，Task 线程阻塞：这就是让 Reader 慢下来的背压。输入结束时，Task 等待所有批次写完，然后让 Writer 准备提交。

### 数据交换与背压

不同算子链的 Task 相连时，上游 Task 把行写入一个**输出**，每个下游子任务对应其中一个子分区；每个下游 Task 读取一个**输入**，
每个上游子分区对应其中一个通道。

- 行被打包进 Worker 网络内存中 32 KB 的网络缓冲。缓冲满了、低流量时超过缓冲超时（100 毫秒）、或者遇到事件之前，都会被发送。
  比缓冲大的行单独占用一个缓冲；超过 `task.max-row-bytes` 的行以 [`PF-DATA-0007`](../reference/errors#pf-data-0007) 失败。
- 事件（子分区结束、有界输入结束、表结构变化）与行在同一条流中传输，因此它们恰好位于之前和之后写入的行之间。
- **credit**：每个输入通道有 2 个专属缓冲，生产者报告积压时，还可以从输入的 8 个浮动缓冲中借用。只有通道有 credit 时，
  生产者才发送数据缓冲；事件不需要 credit。
- **背压**：慢的消费者不再给出 credit，生产者的缓冲被占满，写下一行时等待空闲缓冲。等待一直传到 Source，使它停止读取。
  只有这个输出被拖慢：同一条连接上的其他通道照常传输。
- 同一 Worker 上的 Task 在内存中交接缓冲，credit 和顺序规则相同。不同 Worker 上的 Task 之间，每对 Worker 使用一条 TCP 连接，
  所有通道共用；空闲的连接每 30 秒发送一次 ping，连续三个间隔没有任何消息的连接会被关闭。
- 连接断开时，两端的 Task 都以 [`PF-CLUS-0010`](../reference/errors#pf-clus-0010) 失败。

### 限流

`env.limit.rows-per-second` 和 `env.limit.bytes-per-second` 限制作业所有 Source 合计的读取速度，用于保护源端系统或与其他作业
共享它。JobMaster 每秒把限额分给运行中的 Reader，依据是每个 Reader 上一秒的用量：等待过配额的 Reader 得到其他 Reader 没用完的部分，
空闲的 Reader 保留均分额的十分之一以便重新开始，新的 Reader 从均分额开始，已经结束的 Reader 交出它的份额。每个 Reader 用最多
容纳 50 毫秒配额的令牌桶执行配额，因此不能突发追赶；字节按行在内存中占用的大小计算。

Reader 等待配额的时间计入 `throttleWaitMs`，运行分析把受限流拖慢的作业报告为 `THROTTLE`。自己限制速度的 Source
（`SupportsRateLimit`）直接得到它的行配额，引擎不再拖慢它。运行中的作业可以修改限额，Reader 立即得到新的配额。

### 输入结束时提交

两阶段提交的 Sink 在 `prepareCommit` 中返回待提交内容（committable）。所有 Task 都结束后，JobMaster 先用 Sink 的 Committer、
再用 GlobalCommitter 提交它们，之后才报告 `SUCCESS`。没有 checkpoint 的运行只提交一次，记为第 1 次 checkpoint。

### 作业状态

| 状态 | 含义 |
|---|---|
| `CREATED` | 已接受，正在等待 Slot，随后部署 Task |
| `RUNNING` | Task 正在运行 |
| `CANCELLING` | 收到取消请求，Task 正在停止 |
| `SUCCESS` | 所有 Source 都已结束，所有 Sink 都已写完并提交 |
| `FAILED` | 某个 Task、枚举器或提交失败；结果中带有错误 |
| `CANCELLED` | 按请求停止 |

在集群上，Master 的 Dispatcher 接收 Server 提交的运行，并按以下状态跟踪它们（当前版本的子集）：

| 从 | 到 |
|---|---|
| `QUEUE`（等待 Slot） | `RUNNING`、`CANCELLING`、`FAILED` |
| `RUNNING` | `SUCCESS`、`FAILED`、`CANCELLING` |
| `CANCELLING` | `CANCELLED`、`FAILED`、`TIMEOUT`（运行超过超时时间而被取消） |

每次状态转换都会被校验，并记录时间和原因；不在表中的转换会被拒绝。提交 Master 已知的运行 ID 时返回这个已有的运行，
因此重试提交永远不会启动第二次运行。Master 用 Server 选定的插件版本重新规划作业定义；Master 没有该版本时，提交以
[`PF-PLUG-0009`](../reference/errors#pf-plug-0009) 失败；未知的运行 ID 为 [`PF-CONF-0010`](../reference/errors#pf-conf-0010)。

每次运行都有一个 **JobMaster** 负责从开始到结束：

1. 获取本次运行的 Slot：在集群上由[调度器](./cluster)在 Worker 上预留；在单个进程中由本地的 TaskExecutor 运行所有 Task。
2. 启动分片分配器，为每个子任务把一个 Task 部署到它的 Slot 中。
3. 跟踪 Task 上报的状态。第一个失败会取消其他 Task，并成为本次运行的错误；[Worker 失联](./cluster)时运行以
   `PF-CLUS-0001` 失败，错误位置为在该 Worker 上运行的节点与子任务。
4. 所有 Task 完成后，提交 Sink 准备好的内容，运行成功。
5. 无论以何种方式结束，都会归还 Slot。在等待 Slot 时被取消的运行会立即结束；之后才到达的 Slot 同样会被归还。

## 快速上手

通过 `pipeforge-engine-local` 嵌入引擎；命令行的 `pipeforge run --local` 使用的也是同一套 API。

```java
JobPlan plan = new Planner(components).plan(JobParser.parse(yaml, VariableContext.builder().build()));
try (Engine engine = new LocalEngine()) {
    JobHandle handle = engine.submit(plan);
    JobResult result = handle.result().get();
    System.out.println(result.status());          // SUCCESS
}
```

## 配置

引擎设置在每次提交时通过 `SubmitOptions` 指定：

| 设置 | 默认值 | 作用 |
|---|---|---|
| `asyncWriteBuffer` | `true` | 在独立线程中写入，中间是有界队列；`false` 表示在 Task 线程中直接写入 |
| `writeBatchSize` | `1024` | 每批交给写线程的行数 |
| `writeQueueCapacity` | `4` | 队列最多容纳的批数，满了之后 Task 线程阻塞 |
| `cancelTimeout` | `30s` | 取消后 Task 停止的等待时间，超过后中断其线程；超过两倍时间后放弃该 Task |
| `enumeratorTimeout` | `60s` | 分片分配器单次调用的最长时间；超过时作业以 `PF-SRC-0004` 失败 |
| `metricsInterval` | `1s` | Task 上报指标、作业指标和速率刷新的周期 |

每个 Task 的并行度来自作业：`env.parallelism` 或节点的 `parallelism`。

数据交换按 Worker 配置；Worker 作为独立进程运行（集群发行包）之后才会读取这些设置：

| 设置 | 默认值 | 作用 |
|---|---|---|
| `worker.memory.network` | 内存的 10%（64 MB–1 GB） | 网络缓冲使用的内存 |
| `network.buffer-size` | `32KB` | 网络缓冲的大小 |
| `network.buffers-per-channel` | `2` | 每个输入通道的专属缓冲数 |
| `network.floating-buffers-per-gate` | `8` | 生产者报告积压时，一个输入在各通道之间共享的缓冲数 |
| `network.buffer-timeout` | `100ms` | 未满的缓冲在多久之后也会被发送 |
| `task.max-row-bytes` | `64MB` | 单行的大小上限 |

一个输入需要 `buffer-size × (buffers-per-channel × 通道数 + floating-buffers-per-gate)`，一条边的通道数为上游并行度乘以下游并行度。

## 示例

### 四个并行 Reader

```yaml
version: 1
name: orders-copy
env:
  parallelism: 4
source:
  - { id: src, type: jdbc, table: demo.orders }
transform:
  - { id: map, type: field-mapper }
sink:
  - { id: out, type: jdbc, table: dw.orders }
```

引擎运行 `src-0` 到 `src-3` 四个 Task，每个都有自己的 Reader、映射器和 Writer。枚举器把表按主键切成若干范围，空闲的 Reader 领取下一个范围。

### 取消作业

```java
JobHandle handle = engine.submit(plan);
handle.cancel();
handle.result().get().status();   // CANCELLED
```

`cancel` 立即返回。每个 Task 被唤醒，Reader 的 `cancel()` 和对写线程的中断让阻塞中的调用返回；所有 Task 停止后，作业以 `CANCELLED` 结束，
不提交任何内容。与 [Master](./cluster) 失联的 Worker 也以同样的方式取消它的所有 Task。

## 行为与语义

- **每个 Task 只有一个最终状态。** Task 报告带 committable 的 `FINISHED`、带错误的 `FAILED` 或 `CANCELED`，JobMaster 据此决定作业状态。
- **以第一个失败为准。** 第一个失败会取消其他 Task，并成为作业的错误。本地模式不重启 Task；Region 重启随分布式引擎的 checkpoint 一起提供。
- **取消逐级升级。** 先调用 Reader 的取消钩子并中断写线程；超过 `cancelTimeout` 后中断 Task 线程；超过两倍 `cancelTimeout` 后以
  `PF-RES-0005` 放弃该 Task，作业失败。
- **插件代码隔离。** 每次调用插件代码时，都把插件的 ClassLoader 设为上下文 ClassLoader，插件抛出的异常会转换为带错误码的错误（见“排障”）。
- **统一的运行开始时间。** JobMaster 确定本次运行的开始时间并交给每个 Task，因此表达式中的 `RUN_START_TIME()` 在所有 Task 中都相同。
- **顺序。** 在一个 Task 内，无论是否开启写缓冲，行和 Schema 变更都按 Reader 输出的顺序到达 Sink。

## 可观测性

作业结果中包含最终状态、带错误码和定位（作业、运行、节点、子任务）的错误，以及[指标](../reference/metrics)；作业运行期间
`JobHandle.metrics()` 返回当前指标，每隔 `metricsInterval` 刷新一次。

- **采集。** 每个算子按行计数，每行每个计数器只做一次 `LongAdder` 自增。无论 Task 运行在哪个 Worker 上，它都每隔 `metricsInterval`
  把计数快照发给 JobMaster，结束时随最终状态再发一次；JobMaster 按节点和作业汇总。快照中是累计值，因此丢失或迟到的上报只会让指标暂时滞后，
  不会让它出错。Worker 失联后，它上面的 Task 按最后一次上报计数，之后到达的上报会被忽略。
- **行数。** `rowsRead` 是 Source 输出的行数，`rowsWritten` 是 Sink 写入的行数（两阶段提交的 Sink 为已提交的行数），`rowsFiltered`
  和 `rowsExpanded` 是 Transform 丢弃和多出的行数，`rowsInFlight` 是已读取但还没有被 Sink 接收的行数，大多在写队列中。作业失败或被取消时，没有到达目标端的行计为
  `rowsFailed`。这些计数始终满足对账恒等式，作业运行中也是如此：`rowsRead + rowsExpanded = rowsWritten + rowsFiltered + rowsFailed + rowsInFlight`。
- **速率。** 读写速率每个周期采样一次：最近 5 秒的瞬时速率、全程平均速率和 1 秒内的峰值。
- **自身耗时。** `selfTimeRatio` 是节点自身代码（不含其下游节点）占运行时间的比例。每 16 次读取测量一次，热路径上不必每行都读取时钟；
  开启写缓冲的 Sink 取写线程的忙碌时间。
- **等待。** `readerWaitMs` 是 Task 因写队列已满或达到 [Task 内存](../operations/isolation)上限而阻塞的时间（目标端慢），`writerWaitMs` 是写线程等待数据的时间（源端慢），
  `backpressuredMs` 是 Task 等待网络缓冲的时间（它发送数据的下游 Task 更慢），`backpressuredRatio` 是它占运行时间的比例。
- **数据交换。** `exchangedBytes` 统计 Task 发给其他 Task 的行的字节数；按节点看，`bytesOut` 是一条链的最后一个节点发出的字节数，
  `bytesIn` 是下一条链的第一个节点收到的字节数。
- **队列与分片。** `queueDepth` 和 `queueCapacity` 显示 Sink 写队列当前的占用。`splitsAssigned` 统计分片分配器分出的分片数，
  `splitsFinished` 统计已结束的 Reader 的分片数：Reader 不会单独报告每个分片。

`AnalyzeText` 按 `explain --analyze` 展示运行结果的格式输出[运行分析](./plan-and-explain#运行分析)：

```text
Job orders-copy  SUCCESS 12.4s  parallelism 4
Rows   read 1,000,000  written 999,000  filtered 1,000  in-flight 0  failed 0   reconcile OK
Rate   read 0 r/s (avg 80,645, peak 91,200)   write 0 r/s (avg 80,564, peak 91,000)
Wait   reader 1.2s (target slow)  writer 300ms (source slow)  backpressured 0ms (downstream slow)

Node  kind       in rows    out rows   sel.  in r/s  self%
src   source     1,000,000  1,000,000  -     -       21%
map   transform  1,000,000  999,000    1.00  80,645  4%
out   sink       999,000    999,000    -     80,565  68%

Bottleneck  TARGET at out: out busy 68%; write threads waited 1% of their time for rows
  → Raise the parallelism of out (now 4) or its batch size, if the target can take more writes
  → Check the write latency and the load of the target system
```

每个 Task 在开始运行、结束、失败或被取消时写日志，写入它在 Worker 上的单独日志文件，Task 结束后仍可读取（见[日志](../operations/logs)）；
JobMaster 记录作业的启动、提交和结束。

## 性能与调优

- 保持写缓冲开启：读写可以重叠，目标端变慢时会通过背压限制源端，而不是逐行停顿。
- 目标端适合大批量写入时调大 `writeBatchSize`；需要降低每个 Task 占用的内存时调小（最多占用 `writeBatchSize × writeQueueCapacity` 行）。
- 更大的 `writeQueueCapacity` 可以吸收目标端的短暂变慢，但目标端平均速度较慢时没有帮助。
- 并行度越高，Task 和线程越多；Source 的分片需要足够细，才能让它们都有活干。
- `readerWaitMs` 高且 Sink 的 `selfTimeRatio` 高，说明瓶颈在目标端；`writerWaitMs` 高说明瓶颈在源端。
- 在 Task 之间，输出等待缓冲的时间（`backpressuredMs`）说明下游更慢；下一个 Task 的输入等待时间说明它在等上游。
  更多的浮动缓冲可以吸收突发流量，但对平均速度更慢的消费者没有帮助。

## 排障

| 错误 | 含义 |
|---|---|
| `PF-SRC-0001` | Source 的 Reader 或枚举器抛出了未分类的错误；原因中会写明操作，例如 `read` 或 `start the enumerator` |
| `PF-SINK-0001` | Sink 的 Writer 抛出了未分类的错误，例如写入一行或 flush 时 |
| `PF-SINK-0003` | 数据已写入，但提交失败，或重试 3 次后仍被拒绝 |
| `PF-PLUG-0007` | Transform 处理一行数据时失败 |
| `PF-RES-0005` | 被取消的 Task 既不响应取消也不响应中断；请为连接器配置连接或查询超时 |
| `PF-PLAN-0012` | 作业的形态当前版本无法运行，或者表结构变化到达了数据交换（见“限制”） |
| `PF-CLUS-0010` | 两个 Worker 之间的数据连接断开；两端的 Task 都会失败 |
| `PF-CLUS-0011` | Task 请求的上游输出没有及时出现在它的 Worker 上；请查找本次运行的第一个错误 |
| `PF-RES-0008` | Worker 的网络内存放不下一个输入需要的缓冲；请调大 `worker.memory.network` 或降低并行度 |
| `PF-DATA-0007` | 一行的大小超过了 `task.max-row-bytes` |

连接器用自己的错误码上报的错误保留原错误码，引擎会在其定位中补充节点和子任务。完整列表见[错误码参考](../reference/errors)。

## 限制

- 作业是一条流水线：一个 Source、它的 Transform 和一个 Sink，每个节点读取前一个节点；节点之间的并行度可以不同。多个 Source 或 Sink、
  一个节点输出到多个下游、一个节点读取多个上游，都会以 `PF-PLAN-0012` 失败。
- 表结构变化目前还不能跨越数据交换：到达一条链末尾、而这条链的数据要发给另一条链时，表结构变化会让该 Task 以 `PF-PLAN-0012` 失败。
  所有节点并行度相同的作业运行在一条链中，不受影响。
- 没有 checkpoint：失败或取消的作业再次运行时从头开始，两阶段提交的 Sink 在输入结束时提交一次。
- 没有重启：第一个 Task 失败即作业失败。
- 流式作业一直运行，直到被取消。
