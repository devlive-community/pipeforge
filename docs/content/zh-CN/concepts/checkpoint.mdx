## 概述

**checkpoint** 是运行中作业的一致快照：每个 Source 读到了输入的哪里，每个 Sink 准备提交什么，以及 Source 还没有分配出去的分片。
它被写入 [Checkpoint 存储](../operations/checkpoint-storage)并记录在[元数据库](../operations/metastore)中，这样失败的运行可以从最近的 checkpoint 继续，
而不是从头开始；Sink 提交的也正好是一个已记录的 checkpoint 所覆盖的数据。

只有设置了 `checkpoint.dir` 的集群才会做 checkpoint；作业通过 `env.checkpoint.*` 控制频率和数量。

## 原理

每个 checkpoint 都由 Master 协调：

1. Master 先取 Source 的分片枚举器的状态，再通知读取 Source 的 Task 参与 checkpoint *n*。
2. 这些 Task 取自己的状态，并随数据向下游发送 **barrier**；其他 Task 在所有输入都收到 *n* 的 barrier 后取自己的状态。
   barrier 是数据流中的标记，它之前的行属于这个 checkpoint，之后的不属于。
3. 每个 Task 向 Master 确认自己的部分，并告知状态保存在哪里。
4. 收齐所有 Task 的确认后，Master 写入 checkpoint 的 `_metadata`，在元数据库中把它记为已完成，**然后**才通知各个 Task 它已完成，
   Sink 此时才提交为它准备的数据。

第 4 步的顺序很关键：元数据库中最近完成的 checkpoint 永远不会早于 Sink 已提交的数据，因此从它重新开始的运行不会把同一批数据提交两次。

Task 拒绝、在 `env.checkpoint.timeout` 内没有完成、或者 Master 无法写入或记录时，checkpoint **失败**。已经写入的部分会被删除，
在下一个间隔再尝试。连续失败超过 `env.checkpoint.tolerable-failures` 次时运行失败，因为此时一旦出错丢失的进度会超过作业允许的范围。

### barrier 与对齐

Source Task 在两次读取之间、在自己的线程上取 Reader 的状态（它的分片以及每个分片读到哪里），然后把 barrier 发出去：快照之前读到的每一行都在 barrier 之前。
链在一起的 Task 直接把 barrier 往下传。从多个上游 Task 读取数据的 Task（例如 hash 交换之后的 Writer）需要**对齐**：某个输入通道收到 *n* 的 barrier 后，
它不再读取这个通道，继续读取其他通道，直到它们的 barrier 也到达；之后才取自己的状态并继续传递 barrier。已经结束的通道不会拖住对齐。
等待中的通道不再接收新的缓冲，因此上游 Task 会放慢，而不是让数据堆积。

分片也不会错位。Source 的枚举器在作业运行期间持续分配分片，一个分片可能在枚举器取状态之后才被分配、又在 Reader 取状态之后才送达，
这样它就不在任何一个状态中。Master 会避免这种情况：取完枚举器的状态后，它先等之前发出的分片都送达 Reader，再通知 Reader 做 checkpoint；
之后分配的分片在 Master 处等待，直到对应的 Reader 取完状态，再按顺序发出。每个分片恰好在两者之一中。

取状态只是复制一份；写入 checkpoint 存储在 Worker 的其他线程上进行，Task 同时继续读取，状态写完后 Task 才确认。不超过 16 KB 的状态随确认一起发送，
最终保存在 `_metadata` 中。

### savepoint

**savepoint** 是按需触发、一直保留到手动删除的 checkpoint。它写在 checkpoint 存储的 `<run>/savepoints/<名称>-<时间>/` 下；名称只能包含
字母、数字、`_`、`-` 和 `.`，不指定时为 `savepoint`。做 savepoint 不会让运行停下，Sink 也像普通 checkpoint 一样提交为它准备的内容。
在当前版本中，savepoint 通过 Master 的 `TriggerSavepoint` 调用触发（见[引擎协议](../development/engine-protocol)）；命令行和 REST 接口随后提供。

**运行可以从 savepoint 或已完成的 checkpoint 开始**，只需给出它的目录（运行的 `restore.path`）。Master 读取它的 `_metadata`，恢复 Source 的
Enumerator 和每个 Task 的状态，并先把 Sink 为该点准备的内容重新提交一次（Committer 会把已经提交过的内容当作已提交）。它必须由同一个作业
产生，除非允许其他作业（`allow_other_job`）；有状态的节点必须仍然存在，除非允许丢弃这些状态（`allow_non_restored_state`）；有状态的节点
不能改变并行度。在运行完成自己的第一个 checkpoint 之前，重启的 Task 都从这个点恢复；运行的 checkpoint 编号接在它之后。

运行可以用 savepoint **暂停**（`StopWithSavepoint`）：Source 在 barrier 之后不再读取，savepoint 完成且 Sink 提交之后，Task 被取消，运行进入
`PAUSED`，不再占用 Slot。以该 savepoint 作为恢复点再次提交这个运行即可**继续**：新的尝试从暂停处接着运行，目标端的结果与没有暂停时一致。
savepoint 失败时 Source 继续读取，运行照常进行；已暂停的运行也可以直接取消。

## 快速上手

在 `conf/pipeforge.yaml` 和 `conf/master.yaml` 中为集群配置 checkpoint 存储，并为 Master 配置元数据库：

```yaml
checkpoint.dir: s3://my-bucket/pipeforge
master.metastore.url: jdbc:postgresql://db:5432/pipeforge
```

作业默认每分钟（流式）或每五分钟（批处理）做一次 checkpoint；可以在作业中设置其他间隔：

```yaml
env:
  checkpoint.interval: 30s
```

## 配置

| 选项 | 默认值 | 含义 |
|---|---|---|
| `env.checkpoint.enabled` | `true` | 是否做 checkpoint |
| `env.checkpoint.interval` | 流式 `1min`，批处理 `5min` | 两次 checkpoint 之间的间隔；对批处理作业，它决定失败的运行最多重读多少数据 |
| `env.checkpoint.timeout` | `10min` | 一次 checkpoint 最长可以用多久，超过即失败 |
| `env.checkpoint.min-pause` | `0` | 一次 checkpoint 结束到下一次开始的最短间隔 |
| `env.checkpoint.max-concurrent` | `1` | 同时进行的 checkpoint 数 |
| `env.checkpoint.tolerable-failures` | `3` | 连续失败多少次之后运行失败 |
| `env.checkpoint.retained` | `3` | 保留的已完成 checkpoint 数，更早的会被删除 |
| `env.checkpoint.externalized` | `RETAIN_ON_CANCELLATION` | 运行被取消后保留（`RETAIN_ON_CANCELLATION`）还是删除（`DELETE_ON_CANCELLATION`）它的 checkpoint |
| `env.checkpoint.on-finish` | `true` | 有界运行结束前，先记录一个包含 Sink 预提交内容的最后 checkpoint，再提交这些内容 |

集群一侧是 `checkpoint.dir` 和 `checkpoint.s3.*`（见 [Checkpoint 存储](../operations/checkpoint-storage)）以及 `master.metastore.*`
（见[元数据库](../operations/metastore#master)）；[配置参考](../reference/configuration)列出了全部配置项。

## 示例

不允许 checkpoint 失败、保留最近十个的流式作业：

```yaml
env:
  mode: streaming
  checkpoint.interval: 20s
  checkpoint.timeout: 2min
  checkpoint.tolerable-failures: 0
  checkpoint.retained: 10
```

不做 checkpoint 的作业，用于预览：

```yaml
env:
  checkpoint.enabled: false
```

## 行为与语义

| 保证 | 需要 |
|---|---|
| at-least-once | 开启 checkpoint，并且 Source 能从某个位置重新读取 |
| 效果上的 exactly-once | at-least-once，并且 Sink 按主键幂等写入 |
| exactly-once | at-least-once，并且 Sink 两阶段提交 |
| 故障恢复后的 exactly-once | at-least-once，Source 能按位置续传，Sink 与数据一起记录位置（[进度表](../plugins/sink/jdbc#进度表)），两者在同一个 Task 中 |
| 无保证 | 关闭 checkpoint：失败的运行从头开始 |

- 同一个运行中 checkpoint 编号只增不减，重启之后也不会重复。
- 只有运行的所有 Task 都在运行时才会开始 checkpoint。
- savepoint 由用户手动触发，不会被自动删除；它不计入 `retained`，也不计入作业允许的失败次数。
- 有界运行的所有 Task 都结束后，Master 记录**最后一个 checkpoint**（`env.checkpoint.on-finish`）：它包含 Sink 在输入结束时预提交、
  尚未提交的内容，写入 `_metadata` 并记为已完成之后，才提交其中的内容。进行中的 checkpoint 被放弃，之后也不再做新的。
  `on-finish: false` 时 Master 不先记录，直接提交 Sink 预提交的内容。
- 运行结束时，进行中的 checkpoint 被放弃。**成功**的运行删除自己的 checkpoint（包括最后一个），**失败**的运行保留它们以便继续，
  **被取消**的运行按 `env.checkpoint.externalized` 处理。

## 可观测性

| 指标 | 含义 |
|---|---|
| `lastCompletedCheckpointId` | 最近完成的 checkpoint，第一个完成之前为 0 |
| `lastCheckpointDurationMs` | 它从触发到被记录的耗时 |
| `lastCheckpointSize` | 它的状态大小 |
| `checkpointFailures` | 连续失败的 checkpoint 数，有 checkpoint 完成后归零 |

它们属于运行的指标（见[指标参考](../reference/metrics)）；元数据库的 `checkpoint` 表保存每个 checkpoint 的状态、大小、目录、错误以及每个 Task 的部分。
Master 会在日志中记录每个完成或失败的 checkpoint。

## 性能与调优

- 取状态时在 Task 的线程上复制一份；写入在 Task 继续处理时进行，因此 checkpoint 对吞吐的影响只有复制的那一下。
- 间隔越短，出错时丢失的进度越少，但写入越频繁；对批处理作业，间隔决定失败的运行最多重读多少数据。
- 背压会拖慢 barrier：checkpoint 超时时，先检查运行的背压，再考虑调大 `env.checkpoint.timeout`。

## 排障

| 错误 | 原因与解决 |
|---|---|
| [`PF-CKPT-0001`](../reference/errors#pf-ckpt-0001) | checkpoint 超时；消息中列出了没有完成的 Task |
| [`PF-CKPT-0005`](../reference/errors#pf-ckpt-0005) | Task 拒绝参与，原因见消息 |
| [`PF-CKPT-0006`](../reference/errors#pf-ckpt-0006) | Master 无法写入 checkpoint，或无法在元数据库中记录它 |
| [`PF-CKPT-0007`](../reference/errors#pf-ckpt-0007) | 连续失败的 checkpoint 超过作业允许的次数；运行以最后一次的原因失败 |
| [`PF-CONF-0011`](../reference/errors#pf-conf-0011) `master.metastore.url` | 设置了 `checkpoint.dir`，但没有配置 Master 的元数据库 |
| [`PF-CKPT-0002`](../reference/errors#pf-ckpt-0002) | 运行要从中开始的目录不是已完成的 checkpoint 或 savepoint，或者其中的文件已损坏 |
| [`PF-CKPT-0003`](../reference/errors#pf-ckpt-0003) | 运行不能从这个点开始：它由其他作业产生、有状态的节点已不存在，或者节点改变了并行度 |

## 限制

- Transform 没有状态。Sink 按 checkpoint 在 Master 上提交（见 [Sink 状态与提交](../development/api-overview#sink-状态与提交)）。
- savepoint 的触发、从 savepoint 开始运行以及暂停与继续目前只能通过 Master 的协议进行，命令行、REST 接口和 Web UI 随后提供。从某个点开始运行时，
  有状态的节点不能改变并行度。
- 等待 checkpoint 的 barrier 超过 30 秒的 Task 会在日志中给出背压警告；这个时限目前还不能修改。
- 只有对齐的 checkpoint：Task 要等所有输入都收到 barrier。
