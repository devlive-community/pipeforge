## 协议的范围

PipeForge 集群中有一个负责调度的进程（Master）和多个运行 Task 的进程（Worker）；Server 把作业提交给 Master。
它们之间使用**协议 v1** 通信，也就是 `pipeforge.rpc.v1` 包中的 gRPC 服务与 Protobuf 消息：

| 服务 | 方向 | 内容 |
|---|---|---|
| `ResourceManagerService` | Worker → Master | 注册、心跳、Worker 提供的 Slot |
| `TaskExecutorService` | Master → Worker | 申请 Slot、部署与取消 Task、分配分片、Task 日志 |
| `JobMasterService` | Task → Master | Task 状态变化、请求分片、Task 指标 |
| `DispatcherService` | Server → Master | 提交、取消作业，状态、指标、运行分析；运行的分片及其读取器（`ListSplits`），以及 Task 日志（`ReadTaskLog`），由 Master 从运行该 Task 的 Worker 转发，以及集群的状态（`GetCluster`：Master，以及每个 Worker 的 Slot、标签、资源和最近一次心跳），因此服务端只需要访问 Master |
| `BlobService` | Worker → Master | 按 SHA-256 提供插件包，分块流式传输，可从某个偏移量续传（冻结后的兼容增加） |

定义位于 `pipeforge-engine/engine-rpc/src/main/proto/pipeforge/rpc/v1/`。构建时由它们生成 Java 消息与服务桩
（包 `org.devlive.pipeforge.engine.rpc.proto`）；引擎内部使用自己的类型，`ProtoMapping` 在边界上负责两者之间的转换。

[集群](../concepts/cluster)进程（Master、Worker）通过 gRPC 使用它；本地运行（`pipeforge run --local`）在进程内使用同一组接口。

### Checkpoint 消息

Checkpoint 在三个服务中增加了 RPC，都是对 v1 的兼容增加：

| RPC | 服务 | 作用 |
|---|---|---|
| `TriggerCheckpoint` | `TaskExecutorService` | 在 Source Task 上开始 checkpoint *n*；其他 Task 在 barrier 到达时开始；`stop` 表示快照后结束输入（stop-with-savepoint） |
| `NotifyCheckpointComplete`、`AbortCheckpoint` | `TaskExecutorService` | 通知 Task checkpoint *n* 已经完成（Sink 随之提交），或者已经放弃 |
| `AcknowledgeCheckpoint`、`DeclineCheckpoint` | `JobMasterService` | Task 在 checkpoint *n* 中的部分：每个有状态的节点一个 `StateHandle`（内联字节或 checkpoint 中的文件）及耗时，或者让它无法参与的错误 |
| `TriggerSavepoint`、`StopWithSavepoint`、`ListCheckpoints` | `DispatcherService` | 为运行做 savepoint（可以同时停止运行），以及列出 Master 保留的 checkpoint；`TriggerSavepoint` 在 savepoint 完成后返回它的编号和目录，`StopWithSavepoint` 在运行进入 `PAUSED` 后返回 |

`TaskDeployment` 携带 Task 要恢复的状态（`restore_state`、`restore_checkpoint_id`；编号 9 和 10 从一开始就为它们保留），
`SubmitJobRequest` 携带运行从哪里开始（`restore`）以及第几次尝试，`JobStatus` 携带尝试次数和最近完成的 checkpoint，
`RunState` 增加了重启与暂停的状态：`RESTARTING` 8、`PAUSING` 9、`PAUSED` 10、`RETRY_WAIT` 11。Master 遇到不认识的状态时会拒绝，而不是猜测。
`JobMetrics` 的字段 27 到 30 携带 [checkpoint 指标](../concepts/checkpoint#可观测性)。

在 [Region](../concepts/failure-handling#region-重启) 中重启的 Task 以新的尝试部署，并设置 `restore_state` 和 `restore_checkpoint_id`；
全新启动的 Task 两者分别为空和 0。从 savepoint 或 checkpoint 开始的运行（`SubmitJobRequest.restore`）的 Task 也一样，它们的状态在另一个目录中：
由 `restore_directory`（字段 15，兼容增加）给出，相对 checkpoint 存储的根目录。Worker 直接使用 inline 状态，从该目录（没有时为本运行的
`<run>/chk-<n>/`）读取文件状态，并按句柄中的大小和 CRC32C 校验。不符的状态让 Task 以 `PF-CKPT-0002` 失败，无法读取的文件为 `PF-CKPT-0004`；在当前版本中两者都会让运行失败。

Master 按规范第 2.6 节的顺序处理确认：先写 `_metadata`，再在元数据库中把 checkpoint 记为已完成，然后才发送 `NotifyCheckpointComplete`。
已经带有 `PF-CKPT-0005` 的拒绝会保留原来的原因。

## 约定

- 每个请求都以 `Header` 开头：协议版本、Master 与作业的 epoch（新的 Master 或 JobMaster 的 epoch 一定更大，
  更旧的请求会被拒绝）、使重试幂等的请求 ID，以及截止时间。
- 由插件序列化的值（例如分片、Sink 准备提交的内容）以 `Versioned{version, data}` 传输，接收方用写入时的版本调用插件的序列化器。
- 失败的 Task 上报 `ErrorInfo`：[错误码](../concepts/errors)、参数、出错位置（节点、子任务、表…）、类别和原因链。
  Master 据此重建同样的错误对象，因此 CLI、REST API 和 Web UI 显示的与 Worker 上看到的一致。
- 枚举值带有枚举名前缀（`TASK_STATE_RUNNING`、`RUN_STATE_RUNNING`），因为 Protobuf 中同一个包的枚举值共用一个命名空间。
- 插件标为敏感的选项（例如密码）从不出现在 Task 描述中，而是为运行该 Task 的 Worker 单独加密下发。

## Task 描述

Task 随**描述**一起下发：它运行的节点链、每个节点的选项、节点之间的表，以及本次运行的上下文（作业、运行、时区、变量、开始时间）。
描述是 `ChainDescriptor` 消息加上一层外壳，Worker 在读取任何内容之前先检查外壳：

```text
+---------+----------------+--------+---------------------------+---------+
| "PFCH"  | 格式版本        | 长度   | Protobuf ChainDescriptor  | CRC32C  |
| 4 字节  | 4 字节          | 4 字节 | 长度个字节                 | 4 字节  |
+---------+----------------+--------+---------------------------+---------+
```

- Worker 能读取不高于自身的所有格式版本；对于更新的版本、损坏或被截断的描述，在构建任何东西之前就给出明确的错误。
- 节点通过插件和标识引用组件（`fake`、`connector-mysql@1.2.0`），由 Worker 用自己的插件解析。部署中的 `plugins` 每个插件只列一次，并带有插件包的 SHA-256，其后是它所需的驱动插件。
- 一条链以 Source 开头，或者从其他 Task 读取第一个节点的输入；以 Sink 结尾，或者写入输出：每条下游链一条输出边，带分区方式，
  下游每个 Task 一个子分区。部署中列出 Task 的输入：每个上游 Task 的实例、输出、要读取的子分区，以及它所在 Worker 的数据地址
  （在同一个 Worker 上时为空）。
- 每张表在表目录中只出现一次，列类型使用 DSL 写法（`DECIMAL(10, 2) NOT NULL`）；节点以及以后的行数据都通过编号引用表。
- 选项以 JSON 表示。插件标为敏感的选项不会进入描述：它们的值单独下发并为该 Worker 加密，描述中在原位置写入
  `{"$secret": "<节点>.<选项>"}`。
- 同一个描述总是得到相同的字节。每个已发布格式版本的样本保存在 `pipeforge-engine/protocol-compat/chain/` 中，
  每次构建都检查它仍能被读取，并且仍能逐字节地写出。

本地运行会在每个 Task 启动前写出它的描述再读回，因此整个测试集都经过这个格式。

## 行格式

行以紧凑的二进制格式在 Task 之间传输（`pipeforge-engine/engine-network` 中的 `RowCodec`）。一个数据 Buffer 中依次存放多行，每行为：

```text
+----------+----------+--------+---------------+---------------+------------+
| 行长度    | 行头      | 表     | null 位图     | 槽            | 变长区      |
| varint   | 1 字节    | varint | 每列 1 位     | 每列 8 字节    | 其余内容    |
+----------+----------+--------+---------------+---------------+------------+
```

- **行长度**是其后的字节数。**行头**的第 0–1 位为 RowKind（`0` 插入、`1` 更新前、`2` 更新后、`3` 删除），第 2 位表示是否带事件时间；
  带事件时间时，变长区的前 8 字节为该时间（毫秒）。
- **表**是该行所属表在 Task 描述的表目录中的编号；行中不带列名和类型，读取时使用该表的列。
- 第 *i* 列为 NULL 时，**null 位图**的第 *i* 位（从低位开始）为 1。
- 每列有一个 8 字节的**槽**。整数、布尔值、浮点数（IEEE 754 位模式）、日期（自 1970-01-01 起的天数）、时间（当日纳秒数）、
  精度不超过 6 的时间戳（自 1970-01-01 起的微秒数，`TIMESTAMP` 按 UTC 换算）以及精度不超过 18 的小数（非标度 `long`）直接存放在槽中。
- 不超过 7 字节的字符串、JSON 和字节串**内联**存放：槽的第一个字节为 `0x80` 加长度，其后为内容。更长的值、精度超过 18 的小数、
  精度超过 6 的时间戳（微秒数加上微秒内的纳秒数）以及数组、Map 和嵌套行存放在变长区；它们的槽中为**偏移量**（高 32 位，从行头起算）
  和**长度**（低 32 位）。
- 嵌套行由 null 位图、槽和变长区组成；数组是元素个数（varint）加上相同的结构；Map 是键数组后跟值数组。它们的偏移量从嵌套值的起点算起。
- 所有整数均为大端。

与列不匹配的值会让该行失败：值的类型不对时为 [`PF-DATA-0001`](../reference/errors#pf-data-0001)，超出范围时（例如小数的位数超过精度）
为 [`PF-DATA-0002`](../reference/errors#pf-data-0002)，错误中给出列名，例如 `address.city` 或 `tags[]`。精度不超过 6 的时间戳保留到微秒，
更细的部分被舍去。不是已知表的行的字节会作为内部错误被拒绝。每个格式版本的样本保存在 `pipeforge-engine/protocol-compat/row/` 中，
每次构建都检查它仍能被读取，并且仍能逐字节地写出。

## 数据交换

行通过 TCP 在 Worker 之间传输（Netty，`pipeforge-engine/engine-network`），每对 Worker 之间一条连接，它们之间的所有通道共用。每一帧为：

```text
+---------+---------+---------+-----------+------------------+
| "PF"    | 版本     | 类型     | 长度       | 内容              |
| 2 字节  | 1 字节   | 1 字节   | 4 字节     | 长度个字节         |
+---------+---------+---------+-----------+------------------+
```

| 类型 | 帧 | 方向 | 内容 |
|---|---|---|---|
| `0x00` | `Hello` | 双向 | 协议版本、Worker ID、集群令牌 |
| `0x01` | `PartitionRequest` | 消费者 → 生产者 | 通道 ID、生产者的 Task 实例与输出、子分区、初始 credit |
| `0x02` | `BufferResponse` | 生产者 → 消费者 | 通道 ID、序号、积压数、缓冲类型（数据或事件）、标志、内容 |
| `0x03` | `AddCredit` | 消费者 → 生产者 | 通道 ID、新增 credit |
| `0x04` | `CancelPartition` | 消费者 → 生产者 | 通道 ID |
| `0x05` | `CloseRequest` | 双向 | — |
| `0x06` | `ErrorResponse` | 双向 | 通道 ID（为空表示整条连接）、错误码、信息 |
| `0x07` / `0x08` | `Ping` / `Pong` | 双向 | — |

- 双方先发送 `Hello`。集群令牌不同时以 [`PF-CLUS-0005`](../reference/errors#pf-clus-0005) 拒绝，主版本（每一帧的版本字节）不同时以
  [`PF-CLUS-0007`](../reference/errors#pf-clus-0007) 拒绝；拒绝的一方发送 `ErrorResponse` 后关闭连接。
- 长度、计数和编号为 varint，字符串为 varint 长度加 UTF-8，ID 为 16 字节。帧长度超过 `task.max-row-bytes` + 1 KB、magic 不对或内容无法解析时，
  以 `ErrorResponse` 关闭连接。
- 数据缓冲中是按上文行格式编码的行；事件缓冲中是事件类型（`0x01` 子分区结束、`0x02` 输入结束、`0x03` 表结构变化、`0x10` checkpoint barrier；
  `0x11`–`0x1F` 留给 watermark 和流状态）及其内容。
- Checkpoint barrier 共 18 字节：`u64` checkpoint 编号、`u64` 毫秒时间戳、`u8` 类型（1 checkpoint、2 savepoint）和 `u8` 标志位（第 0 位 `stop`，其余为 0）。
  长度、类型或标志位不符的 barrier 会让通道失败。事件不消耗 credit，因此即使消费者已停止向先收到 barrier 的通道发放 credit，barrier 仍能到达；
  但任何事件都不会越过在它之前发送的缓冲。
- 生产者只在通道有 credit 时发送数据缓冲，并为每个通道的缓冲从 0 开始编号；消费者拒绝序号不连续或没有 credit 的缓冲。
- 消费者请求的输出还不存在时，最多等待一个分区请求超时（30 秒），之后以 [`PF-CLUS-0011`](../reference/errors#pf-clus-0011) 拒绝。
- 没有发送 `CloseRequest` 就关闭的连接，会让消费者一端未结束的通道、以及生产者一端被它们读取的输出以
  [`PF-CLUS-0010`](../reference/errors#pf-clus-0010) 失败。

## Checkpoint 文件

一个 checkpoint 是一个目录，其中的文件使用独立的格式，以便更新的引擎也能恢复它。checkpoint 功能正在加入，这里是它们写入时使用的格式。
两种文件与 Task 描述使用相同的外层结构：magic、格式版本（1）、正文长度、正文和正文的 CRC32C，整数都是大端。

| 文件 | Magic | 正文 |
|---|---|---|
| `_metadata` | `PFCP` | Protobuf `CheckpointMetadata`（包 `pipeforge.checkpoint.v1`）：作业、运行、尝试和作业名，checkpoint 的编号和类型（checkpoint 或 savepoint）、时间、本次运行的变量，以及每个节点的插件、并行度和每个子任务的状态 |
| `<节点>-<子任务>.state`、`enum-<节点>.state` | `PFST` | checkpoint 编号（8 字节）和节点 ID，之后是插件状态序列化器的字节 |

- 不超过 `checkpoint.inline-threshold`（默认 16 KB）的状态直接保存在 `_metadata` 中；更大的状态单独成文件，由 `_metadata` 指出。
  没有状态的子任务不出现，每个节点都记录写入时的并行度。
- 状态文件记录它所属的 checkpoint 和节点；放错位置的文件不会被当作别的文件读取。
- 列表状态（例如 Reader 的分片）先是 varint 个数，然后每个元素为 varint 长度加元素序列化器的输出；`serializer_version` 是元素序列化器的版本。内联状态的结构相同。
- Sink 有两项状态：Writer 状态（`operator_kind = sink`）和待提交物（`operator_kind = committer`，0 或 1 个元素的列表，较大时单独成文件
  `commit-<node>-<subtask>.state`）；Master 在把 checkpoint 记为已完成后提交其中的待提交物。
- Task 把文件写在 checkpoint 编号对应的 `chk-<n>/` 下；对于 savepoint，Master 把它们复制到 `savepoints/<name>-<time>/`，再删除原处的文件。
- 长度或校验不符、或者属于别处的文件报告 [`PF-CKPT-0002`](../reference/errors#pf-ckpt-0002)：恢复时退回到上一个 checkpoint。
  格式版本比引擎能读取的更新时报告 [`PF-CKPT-0003`](../reference/errors#pf-ckpt-0003)。
- 支持原子改名的存储先写 `_metadata.tmp` 再改名；对象存储先写 `_metadata`，再写一个空的 `_COMPLETED`。只有带完成标记的 checkpoint 才算完成。
- `CheckpointMetadata` 与 RPC 消息一样只增不改，由同一个快照测试检查。每个已发布格式版本的样本保存在
  `pipeforge-engine/protocol-compat/checkpoint/` 中，必须一直可以读取。

## 传输

进程之间通过基于 HTTP/2（Netty）的 gRPC 互相调用。每次调用都受到保护，并且可以安全地重复：

| 关注点 | 做法 |
|---|---|
| 谁可以调用 | 每次调用都在元数据 `pipeforge-cluster-token` 中携带集群令牌；服务端拒绝其他调用，错误码为 [`PF-CLUS-0005`](../reference/errors#pf-clus-0005)。 |
| 加密 | 可选 TLS。服务端出示 PKCS#12 密钥库中的证书；客户端只信任 PKCS#12 信任库中的证书，拒绝其他服务端。 |
| 被替换的 Master | Worker 记住见过的最大 leader epoch 和 job epoch，拒绝更小 epoch 的请求（[`PF-CLUS-0006`](../reference/errors#pf-clus-0006)），因此只有当前的 Master 能控制它的 Task。释放 Slot 不属于某一次运行，只校验 leader epoch。 |
| 版本 | 协议主版本不同的请求被拒绝，错误码为 [`PF-CLUS-0007`](../reference/errors#pf-clus-0007)。 |
| 丢失的应答 | 没有得到应答（不可用或超过截止时间）的请求最多再发送三次，指数退避，请求 ID 不变。接收方对每个请求 ID 只执行一次，十分钟内对重复的请求返回第一次的结果。被拒绝的请求从不重试；最后一次重试仍失败时，调用方以 [`PF-CLUS-0008`](../reference/errors#pf-clus-0008) 失败。 |
| 拒绝 | 被拒绝的调用以说明原因的 gRPC 状态结束——`UNAUTHENTICATED`（令牌）、`FAILED_PRECONDITION`（已被替换的 Master）、`UNIMPLEMENTED`（主版本）、`NOT_FOUND`（未知的运行或 Task 日志）、`RESOURCE_EXHAUSTED`（Slot 不足）——并在 trailer 中携带错误，调用方据此显示相同的错误码和信息。 |
| 顺序 | 分片分配与分片请求按 Task 和节点编号；即使乱序到达，接收方也按编号顺序、只交付一次。 |
| 分片进度 | Reader 以 `SplitsFinished` 读取器事件上报读到末尾的分片，与分片请求一样编号。JobMaster 只计入分给该 Reader 的分片，不把这个事件交给 Enumerator。 |
| 敏感选项 | 为运行该 Task 的 Worker 加密：使用 Worker 注册时提供的公钥做一次临时 X25519 密钥协商，再经 HKDF-SHA256 和 AES-256-GCM 加密，并绑定到这次 Task 尝试。重启过的 Worker 无法读取为旧密钥加密的选项（[`PF-CLUS-0009`](../reference/errors#pf-clus-0009)）。 |
| 指标 | 每个 Worker 与 JobMaster 之间一条流；每次上报都包含完整的计数，丢失一次上报不影响结果。上报中还带有 Task 当前记账的内存（`memory_bytes`）和它最先跳过的坏行（`dirty_samples`），`GetJobMetrics` 按作业汇总内存和坏行，并保留作业最先的 20 条样本。`TaskSettings.skip_dirty_rows` 告诉 Task 脏数据策略，默认值 `false` 即 `fail`。 |
| 限流 | JobMaster 以 `RateLimitQuota` 算子事件把作业限额中的份额发给每个 Reader，与分片分配按序到达：在第一个分片之前以及份额变化时发送；0 表示不限。上报中带有 Task 等待配额的时间（`throttle_wait_nanos`）。 |
| Task 日志 | `ReadLog` 以完整行为单位分块流式返回 Task 日志。它不改变任何状态，因此只校验协议版本，也不重试。`LogChunk.offset` 是下一次读取继续的位置——有过滤条件时，它是分块覆盖的日志范围的末尾，而不是分块文本的末尾——`eof` 表示已结束 Task 的日志读到了末尾。跟随没有截止时间，读取方取消调用即可结束。见[日志](../operations/logs)。 |

部署 Task 的截止时间为 60 秒，其他请求为 30 秒。Source 发给分片分配器的自定义 Reader 事件在当前版本中只能在同一进程内传递；跨进程传递需要 Source 提供序列化器。

## 版本

协议版本的格式为 `主.次`，当前版本为 `1.0`。

- 两个进程建立连接时比较版本：主版本不同则不通信；主版本相同时双方使用较低的次版本。
- **次版本**只做增加：新字段、新 RPC、新枚举值、新事件类型。旧进程会忽略不认识的字段，因此集群可以逐个进程升级。
- **主版本**是一个新的包（`pipeforge.rpc.v2`），只有无法用“增加”表达的改动才需要它。

## 兼容性检查

`ProtoSnapshotTest` 把协议中的每个文件、消息、字段、枚举值、保留区间和 RPC 各列为一行，并与
`pipeforge-engine/protocol-compat/rpc/descriptor-v1.txt` 比较。快照中的每一行都必须仍然存在，因此会破坏运行中集群的改动会让构建失败：

| 改动 | 结果 |
|---|---|
| 新字段、新消息、新 RPC、新枚举值 | 接受；用 `-Dpipeforge.protocol.update=true` 扩充快照 |
| 字段改名、改编号或改类型 | 构建失败 |
| 一元 RPC 改为流式，或者请求、响应类型改变 | 构建失败 |
| 删除字段 | 构建失败，除非它的编号和名称都已 `reserved` |
| 把保留的编号用作字段 | 构建失败，除非这个编号从一开始就是为这个字段保留的（测试中的 `PLACEHOLDERS`） |

```text
ProtoSnapshotTest.theProtocolOnlyGrows
protocol v1 elements removed or changed; add new fields, RPCs or enum values instead, or reserve
the number and name of a removed field
Expecting empty but was: ["field pipeforge.rpc.v1.Header 3 job_epoch int64"]
```

## 修改协议

1. 先在协议规范中写明改动；协议的修改需要两位维护者评审。
2. 在 `.proto` 文件中增加字段或 RPC；不要复用字段编号，删除字段时保留它的编号与名称。
3. 先带 `-Dpipeforge.protocol.update=true` 运行 `engine-rpc` 的测试，再不带它运行一次：快照恰好增加你新增的那些行，评审时可以在 diff 中看到。
4. 扩充 `ProtoMapping` 及其测试，确保新的值经过字节往返后保持不变。

```bash
./mvnw -pl pipeforge-engine/engine-rpc test -Dpipeforge.protocol.update=true
./mvnw -pl pipeforge-engine/engine-rpc verify
```
