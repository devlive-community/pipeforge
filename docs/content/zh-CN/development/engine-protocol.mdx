## 协议的范围

PipeForge 集群中有一个负责调度的进程（Master）和多个运行 Task 的进程（Worker）；Server 把作业提交给 Master。
它们之间使用**协议 v1** 通信，也就是 `pipeforge.rpc.v1` 包中的 gRPC 服务与 Protobuf 消息：

| 服务 | 方向 | 内容 |
|---|---|---|
| `ResourceManagerService` | Worker → Master | 注册、心跳、Worker 提供的 Slot |
| `TaskExecutorService` | Master → Worker | 申请 Slot、部署与取消 Task、分配分片、Task 日志 |
| `JobMasterService` | Task → Master | Task 状态变化、请求分片、Task 指标 |
| `DispatcherService` | Server → Master | 提交、取消作业，状态、指标、运行分析 |

定义位于 `pipeforge-engine/engine-rpc/src/main/proto/pipeforge/rpc/v1/`。构建时由它们生成 Java 消息与服务桩
（包 `org.devlive.pipeforge.engine.rpc.proto`）；引擎内部使用自己的类型，`ProtoMapping` 在边界上负责两者之间的转换。

当前版本中协议、它的 gRPC 传输以及 Task 描述都已就绪；集群进程（Master、Worker）以及 Worker 之间的数据交换会在分布式运行时的后续步骤中加入。
本地运行（`pipeforge run --local`）在进程内使用同一组接口。

## 约定

- 每个请求都以 `Header` 开头：协议版本、Master 与作业的 epoch（新的 Master 或 JobMaster 的 epoch 一定更大，
  更旧的请求会被拒绝）、使重试幂等的请求 ID，以及截止时间。
- 由插件序列化的值（例如分片、Sink 准备提交的内容）以 `Versioned{version, data}` 传输，接收方用写入时的版本调用插件的序列化器。
- 失败的 Task 上报 `ErrorInfo`：[错误码](../concepts/errors)、参数、出错位置（节点、子任务、表…）、类别和原因链。
  Master 据此重建同样的错误对象，因此 CLI、REST API 和 Web UI 显示的与 Worker 上看到的一致。
- 枚举值带有枚举名前缀（`TASK_STATE_RUNNING`、`RUN_STATE_RUNNING`），因为 Protobuf 中同一个包的枚举值共用一个命名空间。
- 插件标为敏感的选项（例如密码）从不出现在 Task 描述中，而是为运行该 Task 的 Worker 单独加密下发。

## Task 描述

Task 随**描述**一起下发：它运行的节点链、每个节点的选项、节点之间的表，以及本次运行的上下文（作业、运行、时区、变量、开始时间）。
描述是 `ChainDescriptor` 消息加上一层外壳，Worker 在读取任何内容之前先检查外壳：

```text
+---------+----------------+--------+---------------------------+---------+
| "PFCH"  | 格式版本        | 长度   | Protobuf ChainDescriptor  | CRC32C  |
| 4 字节  | 4 字节          | 4 字节 | 长度个字节                 | 4 字节  |
+---------+----------------+--------+---------------------------+---------+
```

- Worker 能读取不高于自身的所有格式版本；对于更新的版本、损坏或被截断的描述，在构建任何东西之前就给出明确的错误。
- 节点通过插件和标识引用组件（`fake`、`connector-mysql@1.2.0`），由 Worker 用自己的插件解析。
- 每张表在表目录中只出现一次，列类型使用 DSL 写法（`DECIMAL(10, 2) NOT NULL`）；节点以及以后的行数据都通过编号引用表。
- 选项以 JSON 表示。插件标为敏感的选项不会进入描述：它们的值单独下发并为该 Worker 加密，描述中在原位置写入
  `{"$secret": "<节点>.<选项>"}`。
- 同一个描述总是得到相同的字节。每个已发布格式版本的样本保存在 `pipeforge-engine/protocol-compat/chain/` 中，
  每次构建都检查它仍能被读取，并且仍能逐字节地写出。

本地运行会在每个 Task 启动前写出它的描述再读回，因此整个测试集都经过这个格式。

## 传输

进程之间通过基于 HTTP/2（Netty）的 gRPC 互相调用。每次调用都受到保护，并且可以安全地重复：

| 关注点 | 做法 |
|---|---|
| 谁可以调用 | 每次调用都在元数据 `pipeforge-cluster-token` 中携带集群令牌；服务端拒绝其他调用，错误码为 [`PF-CLUS-0005`](../reference/errors#pf-clus-0005)。 |
| 加密 | 可选 TLS。服务端出示 PKCS#12 密钥库中的证书；客户端只信任 PKCS#12 信任库中的证书，拒绝其他服务端。 |
| 被替换的 Master | Worker 记住见过的最大 leader epoch 和 job epoch，拒绝更小 epoch 的请求（[`PF-CLUS-0006`](../reference/errors#pf-clus-0006)），因此只有当前的 Master 能控制它的 Task。 |
| 版本 | 协议主版本不同的请求被拒绝，错误码为 [`PF-CLUS-0007`](../reference/errors#pf-clus-0007)。 |
| 丢失的应答 | 没有得到应答（不可用或超过截止时间）的请求最多再发送三次，指数退避，请求 ID 不变。接收方对每个请求 ID 只执行一次，十分钟内对重复的请求返回第一次的结果。被拒绝的请求从不重试；最后一次重试仍失败时，调用方以 [`PF-CLUS-0008`](../reference/errors#pf-clus-0008) 失败。 |
| 顺序 | 分片分配与分片请求按 Task 和节点编号；即使乱序到达，接收方也按编号顺序、只交付一次。 |
| 敏感选项 | 为运行该 Task 的 Worker 加密：使用 Worker 注册时提供的公钥做一次临时 X25519 密钥协商，再经 HKDF-SHA256 和 AES-256-GCM 加密，并绑定到这次 Task 尝试。重启过的 Worker 无法读取为旧密钥加密的选项（[`PF-CLUS-0009`](../reference/errors#pf-clus-0009)）。 |
| 指标 | 每个 Worker 与 JobMaster 之间一条流；每次上报都包含完整的计数，丢失一次上报不影响结果。 |

部署 Task 的截止时间为 60 秒，其他请求为 30 秒。Source 发给分片分配器的自定义 Reader 事件在当前版本中只能在同一进程内传递；跨进程传递需要 Source 提供序列化器。

## 版本

协议版本的格式为 `主.次`，当前版本为 `1.0`。

- 两个进程建立连接时比较版本：主版本不同则不通信；主版本相同时双方使用较低的次版本。
- **次版本**只做增加：新字段、新 RPC、新枚举值、新事件类型。旧进程会忽略不认识的字段，因此集群可以逐个进程升级。
- **主版本**是一个新的包（`pipeforge.rpc.v2`），只有无法用“增加”表达的改动才需要它。

## 兼容性检查

`ProtoSnapshotTest` 把协议中的每个文件、消息、字段、枚举值、保留区间和 RPC 各列为一行，并与
`pipeforge-engine/protocol-compat/rpc/descriptor-v1.txt` 比较。快照中的每一行都必须仍然存在，因此会破坏运行中集群的改动会让构建失败：

| 改动 | 结果 |
|---|---|
| 新字段、新消息、新 RPC、新枚举值 | 接受；用 `-Dpipeforge.protocol.update=true` 扩充快照 |
| 字段改名、改编号或改类型 | 构建失败 |
| 一元 RPC 改为流式，或者请求、响应类型改变 | 构建失败 |
| 删除字段 | 构建失败，除非它的编号和名称都已 `reserved` |

```text
ProtoSnapshotTest.theProtocolOnlyGrows
protocol v1 elements removed or changed; add new fields, RPCs or enum values instead, or reserve
the number and name of a removed field
Expecting empty but was: ["field pipeforge.rpc.v1.Header 3 job_epoch int64"]
```

## 修改协议

1. 先在协议规范中写明改动；协议的修改需要两位维护者评审。
2. 在 `.proto` 文件中增加字段或 RPC；不要复用字段编号，删除字段时保留它的编号与名称。
3. 先带 `-Dpipeforge.protocol.update=true` 运行 `engine-rpc` 的测试，再不带它运行一次：快照恰好增加你新增的那些行，评审时可以在 diff 中看到。
4. 扩充 `ProtoMapping` 及其测试，确保新的值经过字节往返后保持不变。

```bash
./mvnw -pl pipeforge-engine/engine-rpc test -Dpipeforge.protocol.update=true
./mvnw -pl pipeforge-engine/engine-rpc verify
```
