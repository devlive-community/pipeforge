The server provides the REST API and hosts the Web UI. In this version it is **stateless**: it
validates and explains jobs, describes the installed plugins, lists functions and error codes and
evaluates expressions. Saving jobs, running them and keeping their history arrive with the
metadata database in a later version; the endpoints that exist now keep their paths and fields.

## Starting the server

Build it and start the executable jar:

```bash
./mvnw -B -pl pipeforge-server -am package -DskipTests
java -jar pipeforge-server/target/pipeforge-server-0.1.0-SNAPSHOT-exec.jar
```

It listens on `http://127.0.0.1:8080`. Check that it answers:

```bash
curl -s http://127.0.0.1:8080/api/v1/version
```

## Running from a source checkout

A server started from an IDE or with `./mvnw spring-boot:run` has no `plugins` directory to load
from. Start it with the `dev` profile instead: it then also loads the plugin modules of the checkout
it runs in, straight from their build output, so no plugin has to be packaged.

1. Compile once from the repository root, so that every plugin module gets its dependency list
   (`target/pipeforge-plugin/classpath.txt`):

   ```bash
   ./mvnw compile
   ```

2. Start the server with the profile. In IntelliJ IDEA, set **Active profiles** of the run
   configuration to `dev`; on the command line:

   ```bash
   java -jar pipeforge-server/target/pipeforge-server-0.1.0-SNAPSHOT-exec.jar --spring.profiles.active=dev
   ```

The server finds the checkout from its working directory, whether that is the repository root or
`pipeforge-server`, and loads every module two levels below the root that has
`src/main/plugin/plugin.yaml`, so new plugins are picked up without configuration. The log shows
what it found:

```text
Development mode: loading the plugin modules of /work/pipeforge
Development plugin fake@0.1.0-SNAPSHOT from /work/pipeforge/pipeforge-connectors/connector-fake
Plugin directory /work/pipeforge/pipeforge-server/plugins does not exist
Found 1 plugin(s) in /work/pipeforge
```

After changing a plugin, build it in the IDE and restart the server; run `./mvnw compile` again only
when its dependencies change. A module that is not built yet is listed under `unavailable` by
`GET /api/v1/plugins` with the command that builds it. A plugin of the checkout replaces an installed
package with the same id and version.

## Web UI

The server hosts the [Web UI](../guides/web-ui) at `/` when the UI was built before the server was
packaged (`pnpm --filter @pipeforge/ui build`); the build output in `pipeforge-ui/dist` is then
part of the jar. Addresses outside `/api` that are not files open the UI, so its pages can be
bookmarked; unknown `/api` addresses always answer with an error object. `index.html` is sent with
`Cache-Control: no-cache` and the files under `/assets/`, whose names contain a content hash, are
cached for a year, so browsers pick up a new version of the UI on the next load.

## Configuration

Settings are Spring Boot properties: put them in an `application.yaml` next to the jar, pass them
as `--name=value`, or set them as environment variables (`PIPEFORGE_JOB_TIMEZONE`).

| Setting | Default | Meaning |
|---|---|---|
| `server.address` | `127.0.0.1` | Interface to listen on |
| `server.port` | `8080` | Port |
| `pipeforge.plugin.paths` | `plugins` | Directories with plugin packages (zip files or extracted directories) |
| `pipeforge.plugin.cache` | `work/plugin-cache` | Where zipped plugins are extracted |
| `pipeforge.plugin.dev.enabled` | `false` | Also loads the plugin modules of the source checkout; the `dev` profile turns it on |
| `pipeforge.plugin.dev.root` | found from the working directory | Root of the source checkout for development mode |
| `pipeforge.job.timezone` | `UTC` | Time zone of jobs that do not set `env.timezone` |
| `pipeforge.job.defaults.*` | none | Cluster defaults for node options, in the env form, e.g. `pipeforge.job.defaults.source.fetch-size` |

```yaml
pipeforge:
  plugin:
    paths: [/opt/pipeforge/plugins]
  job:
    timezone: Asia/Shanghai
    defaults:
      source.fetch-size: "5000"
```

Plugins are loaded when the server starts, and the log names every plugin directory with its
absolute path and the number of plugins in it; packages that cannot be used are listed by
`GET /api/v1/plugins` under `unavailable`, with the reason.

## Security

The server has no authentication yet, so it only listens on the loopback interface. Do not set
`server.address` to a public interface; put a reverse proxy with authentication in front of it if
others must reach it. Variables such as `${env:NAME}` read the environment of the server process.

## Logs and errors

The server logs to the console. Requests that fail because of the client get an error object with
a code (see the [REST API](../reference/api#conventions)); only internal errors (`PF-SYS-0001`)
are logged with their stack trace.
