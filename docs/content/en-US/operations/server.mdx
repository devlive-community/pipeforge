The server provides the REST API and hosts the Web UI. In this version it is **stateless**: it
validates and explains jobs, describes the installed plugins, lists functions and error codes and
evaluates expressions. Saving jobs, running them and keeping their history arrive with the
metadata database in a later version; the endpoints that exist now keep their paths and fields.

## Starting the server

Build it and start the executable jar:

```bash
./mvnw -B -pl pipeforge-server -am package -DskipTests
java -jar pipeforge-server/target/pipeforge-server-0.1.0-SNAPSHOT-exec.jar
```

It listens on `http://127.0.0.1:8080`. Check that it answers:

```bash
curl -s http://127.0.0.1:8080/api/v1/version
```

## Running from a source checkout

A server started from an IDE or with `./mvnw spring-boot:run` has no `plugins` directory to load
from. Start it with the `dev` profile instead: it then also loads the plugin modules of the checkout
it runs in, straight from their build output, so no plugin has to be packaged.

1. Compile once from the repository root, so that every plugin module gets its dependency list
   (`target/pipeforge-plugin/classpath.txt`):

   ```bash
   ./mvnw compile
   ```

2. Start the server with the profile. In IntelliJ IDEA, set **Active profiles** of the run
   configuration to `dev`; on the command line:

   ```bash
   java -jar pipeforge-server/target/pipeforge-server-0.1.0-SNAPSHOT-exec.jar --spring.profiles.active=dev
   ```

The server finds the checkout from its working directory, whether that is the repository root or
`pipeforge-server`, and loads every module two levels below the root that has
`src/main/plugin/plugin.yaml`, so new plugins are picked up without configuration. The log shows
what it found:

```text
Development mode: loading the plugin modules of /work/pipeforge
Development plugin fake@0.1.0-SNAPSHOT from /work/pipeforge/pipeforge-connectors/connector-fake
Plugin directory /work/pipeforge/pipeforge-server/plugins does not exist
Found 1 plugin(s) in /work/pipeforge
```

After changing a plugin, build it in the IDE and restart the server; run `./mvnw compile` again only
when its dependencies change. A module that is not built yet is listed under `unavailable` by
`GET /api/v1/plugins` with the command that builds it. A plugin of the checkout replaces an installed
package with the same id and version.

## Web UI

The server hosts the [Web UI](../guides/web-ui) at `/` when the UI was built before the server was
packaged (`pnpm --filter @pipeforge/ui build`); the build output in `pipeforge-ui/dist` is then
part of the jar. Addresses outside `/api` that are not files open the UI, so its pages can be
bookmarked; unknown `/api` addresses always answer with an error object. `index.html` is sent with
`Cache-Control: no-cache` and the files under `/assets/`, whose names contain a content hash, are
cached for a year, so browsers pick up a new version of the UI on the next load.

## Configuration

Settings are Spring Boot properties: put them in an `application.yaml` next to the jar, pass them
as `--name=value`, or set them as environment variables (`PIPEFORGE_JOB_TIMEZONE`).

| Setting | Default | Meaning |
|---|---|---|
| `server.address` | `127.0.0.1` | Interface to listen on |
| `server.port` | `8080` | Port |
| `pipeforge.plugin.paths` | `plugins` | Directories with plugin packages (zip files or extracted directories) |
| `pipeforge.plugin.cache` | `work/plugin-cache` | Where zipped plugins are extracted |
| `pipeforge.plugin.dev.enabled` | `false` | Also loads the plugin modules of the source checkout; the `dev` profile turns it on |
| `pipeforge.plugin.dev.root` | found from the working directory | Root of the source checkout for development mode |
| `pipeforge.job.timezone` | `UTC` | Time zone of jobs that do not set `env.timezone` |
| `pipeforge.job.defaults.*` | none | Cluster defaults for node options, in the env form, e.g. `pipeforge.job.defaults.source.fetch-size` |
| `pipeforge.metastore.*` | an H2 file in `~/.pipeforge/metastore` | The database of the server's records; see [metastore](./metastore) |
| `pipeforge.master.address` | none | `host:port` of the cluster master's RPC port, or a comma-separated list of the masters of a cluster with [standbys](./deployment#standby-masters), whose leader the server follows; without it runs cannot be submitted |
| `pipeforge.master.token` | none | The cluster token (`cluster.token` of the cluster), required with a master |
| `pipeforge.master.tls.*` | off | `enabled`, `key-store`, `key-store-password`, `trust-store`, `trust-store-password`, as `security.tls.*` of the cluster |
| `pipeforge.master.poll-interval` | `1s` | How often the server asks the master about the runs that have not ended |
| `pipeforge.master.metrics-interval` | `10s` | How often the server keeps a sample of a running run's metrics |

```yaml
pipeforge:
  plugin:
    paths: [/opt/pipeforge/plugins]
  job:
    timezone: Asia/Shanghai
    defaults:
      source.fetch-size: "5000"
```

Plugins are loaded when the server starts, and the log names every plugin directory with its
absolute path and the number of plugins in it; packages that cannot be used are listed by
`GET /api/v1/plugins` under `unavailable`, with the reason.

## Running jobs on a cluster

With `pipeforge.master.*` set, the server runs jobs on the cluster (see [deployment](./deployment)):

```yaml
pipeforge:
  master:
    address: master.example.com:6123
    token: ${PIPEFORGE_CLUSTER_TOKEN}
```

`POST /api/v1/runs` plans the job on the server first, so an invalid job is refused before it
becomes a run; then the server records the run in the [metastore](./metastore) and submits it to the
master with the plugin versions it planned with. Every `poll-interval` the server asks the master
about the runs that have not ended and records each change of state with its time and reason:

```text
QUEUE → RUNNING → SUCCESS | FAILED | TIMEOUT
          ├──── CANCELLING → CANCELLED
          └──── RETRY_WAIT → QUEUE (the next attempt)
```

A run whose job sets `env.retry` waits in `RETRY_WAIT` after a failure that may be retried and is
submitted again as its next attempt (see [retrying runs](../concepts/failure-handling#retrying-runs));
`GET /api/v1/runs/{id}` lists its attempts. `POST /api/v1/runs/{id}/retry` retries a run that
failed, timed out or was cancelled by hand, as its next attempt.

`GET /api/v1/runs` lists runs newest first, filtered by state and job and paged with the `next`
token, each with the rows read and written as of its last metrics sample; `GET /api/v1/runs/{id}` shows a run with its definition and its changes of state;
`POST /api/v1/runs/{id}/cancel` asks the master to cancel it. While the master cannot be reached,
runs keep their state. A run the master no longer knows, because another master took over or the
master restarted, goes on there in the same attempt: from its last completed checkpoint, or from the
start when the job is delivered exactly once and has none yet; its changes of state say where it was
recovered from. A run that has nothing to go on from fails with `PF-CLUS-0016`, which `env.retry`
may retry, and a run that was being cancelled ends `CANCELLED`.

While a run runs, `GET /api/v1/runs/{id}/metrics` shows its current metrics from the master, and
every `metrics-interval` the server keeps a sample for `GET /api/v1/runs/{id}/metrics/history`.
When the run ends the server keeps its final metrics and its run analysis
(`GET /api/v1/runs/{id}/analysis`), so both stay available after the master forgets the run.
`/splits` lists the splits with their readers and `/tasks` the tasks with their workers, as long as
the master has the run. `/logs` reads a task's log through the master from the worker the task ran
on; the server needs no access to the workers. To follow a log, read again from the `offset` of
the previous answer until `eof`.

`GET /api/v1/cluster` shows the cluster as the master sees it: the master's version and start time,
and every registered worker with its addresses, labels, resource group, cores and memory, its slots
with the job that holds each, its running tasks and the time since its last heartbeat, with the
slot usage of the whole cluster. Without a master, or when it cannot be reached, it answers 503.

### Checkpoints, savepoints and pausing

For runs whose jobs take [checkpoints](../concepts/checkpoint):

| Endpoint | What it does |
|---|---|
| `GET /api/v1/runs/{id}/checkpoints` | The checkpoints and savepoints of the run across its attempts, newest first: number, attempt, type, status, why it was taken (`PERIODIC`, `SAVEPOINT`, `PAUSE`, `FINISH`, ...), when it was taken and completed, size, directory and the error of a failed one; a completed one lists each task's part: how long its snapshot held it up, the upload and the barrier alignment took, and the size of its states |
| `POST /api/v1/runs/{id}/savepoint` | Takes a savepoint of a running run, named by `{"name": ...}` or a time stamp, and answers with it once it completed; the run goes on. Savepoints are kept until deleted by hand |
| `POST /api/v1/runs/{id}/pause` | Stops a running run with a savepoint (HTTP 202): it moves to `PAUSING` at once and to `PAUSED` once its sinks committed, holding no slots. When the savepoint fails the run reads on and moves back to `RUNNING` |
| `POST /api/v1/runs/{id}/resume` | Starts a paused run again from the savepoint it was paused at, in the same attempt; it moves to `QUEUE` |
| `GET /api/v1/runs/{id}/attempts` | The attempts of the run, oldest first: start, end, error, the checkpoint each started from, the rows it read, wrote and found dirty as its last metrics sample has them, and when the next one starts while the run waits in `RETRY_WAIT` |

A run that is not running answers a savepoint or a pause with HTTP 400, and only a paused run can be
resumed. The time a run spends paused does not count against `env.timeout.run`. A paused run stays
paused when the master changes over; resume it on the new leader. Pausing waits for the savepoint
up to 15 minutes.

## Previews and dry runs

`POST /api/v1/jobs/preview` shows what a job produces without running it on the cluster: the job
editor's data preview and dry run. The server cuts the job after the chosen `node`, or after the
input of its sink for a dry run, replaces the sinks with a buffer and runs that part in its own
process, at parallelism 1. It answers with the first `limit` rows (100 by default, 1,000 at most)
of every table there and how it ended:

| Outcome | Meaning |
|---|---|
| `COMPLETE` | The sources were read to the end |
| `LIMIT` | A table reached `limit` rows; the job was stopped there |
| `TIMEOUT` | `timeoutSeconds` (30 by default, 120 at most) was up; the rows read so far |
| `FAILED` | The job failed; `error` says why |

Nothing is written to any target: the job's sinks are not even planned. The sources are read from
the server's host, with the server's plugins, so the server needs access to them. At most two
previews run at once; more wait for one to end, and give up with `PF-CONF-0007` after their timeout.

## Security

The server has no authentication yet, so it only listens on the loopback interface. Do not set
`server.address` to a public interface; put a reverse proxy with authentication in front of it if
others must reach it. Variables such as `${env:NAME}` read the environment of the server process.

## Logs and errors

The server logs to the console. Requests that fail because of the client get an error object with
a code (see the [REST API](../reference/api#conventions)); only internal errors (`PF-SYS-0001`)
are logged with their stack trace.
