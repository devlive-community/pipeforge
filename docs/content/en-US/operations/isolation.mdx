Jobs share the workers of a cluster: the tasks of several jobs run in the same worker process, each
in a slot of its own. A job must not take down the others, so every task is held to limits that
fail or slow down that task only.

## Row size

Every row a source reads is measured by its estimated size in memory — object headers, references
and the content of its values, two bytes per character of text. A row larger than
`task.max-row-bytes` (64MB by default) fails its job with
[`PF-DATA-0007`](../reference/errors#pf-data-0007), naming the node, the table, the size and the
limit. Rows that a transform made larger are checked again before the write buffer holds them, and
rows sent to another task are checked by their encoded size.

The job fails as a whole for now; the other jobs on the worker keep running. A policy for bad rows,
which can skip such a row or keep it aside, comes in a later version.

## Task memory

Each task accounts the memory it holds:

| Holder | What is counted |
|---|---|
| Write buffer | Rows waiting for the sink's write thread, by their estimated size |
| Network buffers | The buffers of its outputs and inputs, from the worker's network memory |
| Split queue | Split assignments that wait until the task hands them to the reader |

Rows waiting in the write buffer are limited by `worker.memory.task`: when they reach it, the reader
waits until the write thread has written some, the same backpressure as a full write queue, and the
wait counts as `readerWaitMs`. A single row is always taken when nothing waits, so a row larger than
the limit still passes. Network buffers are limited by the
[data exchange](../concepts/execution) settings; a task waits for them instead of growing.

| Setting | Default | Meaning |
|---|---|---|
| `worker.memory.task` | half of the heap left after the network memory, split over the slots, at least 16MB | Rows a task may hold for its sink |
| `task.max-row-bytes` | `64MB` | The largest row |
| `worker.memory.network` | 10% of the heap, 64MB to 1GB | The network buffers of all tasks |

Local runs (`pipeforge run --local`) check the row size but do not limit task memory.

## Heap guard

Task memory limits what a task holds for its sink, but a job can still fill the heap of a worker
with rows it keeps elsewhere. Rather than let the worker run out of memory and take every job on it
down, the heap guard looks at the heap once a second and blames the run whose running tasks on this
worker account the most memory:

1. When the heap is `worker.heap-guard.pause-percent` full (85% by default), the source tasks of
   that run stop reading. Rows already read go on to the sinks, so the run lets go of memory, while
   the other runs keep reading. The run reads on as soon as the heap is below the line again; if
   another run comes to hold the most, that run is paused instead.
2. When the heap stays `worker.heap-guard.fail-percent` full (92%) for `worker.heap-guard.fail-after`
   (10 seconds), the tasks of that run on this worker fail with
   [`PF-RES-0002`](../reference/errors#pf-res-0002), naming the worker, the run and what it held.
   They stop the way cancelled tasks do and free their memory; the other runs go on. The failure is
   a resource error, so the [restart strategy](../concepts/failure-handling) of the job may restart
   it, from its last checkpoint when it has one.

The heap is read as used over maximum, garbage included: a heap that the collector keeps freeing
does not stay above the failure line for ten seconds, a heap full of live rows does. When the heap is
full but no running task accounts any memory, there is no run to blame: the worker logs a warning and
does nothing. Every pause, resume and failure is logged by the worker.

| Setting | Default | Meaning |
|---|---|---|
| `worker.heap-guard.enabled` | `true` | Whether the guard runs |
| `worker.heap-guard.pause-percent` | `85` | The heap use, in percent, at which the run holding the most stops reading |
| `worker.heap-guard.fail-percent` | `92` | The heap use at which that run fails once it lasted `fail-after` |
| `worker.heap-guard.fail-after` | `10s` | How long the heap must stay at `fail-percent` |

The pause percent must not be above the fail percent. Local runs have no heap guard.

## Plugin code

Every call into a plugin runs with the plugin's class loader as the context class loader. An error
it throws keeps its code when it has one, is otherwise mapped by the plugin's `ErrorClassifier`
(see [failure handling](../concepts/failure-handling)) when it has one, and otherwise becomes `PF-SRC-0001` for a source,
`PF-SINK-0001` for a sink or `PF-PLUG-0007` for a transform, naming the node and what it was doing;
a class the plugin needs but does not bring (`NoClassDefFoundError` and other linkage errors) is
reported the same way instead of stopping the worker.

**Threads.** Threads a plugin takes from `threadFactory()` of its reader or writer context are
named `plugin-<task>-<node>-<n>`, carry the plugin's class loader and the task's log, and are daemon
threads. An uncaught exception in one of them fails the task. When the task ends, the engine
interrupts the ones still alive; one that is still alive a second later is reported as leaked in
the worker's log, with where it hangs. Threads started any other way are not tracked.

**Cancelling.** A cancelled task is woken up and its reader and writer are asked to stop blocking
IO. A task that has not stopped after `task.cancel-timeout` has its thread interrupted. One that
ignores the interrupt too is given up after `task.cancel-kill-timeout`: it fails with
[`PF-RES-0005`](../reference/errors#pf-res-0005), its slot is freed, and its thread is reported as
left behind, with where it hangs. Other jobs on the worker keep running.

| Setting | File | Default | Meaning |
|---|---|---|---|
| `task.cancel-timeout` | `master.yaml` | `30s` | When the thread of a cancelled task is interrupted; the default of the jobs the master runs |
| `task.cancel-kill-timeout` | `worker.yaml` | `3min` | When a task that ignores cancel and interrupt is given up |

Local runs give a task up at twice its cancel timeout.

## Disk quota

Readers and writers that need local files take them from the work directory their context gives
them (`workDirectory()`, see the [API overview](../development/api-overview)). A run's work
directories are under `<worker.dir>/jobs/<run>/`, one per task and node; a task's directory is
deleted when the task ends, the run's when its last task on the worker ended, and what a stopped
worker left there is deleted when it starts again.

What a run holds on a worker's disk, its work directories and its task logs together, is limited by
`worker.disk.quota-per-job`. The worker checks every five seconds; a run over its quota has its
tasks on that worker fail with [`PF-RES-0004`](../reference/errors#pf-res-0004), naming the run, what
it holds and the quota. They stop the way cancelled tasks do and their work directories are
deleted; task logs are kept, so they stay readable. The other runs on the worker go on. Writes are
not refused as they happen, so a run may go over its quota by what it writes within five seconds.

| Setting | Default | Meaning |
|---|---|---|
| `worker.disk.quota-per-job` | `10GB` | What one run may hold on the disk of a worker |

Local runs give work directories in a temporary directory and set no quota.

## Leaked class loaders

Every run loads its plugins with class loaders of its own, which the worker closes when the last task
of the run on it ended. Something may still hold one: a thread the plugin left running, a JDBC driver
it registered, a shutdown hook, a thread local or a cache outside the plugin. Such a loader keeps every
class of its plugin in memory, and after enough of them the worker runs out of metaspace.

The worker follows the loaders of every run that ended, without holding them. One still reachable
`worker.class-loader-leak-timeout` (one minute by default) after its run ended is given a chance
first: the worker asks for a garbage collection and looks again a few seconds later. A loader still
reachable then is logged once as a warning, with its plugin, its run, the total of leaked loaders on
the worker and what holds it:

- the threads whose context class loader it is, whose class it defined, or that run code of the
  plugin (code of the same plugin loaded for another run counts too);
- when no thread holds it, the warning says so: a static cache or a JVM-wide registration of the
  plugin does.

```text
WARN  The class loader of plugin acme@1.2.0 for run 8f2c… was not collected 60 s after the run ended;
held by thread acme-refresher (its context class loader). The worker has 1 leaked class loader(s)
```

| Setting | Default | Meaning |
|---|---|---|
| `worker.class-loader-leak-timeout` | `1min` | How long after a run ended its plugin class loaders may take to be collected |

A worker started with `-XX:+DisableExplicitGC` ignores the collection the check asks for, so loaders
that no full collection has reached yet may be reported; raise the timeout there.

## Observability

Every task reports the memory it accounts with its metrics; the job's
[`memoryBytes`](../reference/metrics) is the sum over its running tasks. A task that ended holds
nothing: its write buffer is empty or dropped, its network buffers belong to the data exchange
until other tasks read them, and splits it never took are dropped. A task that ends with memory
still accounted is logged by the worker as a leak, with what holds it.

## Limitations

- The heap guard only knows the memory that tasks account; it blames the wrong run when another
  one fills the heap with memory that is not accounted. Its actions appear in the worker's log, not
  yet as metrics. A worker that runs out of memory anyway still stops; the deployment restarts it.
- Leaked class loaders are logged but not yet counted as a metric, and a worker with many of them
  does not restart by itself yet.
- A worker whose disk is nearly full still takes new tasks; refusing them, and a metric of the disk a
  job uses (`jobDiskUsedBytes`), come in a later version.
- A task that was given up keeps its thread until the worker restarts; restarting a worker with
  stuck threads by itself comes in a later version.
- The memory of the source and sink plugins themselves, such as their client libraries, is not
  accounted.
