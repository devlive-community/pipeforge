Jobs share the workers of a cluster: the tasks of several jobs run in the same worker process, each
in a slot of its own. A job must not take down the others, so every task is held to limits that
fail or slow down that task only.

## Row size

Every row a source reads is measured by its estimated size in memory — object headers, references
and the content of its values, two bytes per character of text. A row larger than
`task.max-row-bytes` (64MB by default) fails its job with
[`PF-DATA-0007`](../reference/errors#pf-data-0007), naming the node, the table, the size and the
limit. Rows that a transform made larger are checked again before the write buffer holds them, and
rows sent to another task are checked by their encoded size.

The job fails as a whole for now; the other jobs on the worker keep running. A policy for bad rows,
which can skip such a row or keep it aside, comes in a later version.

## Task memory

Each task accounts the memory it holds:

| Holder | What is counted |
|---|---|
| Write buffer | Rows waiting for the sink's write thread, by their estimated size |
| Network buffers | The buffers of its outputs and inputs, from the worker's network memory |
| Split queue | Split assignments that wait until the task hands them to the reader |

Rows waiting in the write buffer are limited by `worker.memory.task`: when they reach it, the reader
waits until the write thread has written some, the same backpressure as a full write queue, and the
wait counts as `readerWaitMs`. A single row is always taken when nothing waits, so a row larger than
the limit still passes. Network buffers are limited by the
[data exchange](../concepts/execution) settings; a task waits for them instead of growing.

| Setting | Default | Meaning |
|---|---|---|
| `worker.memory.task` | half of the heap left after the network memory, split over the slots, at least 16MB | Rows a task may hold for its sink |
| `task.max-row-bytes` | `64MB` | The largest row |
| `worker.memory.network` | 10% of the heap, 64MB to 1GB | The network buffers of all tasks |

Local runs (`pipeforge run --local`) check the row size but do not limit task memory.

## Plugin code

Every call into a plugin runs with the plugin's class loader as the context class loader. An error
it throws keeps its code when it has one, and otherwise becomes `PF-SRC-0001` for a source,
`PF-SINK-0001` for a sink or `PF-PLUG-0007` for a transform, naming the node and what it was doing;
a class the plugin needs but does not bring (`NoClassDefFoundError` and other linkage errors) is
reported the same way instead of stopping the worker.

**Threads.** Threads a plugin takes from `threadFactory()` of its reader or writer context are
named `plugin-<task>-<node>-<n>`, carry the plugin's class loader and the task's log, and are daemon
threads. An uncaught exception in one of them fails the task. When the task ends, the engine
interrupts the ones still alive; one that is still alive a second later is reported as leaked in
the worker's log, with where it hangs. Threads started any other way are not tracked.

**Cancelling.** A cancelled task is woken up and its reader and writer are asked to stop blocking
IO. A task that has not stopped after `task.cancel-timeout` has its thread interrupted. One that
ignores the interrupt too is given up after `task.cancel-kill-timeout`: it fails with
[`PF-RES-0005`](../reference/errors#pf-res-0005), its slot is freed, and its thread is reported as
left behind, with where it hangs. Other jobs on the worker keep running.

| Setting | File | Default | Meaning |
|---|---|---|---|
| `task.cancel-timeout` | `master.yaml` | `30s` | When the thread of a cancelled task is interrupted; the default of the jobs the master runs |
| `task.cancel-kill-timeout` | `worker.yaml` | `3min` | When a task that ignores cancel and interrupt is given up |

Local runs give a task up at twice its cancel timeout.

## Observability

Every task reports the memory it accounts with its metrics; the job's
[`memoryBytes`](../reference/metrics) is the sum over its running tasks. A task that ended holds
nothing: its write buffer is empty or dropped, its network buffers belong to the data exchange
until other tasks read them, and splits it never took are dropped. A task that ends with memory
still accounted is logged by the worker as a leak, with what holds it.

## Limitations

- The heap guard that slows down or fails the task holding the most memory when the heap runs
  full, the detection of leaked class loaders and the disk quota per job come in a later version.
- A task that was given up keeps its thread until the worker restarts; restarting a worker with
  stuck threads by itself comes in a later version.
- The memory of the source and sink plugins themselves, such as their client libraries, is not
  accounted.
