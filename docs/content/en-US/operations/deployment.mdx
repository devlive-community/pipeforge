A cluster is one **master** and any number of **workers** (see [cluster](../concepts/cluster)).
Both come with the distribution, which also holds the `pipeforge` command and the Web UI server.

## Installing

Unpack `pipeforge-<version>.tar.gz` on every machine of the cluster. In a checkout, build it with:

```bash
./mvnw -B -pl pipeforge-dist -am package -DskipTests
tar -xzf pipeforge-dist/target/pipeforge-0.1.0-SNAPSHOT.tar.gz
```

| Directory | Content |
|---|---|
| `bin/` | `pipeforge` (the command) and `pipeforge-master`, `pipeforge-worker`, `pipeforge-standalone` as `.sh` and `.cmd` |
| `conf/` | `pipeforge.yaml`, `master.yaml`, `worker.yaml`, `logback.xml`, `jvm.options` |
| `lib/` | the libraries; `lib/logback/` the logging of the cluster processes, `lib/server/` the server |
| `plugins/` | the plugins the master offers, and the [driver plugins](../concepts/plugins#driver-plugins) you install: `fake`, `mysql` (with the driver plugin installed separately), `postgres`, `jdbc` (with the drivers you install), `field-mapper`, `console`, `blackhole` |
| `logs/`, `run/`, `data/` | created at the first start: logs, process IDs, plugin caches |

The processes need Java 21 or later; `JAVA_HOME` selects the runtime.

## Starting a cluster

Every process needs the same cluster token. Set it in `conf/pipeforge.yaml` of every machine, or
give it as an environment variable:

```bash
export PIPEFORGE_CLUSTER_TOKEN="$(openssl rand -hex 32)"
```

On the master's machine:

```bash
bin/pipeforge-master.sh start
```

On each worker's machine, tell the worker where the master is and how others reach it:

```bash
export PIPEFORGE_WORKER_MASTER_ADDRESS=master.example.com:6123
export PIPEFORGE_WORKER_HOST=worker-1.example.com
bin/pipeforge-worker.sh start --labels zone=east
```

The worker registers with the master and offers its slots, one per processor unless
`worker.slots` says otherwise; its log shows `Worker … offers 8 slot(s)`. For a trial on one
machine, `bin/pipeforge-standalone.sh start` runs a master and a worker in one process.

## Managing the processes

| Command | Effect |
|---|---|
| `start` | Starts the process in the background and waits until it runs; if it does not start, prints the end of its output and exits with 1 |
| `stop` | Stops it: SIGTERM, then SIGKILL after 60 seconds |
| `status` | Exits with 0 when it runs, 3 when it does not |
| `restart` | `stop`, then `start` |
| `run` | Runs it in the foreground, for containers and service managers such as systemd |

`start`, `restart` and `run` accept `--set key=value` and `--labels key=value,...`. A process
writes its ID to `run/<role>.pid` and its log to `logs/pipeforge-<role>.log` (a new file every day
or 100 MB, kept 14 days); what it prints before logging starts goes to `logs/pipeforge-<role>.out`.
`PIPEFORGE_LOG_DIR` moves the logs. Every task also writes a log of its own under `logs/tasks/`
(see [logs](./logs)).

On Windows the `.cmd` scripts offer the same commands except `restart`; `stop` ends the process at
once, since Windows has no SIGTERM.

## Configuration

Settings come from `conf/*.yaml`, then `PIPEFORGE_*` environment variables, then `--set`; the
[configuration reference](../reference/configuration) lists every one with its default. JVM
options are in `conf/jvm.options`, one per line; a line applies to every process, or to one when it
starts with `master:`, `worker:` or `standalone:`. `JAVA_OPTS` adds options for one start:

```text
-XX:+UseG1GC
master: -Xmx2g
worker: -Xmx4g
```

Checkpoints go to the storage of `checkpoint.dir`, which every master and worker must reach: a
directory, on NFS at the same path everywhere, or `s3://bucket/prefix`. Each process checks it at
its start; see [checkpoint storage](./checkpoint-storage). The master then also needs
`master.metastore.url` in `conf/master.yaml`, the server's [metastore](./metastore#the-master),
where it records the checkpoints. The workers write the states of their tasks to the same storage.

## Ports and security

| Port | Setting | Who connects |
|---|---|---|
| 6123 | `master.rpc.port` | workers, and clients that submit jobs |
| 6125 | `worker.rpc.port` | the master, to deploy and cancel tasks |
| 6124 | `worker.data.port` | other workers, to read the rows of tasks |

Every call carries the cluster token; a process with another token is refused with
[`PF-CLUS-0005`](../reference/errors#pf-clus-0005). With `security.tls.enabled`, the RPC between
the processes is encrypted with the PKCS#12 key and trust stores of `security.tls.*`. Keep the
ports reachable only inside the cluster's network.

## Submitting jobs

The master accepts runs over its RPC (`DispatcherService` of the
[engine protocol](../development/engine-protocol)): it plans the job with its plugins, places the
tasks on the workers' slots and follows the run. People and scripts submit jobs to the
[server](./server#running-jobs-on-a-cluster), which keeps the runs and talks to the master: with
`pipeforge run <file>` (see the [cluster quickstart](../getting-started/cluster-quickstart)), the
[Java client](../development/java-client), the REST API or the Web UI.

## Standby masters

A cluster can run more than one master: the masters that share its `cluster.name` and
[metastore](./metastore#the-master) (`master.metastore.url`) elect one leader through a lease in the
metastore's `leader` table. Start them the same way on different machines; nothing else needs to be
set. Only the leader takes registrations, heartbeats and runs. A standby answers every request with
[`PF-CLUS-0018`](../reference/errors#pf-clus-0018) `NOT_LEADER`, naming the leader, and only serves
the plugin packages.

- The leader renews its lease every third of `master.leader.lease` (15 seconds by default).
- A standby takes the lease over when it has seen it unchanged for a whole lease, measured on its own
  clock, so the clocks of the machines do not have to agree.
- A leader that cannot renew steps down after two thirds of a lease, before any standby can take
  over, and stops serving even when it cannot reach the metastore.
- A master that is stopped gives its lease up, so that a standby takes over within a third of a
  lease. A master that loses the lead it had exits with code 1; start it again and it joins as a
  standby.
- Every new leader has the next leader epoch, which every request to a worker carries. A worker that
  has heard from a leader refuses requests of the leaders before it with `PF-CLUS-0006`
  `RPC_STALE_EPOCH`, so a master that was cut off cannot control tasks any more.

| Setting | File | Default | Meaning |
|---|---|---|---|
| `master.host` | `master.yaml` | the host name of the machine | The address workers and servers reach this master at; a standby names the leader by it |
| `master.leader.lease` | `master.yaml` | `15s` | How long a lease lasts without renewal |
| `cluster.name` | `pipeforge.yaml` | `default` | The masters of a cluster compete for its lease |

Without `master.metastore.url` there is no election: the master leads alone with epoch 1.

**Failing over.** Give workers and the server every master of the cluster:
`worker.master.address: master-1:6123,master-2:6123` and the same list in
`pipeforge.master.address`. They call one master at a time; a standby that names the leader sends
them there, and a master that does not answer sends them to the next one. When a new leader takes
over:

1. Workers lose the old leader's heartbeats or are sent on, and register with the new one. A worker
   that registers with a leader of a higher epoch cancels the tasks and releases the slots of the
   one before: the new leader knows none of them.
2. The server finds that the new leader does not know its running runs and submits each again, in
   the same attempt, from its last completed [checkpoint](../concepts/checkpoint), or from the
   start when the job is delivered exactly once and has none. Checkpoint numbers go on from those
   of the run, so its sinks commit and abort as after any restart: the rows of the target are
   neither lost nor written twice, as far as the job's delivery guarantee holds.
3. A run without a checkpoint to go on from fails with `PF-CLUS-0016` `RUN_LOST`, and is retried
   when `env.retry` allows.

With the default settings a failover takes about a lease and a heartbeat timeout, 15 to 45 seconds,
plus the time the runs take to start again.


## Maintenance drills

**Failing over by hand.** `pipeforge cluster failover` asks the leading master to give its lease up
(it asks first; `--yes` skips the question, and is needed outside a terminal). A standby takes over
within a third of `master.leader.lease`, and the runs go on there from their last checkpoints as in
any [failover](#standby-masters). The old leader stops with exit code 1, so that its supervisor —
systemd or Kubernetes — starts it again as a standby. Use it to upgrade the masters one by one:
upgrade a standby, fail over to it, then upgrade the old leader. Masters without a metastore elect
no leader and refuse with `PF-CLUS-0019`.

```bash
pipeforge cluster failover --yes
```

**Draining a worker.** `pipeforge cluster drain <worker>` gives a worker no new tasks: its free
slots are offered to no run, and the tasks running on it finish where they are. With `--wait` the
command waits until none runs any more (`--timeout`, 30 minutes by default; exit code 5 when tasks
still run then), so the worker can be stopped for maintenance without failing a task.
`pipeforge cluster workers` marks it `(draining)`; `pipeforge cluster uncordon <worker>` gives it new
tasks again. The IDs are those `cluster workers` lists.

```bash
pipeforge cluster drain 6f1c2b7e-1d8a-4c55-9b0e-7a3f1e2d4c11 --wait --timeout 2h
```

A drain is kept by the leading master while the worker registers again, but not across a failover:
drain it again on the new leader.

## Troubleshooting

| Error | Cause and fix |
|---|---|
| `PF-CONF-0011` `SETTING_INVALID` | A setting is unknown, of the wrong type, or `cluster.token` is missing. The error names the key and the file or variable it came from. |
| `PF-RES-0006` `PORT_IN_USE` | Another process uses the port. Stop it or change the port setting. |
| `PF-CLUS-0005` `RPC_UNAUTHENTICATED` | The processes have different cluster tokens. |
| `PF-CLUS-0001` `WORKER_LOST` | A worker stopped sending heartbeats; see [cluster](../concepts/cluster#troubleshooting). |
| `PF-CLUS-0019` `FAILOVER_UNAVAILABLE` | `cluster failover` on a master that elects no leader: give the masters a metastore and start a standby. |
| `PF-CLUS-0020` `WORKER_NOT_FOUND` | `cluster drain` or `uncordon` names a worker the master does not know; take the ID from `cluster workers`. |
| `PF-CLUS-0018` `NOT_LEADER` | A worker or server talks to a standby master. Point `worker.master.address` and the server's master address at the leader the error names. |

## Limitations

- Draining waits for tasks to end: moving streaming tasks to other workers through a checkpoint
  comes with streaming jobs.
- Runs come back on a new leader only through the server: a run submitted to a master directly,
  without a server, is not recovered.
- The time a run already ran in an attempt counts towards its `env.timeout.run` as the server
  recorded it; a run that is recovered keeps no savepoint of a pause the old leader was taking.
- `standalone` runs a master and a worker; the server joins it once it submits jobs to a cluster.
- The settings of the metadata database, checkpoints and isolation arrive with those features.
