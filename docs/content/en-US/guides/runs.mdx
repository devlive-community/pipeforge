The **Runs** page lists every run of a job on the cluster, newest first. A run is created when a job
is submitted to the server (`POST /api/v1/runs`, see [running jobs on a
cluster](../operations/server#running-jobs-on-a-cluster)). On a server without a master, a submitted
run fails at once with `PF-CLUS-0015` and is listed as failed.

<Screenshot name="runs" alt="The runs page" />

## The list

| Column | Meaning |
|---|---|
| Job | The name of the job, and the first characters of the run's ID |
| State | **Queued**, **Running**, **Cancelling**, **Succeeded**, **Failed**, **Timed out** or **Cancelled** |
| Submitted | When the run was submitted, in the time zone of the browser |
| Duration | From the start to the end; while the run runs, up to now |
| Read, Written | The rows the sources read and the sinks wrote, as of the last sample of the run's metrics (every 10 seconds by default), or a dash before the first one |
| Error | The error code of a run that did not succeed; hover or focus it for the message, and look it up on the [error codes](./error-codes) page |

The page asks the server again every two seconds while it is open, and stops while the browser tab
is hidden, so a page left in the background costs nothing.

## Finding runs

Choose a state group above the list:

| Group | States |
|---|---|
| All | Every run |
| Active | Queued, Running, Cancelling |
| Succeeded | Succeeded |
| Failed | Failed, Timed out |
| Cancelled | Cancelled |

Type a job's name into the search field to see only its runs; the name must match exactly. Both
filters are part of the address (`/runs?state=failed&job=orders-daily`), so a filtered list can be
bookmarked and shared. A list longer than 50 runs has **Previous page** and **Next page** buttons.

## A run

Select a job's name in the list to open its run. The top of the page shows the run's ID, when it
was submitted, started and ended, how long it took and, for a run that did not succeed, its error.
The address (`/runs/<id>`) can be shared; a run that does not exist says so. While the run is not
finished, the page asks again every two seconds.

<Screenshot name="run-detail" alt="The overview of a run" />

The **Overview** tab:

| Part | Shows |
|---|---|
| Rows | The rows read and written with their current rates, the rows between the readers and the writers (in flight) and the bad rows skipped; the splits read of all splits, as progress |
| Waits | How much of the tasks' time went to waiting: readers for the target, writers for the source, for the rate limit and for network buffers |
| Bottleneck | What limits the run, the metrics that show it and what to change, from the [run analysis](../concepts/plan-and-explain#run-analysis); a running run is judged on the last 10 seconds, a finished one on the whole run |

The **Metrics** tab (`/runs/<id>?tab=metrics`) draws the read and write rates and the rows over
time from the server's samples of the run's metrics, and lists the rows in and out of each node of
the plan. The charts appear once there are two samples; the server takes one every 10 seconds by
default (`pipeforge.master.metrics-interval`).

<Screenshot name="run-metrics" alt="The metrics of a run over time" />

The **Execution plan** tab (`/runs/<id>?tab=plan`) draws the run's job as a graph with its numbers
on it:

- under each node, the rows it has given (for a sink, the rows it has taken) and its current rate
- the edges are as thick as the rate of the node they come from, so the busy paths stand out
- the node the [run analysis](../concepts/plan-and-explain#run-analysis) finds to be the bottleneck
  has a warning border and mark; the conclusion, evidence and advice follow below the graph

Choose a node to see its rows in and out, filtered and added by expansion, bad rows skipped, bytes
in and out, and rates in and out. The chosen node is part of the address
(`/runs/<id>?tab=plan&node=warehouse`). A node's counters add up all of its parallel subtasks.
How busy each node is and where it waits are not measured per node yet; the overview shows the
waits of the whole run.
