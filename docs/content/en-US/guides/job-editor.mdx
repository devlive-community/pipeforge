The job editor is the place to write and check a job definition before it runs. It validates the
YAML on the server while you type, marks problems where they are, and shows the plan and the graph
once the job is valid. It does not run jobs or store them on the server: the definition is kept in
your browser until you export it.

<Screenshot name="job-editor" alt="The job editor with a valid job and its plan" />

The editor fills the browser window and shows the job name in the toolbar. Switch between **Topology** and **YAML** in the center. The left pane shows installed components and the nodes in the current job. The right pane shows properties of the selected node. On wide screens, drag the separators on either side to resize the panes. On narrow screens, open the component library or node properties from the workspace toolbar. Long content scrolls within its pane.

The results pane starts collapsed. Open a result tab or drag the separator above it upward. When a separator has keyboard focus, arrow keys resize the pane. Double-click a separator to reset its size.

## Opening the editor

Choose **Job editor** in the navigation, or open `/editor`. The first time it shows an example job;
afterwards it shows your last draft. **Load the example** replaces the draft with the example
again.

## Writing a job

The editor follows the [job DSL](../reference/job-dsl). Completion knows the fields of the job, of
`env` and of the nodes, and the options of every installed plugin:

| Where | What is offered |
|---|---|
| At the top level | `version`, `name`, `env`, `source`, `transform`, `sink`, … |
| In `env` | `mode`, `parallelism`, `delivery`, `timezone`, `variables`, and under `env.source` the options sources declare |
| In a node | `id`, `type`, `plugin`, `inputs`, `parallelism`, and the options of the node's `type` |
| After `type:` | The installed components of that kind |
| After `inputs:` | The ids of the sources and transforms |
| After an option with choices | Its values, for example `batch` and `streaming` after `mode:` |

Completion opens while you type, or with **Ctrl+Space**. It works in block style (one key per
line); in flow style (`{ id: src, type: fake }`) the editor still validates but does not complete.
Fields already written in the same mapping are not offered again.

## Problems

About half a second after you stop typing, the server [validates](../reference/api#validatejob)
the job. The status next to the title says **Valid** or how many problems there are.

<Screenshot name="job-editor-problem" alt="A missing plugin marked at its node in the editor, the graph and the problem list" />

- A mistake in the YAML is marked at its line and column, with the reason.
- A problem of a node, such as a plugin that is not installed, is marked at the node: in the
  editor, in red in the graph, and in the **Problems** tab with the error code and a hint.
- **Line N** in the problem list moves the cursor there; choosing a node in the graph does the same.
- Warnings, such as an `env` default that no node uses, are listed as well.

## Field mappings

The **Mapping** tab edits a `field-mapper` node with the mouse: drag input columns onto output
columns, rename and retype them, and the YAML follows. See the
[field mapping editor](./field-mapping).

## Plan and text

Once the job is valid, the **Plan** tab shows what `explain` prints, in tables: the job settings
and variables, the nodes with their plugins, parallelism and inputs, the options of each node with
where every value comes from, and the tables each node produces. The **Text** tab shows the same
plan as text. See [plan and explain](../concepts/plan-and-explain) for what it contains.

## Editing options

Choose a node from the outline, the topology, or the menu in **Node configuration**. Edit its options
in the panel. Select **Option details** to see descriptions, defaults, ranges, and choices from
the installed component. Changes are written at that node in YAML, preserving the surrounding text and comments.

- numbers, durations and text are written when you press **Enter** or leave the field; a number
  outside the option's range or a word where a number belongs is refused with a message, and a
  variable such as `${env:ROWS}` is accepted anywhere
- a yes/no option has **default**, **true** and **false**; a choice has a menu that starts with
  **default**
- emptying a field or choosing **default** removes the option, so its default applies
- lists and maps, such as the columns of the `fake` source, are shown but edited in the definition
- secret options are not shown as typed

A node written on one line (`{ id: print, type: console }`) is rewritten in block style the first
time one of its options changes.

## Dry run and data preview

**Dry run** in the toolbar runs the job in the server and shows the rows that would reach its
sinks, without writing them anywhere: the sinks are replaced and not even planned. To see what one
node produces instead, open the **Preview** tab, choose a source or transform (choosing a node in
the graph does the same) and press **Run**.

<Screenshot name="job-editor-preview" alt="A dry run of the example job with its first rows" />

The job runs at parallelism 1 in the server's own process, with the server's plugins and its access
to the sources, until 100 rows of a table were read, the sources were read to the end, or 30
seconds passed. The tab shows how it ended, how many rows were read in how long, and the first rows
of every table with its columns and types; `NULL` stands for missing values. When the job fails,
its error code and message take the place of the rows. A preview of an earlier version of the job
is marked once you change the definition. Both need a job without problems. See [previews and dry
runs](../operations/server#previews-and-dry-runs) for the limits on the server.

## The graph

The topology follows the YAML as you edit. Drag an installed component from **Components** onto the canvas, or select its button to add it with the automatic layout. Drag a node to rearrange its position within the current editor session. Drag an output port onto an input port to update the downstream node's `inputs` in YAML. You can also select the two ports in order with the keyboard. For a node with several upstream inputs, remove individual links from **Upstream inputs** in the properties pane.

Drag an empty area to pan. Hold **Ctrl** or **Cmd** and scroll, or use the zoom controls. Select a node to see its configuration, then choose **Go to YAML** to jump to its definition.

## Importing and exporting

**Import** reads a `.yaml`, `.yml` or `.json` file into the editor; **Export** downloads the
definition as `<name>.yaml`. The draft is saved in the browser as you type, so a reload keeps it,
but it is not shared with other browsers.

## Troubleshooting

| Problem | What to do |
|---|---|
| "The job cannot be checked" | The server does not answer; check that it is running |
| A plugin is not installed (`PF-PLUG-0001`) | Install it into the server's plugin directory, see [server](../operations/server) |
| No completion for options | Completion needs the node's `type` written in block style; options come from the installed plugins |
| A dry run cannot connect to a source | The server reads the sources from its own host; it needs the same network access and drivers as a worker |
