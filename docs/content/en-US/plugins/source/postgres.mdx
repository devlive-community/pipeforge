## Introduction

The PostgreSQL source (`type: jdbc-postgres`) reads tables of a PostgreSQL database over JDBC: one
table, every table whose name matches a pattern, or the result of a query. It reads a snapshot of
each table in bounded jobs, split into key ranges that the readers share, and streams the rows
without holding a result in memory.

Use it to copy a PostgreSQL schema or some of its tables into another system, to load tables into a
data lake or warehouse each day, or to feed a query result to a pipeline. Changes as they happen
(CDC) come in a later milestone. The same plugin writes into PostgreSQL with the
[PostgreSQL sink](../sink/postgres).

## Quick start

```yaml
version: 1
name: orders-to-console
source:
  - id: orders
    type: jdbc-postgres
    url: jdbc:postgresql://db.example.com:5432/shop
    username: reader
    password: ${env:PG_PASSWORD}
    table: public.orders
sink:
  - { id: out, type: console }
```

## Prerequisites

- **Nothing to install:** the plugin ships the PostgreSQL JDBC driver (42.7, BSD-2-Clause).
- **Network access** from the workers, and the master that plans the job, to the PostgreSQL port.
- **A user with `USAGE` on the schemas and `SELECT` on the tables.** Tables the user cannot see are
  not listed for `tables.include`.

## Data source configuration

The node connects with `url` (the database is part of it), `username` and `password`. Properties of
the driver go into `jdbc.properties.<name>`; the plugin sets two unless you set them:

| Property | Value | Why |
|---|---|---|
| `reWriteBatchedInserts` | `true` | used by the sink: batches become multi-row inserts |
| `stringtype` | `unspecified` | text parameters take the column's type, so `jsonb`, `uuid` and enum columns accept text |

Properties that make the driver load a class by name (`socketFactory`, `socketFactoryArg`,
`sslfactory`, `sslfactoryarg`, `sslhostnameverifier`, `sslpasswordcallback`,
`authenticationPluginClassName`) or write a file (`loggerFile`) are controlled: setting them fails
with `PF-CONF-0003`. TLS works through the usual `ssl`, `sslmode` and `sslrootcert` properties. The
password never appears in logs, metrics or exported jobs.

## Splits and parallelism

- Table names are `schema.table` within the database of the URL.
- With `split.mode: range` (the default) a table is split on `split.column`, or on its primary key
  when that is a single integer column. The source reads its `MIN` and `MAX` and cuts the range into
  `split.count` parts (four per reader by default), plus one split for `NULL` values when the
  column is nullable.
- A table without such a column, `split.mode: none` and a `query` are read in one split.
- With `tables.include` every table is split on its own and the splits of all tables share one
  queue.
- Each reader keeps one connection and streams one split at a time, `fetch-size` rows per round
  trip, inside a transaction, which the driver needs to stream.

## Consistency

Each split is a separate query in the reader's transaction, so different splits, and different
readers, can see the table at different moments while it is written, and a row whose key moves
between splits can be read twice or not at all. Read a table that is not written meanwhile, or a
replica, when the copy must be exact.

### Resume

A range split is read in the order of its split column, and a checkpoint always falls between two
values of the column: the reader reads one row ahead and ends a poll only where the value changes.
The split's state records the last value read, and a reader restored from the checkpoint reads the
split on with `<range> AND <column> > <last value> ORDER BY <column>`. Every row of the split is
then read exactly once across the restore, also when the column has the same value in many rows;
finished splits are not read again.

- More than `resume.max-group-rows` rows (100,000 by default) with one value let a checkpoint fall
  among them; that split then resumes before the value and reads its rows again.
- A whole table (`split.mode: none`, or no integer key to split on), a `query` and the split of NULLs
  resume from their start.
- Whether the target then receives a row once depends on the sink: see
  [failure handling](../../concepts/failure-handling#region-restarts).

## Examples

### Every table of a schema but the backups

```yaml
version: 1
name: public-copy
source:
  - id: public
    type: jdbc-postgres
    url: jdbc:postgresql://db.example.com:5432/shop
    username: reader
    password: ${env:PG_PASSWORD}
    tables.include: ["public\\..*"]
    tables.exclude: [".*_bak"]
    split.count: 32
    fetch-size: 5000
sink:
  - { id: out, type: console }
```

Names are matched whole, as `schema.table`. The system schemas `pg_catalog`, `pg_toast` and
`information_schema` are never selected.

### A query over TLS

```yaml
version: 1
name: paid-orders
source:
  - id: paid
    type: jdbc-postgres
    url: jdbc:postgresql://db.example.com:5432/shop
    username: reader
    password: ${env:PG_PASSWORD}
    jdbc.properties.sslmode: verify-full
    query: SELECT id, customer_id, amount FROM public.orders WHERE status = 'PAID'
sink:
  - { id: out, type: console }
```

The query's result columns become a table named after the node (`paid`), read in one split.

## Metrics

The source reports the standard source metrics: `rowsRead`, the read rate and splits assigned and
finished. Rows whose values cannot be read count as bad rows and follow the job's
[dirty data policy](../../concepts/dirty-data).

## Performance and tuning

- Set `split.count` to a few times the parallelism and split on an indexed integer column; each
  split is a range query on it.
- `fetch-size` (1,000 by default) sets the rows per round trip; memory grows with it, not with the
  table.
- Each reader holds a transaction open while it reads, which holds back `VACUUM` on a busy primary;
  read long copies from a replica.

## Errors and troubleshooting

| Error | Cause and fix |
|---|---|
| `PF-CONN-0001` | The server cannot be reached, refused the connection, or the database does not exist |
| `PF-AUTH-0001` | Wrong user or password, or `pg_hba.conf` does not allow the workers' hosts |
| `PF-META-0001` | The table does not exist or the user cannot see it |
| `PF-CONF-0002` … `tables.include` … `no table of … matches` | No visible table matches the patterns; they must match the whole `schema.table` name |
| `PF-CONF-0003` | A controlled driver property was set in `jdbc.properties.*` |
| `PF-DATA-0001` | A column has a type the plugin cannot read, such as geometric types or arrays of other elements |

## Known limitations

- A whole table, a query and the split of NULLs resume from their start after a restore (see Resume under Consistency).
- Bounded reads only; CDC comes in a later milestone.
- Partitioned tables are read through their partitions; `tables.include` does not list the parent.
- Geometric and range types, and arrays other than of booleans, numbers and text, cannot be read.
- PostgreSQL 12, 13, 15 and 17 are not verified yet.
