## What the protocol covers

A PipeForge cluster has one process that schedules (the master) and many that run tasks (the
workers); the server submits jobs to the master. They talk to each other in **protocol v1**, the
gRPC services and Protobuf messages of the package `pipeforge.rpc.v1`:

| Service | From → to | What it carries |
|---|---|---|
| `ResourceManagerService` | worker → master | registration, heartbeats, the slots a worker offers |
| `TaskExecutorService` | master → worker | slot requests, task deployment and cancellation, split assignment, task logs |
| `JobMasterService` | task → master | task state changes, split requests, task metrics |
| `DispatcherService` | server → master | job submission, cancellation, status, metrics, run analysis; the splits of a run with their readers (`ListSplits`), and task logs (`ReadTaskLog`), which the master forwards from the worker the task ran on, and the state of the cluster (`GetCluster`: the master, and every worker with its slots, labels, resources and last heartbeat), so the server reaches only the master |
| `BlobService` | worker → master | plugin packages by their SHA-256, streamed in chunks and resumable from an offset (added after the freeze, as a compatible addition) |

The definitions live in `pipeforge-engine/engine-rpc/src/main/proto/pipeforge/rpc/v1/`. The build
generates the Java messages and service stubs from them (package
`org.devlive.pipeforge.engine.rpc.proto`); the engine itself works with its own types, and
`ProtoMapping` converts between the two at the edge.

The [cluster](../concepts/cluster) processes (master, workers) speak it over gRPC; local runs
(`pipeforge run --local`) use the same interfaces in process.

### Checkpoint messages

Checkpoints add RPCs to three services, all compatible additions to v1:

| RPC | Service | What it does |
|---|---|---|
| `TriggerCheckpoint` | `TaskExecutorService` | starts checkpoint *n* at a source task; the other tasks start it when its barrier reaches them; `stop` ends the input after the snapshot (stop-with-savepoint) |
| `NotifyCheckpointComplete`, `AbortCheckpoint` | `TaskExecutorService` | tells a task that checkpoint *n* is complete, so that sinks commit, or that it was given up |
| `AcknowledgeCheckpoint`, `DeclineCheckpoint` | `JobMasterService` | a task's part of checkpoint *n*: a `StateHandle` per stateful node (inline bytes or a file of the checkpoint) with its timings, or the error that kept it from taking part |
| `TriggerSavepoint`, `StopWithSavepoint`, `ListCheckpoints` | `DispatcherService` | savepoints of a run, with or without stopping it, and the checkpoints the master keeps |

`TaskDeployment` carries the states a task restores (`restore_state`, `restore_checkpoint_id`;
numbers 9 and 10, reserved for them from the start), `SubmitJobRequest` where a run starts from
(`restore`) and its attempt, `JobStatus` the attempt and the last completed checkpoint, and
`RunState` the states of restarts and pauses: `RESTARTING` 8, `PAUSING` 9, `PAUSED` 10,
`RETRY_WAIT` 11. A master that does not know a state refuses it rather than guessing.
`JobMetrics` carries the [checkpoint metrics](../concepts/checkpoint#observability) in fields 27 to
30.

The master answers acknowledgements in the order of section 2.6 of the specification: it writes
`_metadata`, records the checkpoint as completed in the metastore, and only then sends
`NotifyCheckpointComplete`. A decline that already carries `PF-CKPT-0005` keeps its reason.

## Conventions

- Every request starts with a `Header`: the protocol version, the master's and the job's epoch (a
  newer master or job master always has a larger one, and older requests are refused), a request ID
  that makes retries idempotent, and a deadline.
- Values that a plugin serializes, such as splits or what a sink prepared to commit, travel as
  `Versioned{version, data}`, so the receiving side calls the plugin's serializer with the version
  that wrote them.
- A task that fails reports an `ErrorInfo`: the [error code](../concepts/errors), its parameters,
  where it happened (node, subtask, table…), its kind and the chain of causes. The master rebuilds
  the same error object from it, so the CLI, the REST API and the Web UI show what the worker saw.
- Enum values carry the name of their enum (`TASK_STATE_RUNNING`, `RUN_STATE_RUNNING`), because
  Protobuf enum values share one namespace per package.
- Options that a plugin marks as sensitive, such as passwords, are never part of a task's
  description; they are encrypted for the worker that runs the task.

## Task descriptions

A task arrives with its **description**: the chain of nodes it runs, the options of each node, the
tables between them and the context of the run (job, run, time zone, variables, start time). It is
the `ChainDescriptor` message inside an envelope that the worker checks before it reads anything:

```text
+---------+----------------+--------+---------------------------+---------+
| "PFCH"  | format version | length | Protobuf ChainDescriptor  | CRC32C  |
| 4 bytes | 4 bytes        | 4 bytes| length bytes              | 4 bytes |
+---------+----------------+--------+---------------------------+---------+
```

- A worker reads every format version up to its own and refuses newer ones, damaged or truncated
  descriptions with a clear message, before it builds anything.
- Nodes name their components by plugin and identifier (`fake`, `connector-mysql@1.2.0`); the
  worker resolves them with its own plugins. The deployment's `plugins` list each plugin once with
  the SHA-256 of its package, followed by the driver plugins it requires.
- A chain starts with a source or reads its first node's input from other tasks, and ends with a
  sink or writes to outputs: one output edge per downstream chain, with its partitioning and one
  subpartition per downstream task. The deployment lists the task's inputs: for every upstream
  task, its attempt, output and the subpartition to read, and the data address of its worker, or
  none when it runs on the same worker.
- Every table appears once in a table directory, with its columns as DSL types
  (`DECIMAL(10, 2) NOT NULL`); nodes and, later, rows refer to tables by their number there.
- Options are JSON. Options a plugin marks as sensitive never enter the description: their values
  are delivered separately, encrypted for the worker, and the description holds
  `{"$secret": "<node>.<option>"}` in their place.
- The same description always gives the same bytes. A sample of every released format version is
  kept in `pipeforge-engine/protocol-compat/chain/`, and each build checks that it still reads it
  and still writes it byte for byte.

Local runs write the description of every task and read it back before the task starts, so the
whole test suite runs through this format.

## Row format

Rows travel between tasks in a compact binary format (`RowCodec` in `pipeforge-engine/engine-network`).
A data buffer holds rows one after another; each row is:

```text
+------------+------------+----------+-----------------+--------------------+------------------+
| row length | row header | table    | null bitmap     | slots              | variable section |
| varint     | 1 byte     | varint   | 1 bit per column| 8 bytes per column | the rest         |
+------------+------------+----------+-----------------+--------------------+------------------+
```

- The **row length** counts the bytes after it. The **header** holds the row kind in bits 0–1
  (`0` insert, `1` update before, `2` update after, `3` delete) and, in bit 2, whether the row has
  an event time; that time is then the first 8 bytes of the variable section, in milliseconds.
- The **table** is the number of the row's table in the table directory of the task description;
  rows carry no column names or types, so they are read with the columns of that table.
- Bit *i* of the **null bitmap** (low bit first) is set when column *i* is NULL.
- Every column has an 8-byte **slot**. Integers, booleans, floats (their IEEE 754 bits), dates
  (days since 1970-01-01), times (nanoseconds of the day), timestamps up to precision 6
  (microseconds since 1970-01-01, `TIMESTAMP` taken as UTC) and decimals up to precision 18 (the
  unscaled `long`) are stored in the slot itself.
- Strings, JSON and bytes of up to 7 bytes are stored **inline**: the first byte of the slot is
  `0x80` plus the length, the content follows. Longer values, decimals above precision 18,
  timestamps above precision 6 (microseconds plus the nanoseconds within them) and arrays, maps and
  nested rows are stored in the variable section; their slot holds the **offset** (high 32 bits,
  from the header) and **length** (low 32 bits).
- A nested row is a null bitmap, slots and variable section; an array is its element count
  (varint) followed by the same; a map is an array of keys followed by an array of values. Their
  offsets count from the start of the nested value.
- All integers are big-endian.

A value that does not match its column fails the row with
[`PF-DATA-0001`](../reference/errors#pf-data-0001) (a value of another type) or
[`PF-DATA-0002`](../reference/errors#pf-data-0002) (for example a decimal with more digits than its
precision), naming the column, such as `address.city` or `tags[]`. Timestamps of precision 6 or less
keep microseconds; finer digits are dropped. Bytes that are not a row of a known table are refused
as an internal error. A sample of every format version is kept in
`pipeforge-engine/protocol-compat/row/`; each build checks that it still reads it and still writes
it byte for byte.

## Data exchange

Rows travel between workers over TCP (Netty, `pipeforge-engine/engine-network`), one connection per
pair of workers shared by all channels between them. Every frame is:

```text
+---------+---------+---------+-----------+------------------+
| "PF"    | version | type    | length    | payload          |
| 2 bytes | 1 byte  | 1 byte  | 4 bytes   | length bytes     |
+---------+---------+---------+-----------+------------------+
```

| Type | Frame | Direction | Payload |
|---|---|---|---|
| `0x00` | `Hello` | both | protocol version, worker ID, cluster token |
| `0x01` | `PartitionRequest` | consumer → producer | channel ID, the producer's task attempt and output, subpartition, initial credit |
| `0x02` | `BufferResponse` | producer → consumer | channel ID, sequence, backlog, buffer type (data or event), flags, content |
| `0x03` | `AddCredit` | consumer → producer | channel ID, new credit |
| `0x04` | `CancelPartition` | consumer → producer | channel ID |
| `0x05` | `CloseRequest` | both | — |
| `0x06` | `ErrorResponse` | both | channel ID or none for the connection, error code, message |
| `0x07` / `0x08` | `Ping` / `Pong` | both | — |

- Both ends start with `Hello`. Another cluster token is refused with
  [`PF-CLUS-0005`](../reference/errors#pf-clus-0005), another major version (the version byte of
  every frame) with [`PF-CLUS-0007`](../reference/errors#pf-clus-0007); the refusing end sends an
  `ErrorResponse` and closes the connection.
- Lengths, counts and numbers are varints, strings are a varint length and UTF-8, IDs are 16 bytes.
  A frame longer than `task.max-row-bytes` + 1 KB, a wrong magic or a malformed payload closes the
  connection with an `ErrorResponse`.
- Data buffers hold rows in the row format above; event buffers hold an event type (`0x01` end of
  partition, `0x02` end of input, `0x03` schema change, `0x10` checkpoint barrier; `0x11`–`0x1F`
  are kept for watermarks and stream status) and its content.
- A checkpoint barrier is 18 bytes: `u64` checkpoint ID, `u64` timestamp in milliseconds, `u8`
  type (1 checkpoint, 2 savepoint) and `u8` flags (bit 0 `stop`, the others 0). A barrier with
  another length, type or flag fails the channel. Events need no credit, so a barrier reaches a
  consumer that has stopped giving credit to the channels that already delivered theirs; but no
  event overtakes the buffers sent before it.
- A producer sends a data buffer only while the channel has credit and numbers the buffers of a
  channel from 0; a consumer refuses a buffer out of sequence or without credit.
- An output that a consumer asks for before it exists is waited for up to the partition request
  timeout (30 seconds), then refused with [`PF-CLUS-0011`](../reference/errors#pf-clus-0011).
- A connection that closes without `CloseRequest` fails the unfinished channels at the consumer and
  the outputs they read at the producer with [`PF-CLUS-0010`](../reference/errors#pf-clus-0010).

## Checkpoint files

A checkpoint is a directory of files in a format of its own, so that a later engine can restore
it. Checkpoints themselves are being added now; this is the format they are written in. Both kinds
of file have the same envelope as a task description: a magic number, the format version (1), the
length of the body, the body and its CRC32C, integers big-endian.

| File | Magic | Body |
|---|---|---|
| `_metadata` | `PFCP` | Protobuf `CheckpointMetadata` (package `pipeforge.checkpoint.v1`): the job, run, attempt and job name, the checkpoint's number and type (checkpoint or savepoint), its times, the variables of the run, and for every node its plugin, parallelism and the state of each subtask |
| `<node>-<subtask>.state`, `enum-<node>.state` | `PFST` | The checkpoint's number (8 bytes) and the node's ID, then the bytes of the plugin's state serializer |

- A state up to `checkpoint.inline-threshold` (16 KB by default) is kept inside `_metadata`; a
  larger one gets its own file, which `_metadata` names. A subtask without state is left out, and
  every node records the parallelism it was written with.
- A state file names the checkpoint and node it belongs to; a file copied to the wrong place is not
  read as another's.
- A file whose length or checksum does not match, or that belongs elsewhere, is
  [`PF-CKPT-0002`](../reference/errors#pf-ckpt-0002): recovery falls back to the checkpoint before
  it. A format version newer than the engine reads is
  [`PF-CKPT-0003`](../reference/errors#pf-ckpt-0003).
- Storage that can rename atomically writes `_metadata.tmp` and renames it; object storage writes
  `_metadata` and then an empty `_COMPLETED`. Only a checkpoint with its marker counts as complete.
- `CheckpointMetadata` only grows, like the RPC messages: the same snapshot test checks it. Samples
  of every released format are kept in `pipeforge-engine/protocol-compat/checkpoint/` and must
  stay readable.

## Transport

Processes call each other with gRPC over HTTP/2 (Netty). Every call is protected and made safe to
repeat:

| Concern | How |
|---|---|
| Who may call | Every call carries the cluster token in the metadata `pipeforge-cluster-token`; a server refuses others with [`PF-CLUS-0005`](../reference/errors#pf-clus-0005). |
| Encryption | Optional TLS. The server presents the certificate of a PKCS#12 key store; clients trust the certificates of a PKCS#12 trust store and refuse any other server. |
| Replaced masters | A worker remembers the largest leader and job epoch it has seen and refuses requests with a smaller one ([`PF-CLUS-0006`](../reference/errors#pf-clus-0006)), so only the current master controls its tasks. Releasing a slot concerns no single run and is checked against the leader epoch only. |
| Versions | A request of another major protocol version is refused with [`PF-CLUS-0007`](../reference/errors#pf-clus-0007). |
| Lost answers | A request that got no answer (unavailable, or past its deadline) is sent again up to three times, with exponential backoff and the same request ID. The receiver runs every request ID once and answers repeats with the first result for ten minutes. A refusal is never retried; after the last retry the caller fails with [`PF-CLUS-0008`](../reference/errors#pf-clus-0008). |
| Refusals | A refused call ends with a gRPC status that says why — `UNAUTHENTICATED` (token), `FAILED_PRECONDITION` (replaced master), `UNIMPLEMENTED` (major version), `NOT_FOUND` (unknown run or task log), `RESOURCE_EXHAUSTED` (too few slots) — and carries the error in its trailers, so the caller shows the same error code and message. |
| Order | Split assignments and split requests are numbered per task and node; the receiver hands them over in that order, once, even when they arrive out of order. |
| Split progress | A reader reports the splits it read to their end as a `SplitsFinished` reader event, numbered like split requests. The job master counts only splits it gave that reader; it does not pass the event to the enumerator. |
| Sensitive options | Encrypted for the worker that runs the task: an ephemeral X25519 key agreement with the public key the worker registered, HKDF-SHA256 and AES-256-GCM bound to the task attempt. A worker that restarted cannot read options sealed for its old key ([`PF-CLUS-0009`](../reference/errors#pf-clus-0009)). |
| Metrics | Sent over one stream per worker and job master; every report holds the full counters, so a lost report changes nothing. A report also carries the memory the task accounts now (`memory_bytes`) and the first bad rows it skipped (`dirty_samples`); `GetJobMetrics` sums the memory and the bad rows and keeps the first 20 samples of the job. `TaskSettings.skip_dirty_rows` tells a task the dirty data policy; its default `false` is `fail`. |
| Rate limits | The job master sends each reader its share of the job's rate limit as a `RateLimitQuota` operator event, in order with its split assignments: before its first split and whenever it changes; 0 means no limit. Reports carry the time a task waited for its quota (`throttle_wait_nanos`). |
| Task logs | `ReadLog` streams a task log in chunks of whole lines. It changes nothing, so it checks only the protocol version and is not retried. `LogChunk.offset` is where the next read continues — with filters, the end of the part of the log the chunk covers, not of the text it holds — and `eof` marks the end of the log of a task that has ended. A follow has no deadline; the reader ends it by cancelling the call. See [logs](../operations/logs). |

The deadlines are 60 seconds for deploying a task and 30 seconds for the other requests. Custom
reader events, which a source can send to its split enumerator, stay within one process in this
version; across processes they need a serializer from the source.

## Versions

A protocol version is `major.minor`, `1.0` in this release.

- When two processes connect, they compare versions. Different major versions do not talk to each
  other; with the same major version both use the lower minor version.
- A **minor** version only adds: new fields, new RPCs, new enum values, new event types. An older
  process ignores fields it does not know, so a cluster can be upgraded one process at a time.
- A **major** version is a new package (`pipeforge.rpc.v2`); it is only needed for a change that
  cannot be expressed as an addition.

## Checking compatibility

`ProtoSnapshotTest` lists every file, message, field, enum value, reserved range and RPC of the
protocol as one line, and compares them with
`pipeforge-engine/protocol-compat/rpc/descriptor-v1.txt`. Every line of that snapshot must still be
there, so the build fails when a change would break a running cluster:

| Change | Result |
|---|---|
| New field, message, RPC or enum value | Accepted; the snapshot is extended with `-Dpipeforge.protocol.update=true` |
| Renamed, renumbered or retyped field | Build fails |
| A unary RPC turned into a stream, or other request or response types | Build fails |
| Removed field | Build fails, unless its number and name are `reserved` |
| A reserved number used for a field | Build fails, unless the number was kept for exactly that field from the start (`PLACEHOLDERS` in the test) |

```text
ProtoSnapshotTest.theProtocolOnlyGrows
protocol v1 elements removed or changed; add new fields, RPCs or enum values instead, or reserve
the number and name of a removed field
Expecting empty but was: ["field pipeforge.rpc.v1.Header 3 job_epoch int64"]
```

## Changing the protocol

1. Describe the change in the protocol specification first; changes to the protocol need the
   review of two maintainers.
2. Add the fields or RPCs to the `.proto` files; never reuse a field number, and reserve the number
   and name of a field you remove.
3. Run the `engine-rpc` tests with `-Dpipeforge.protocol.update=true`, then without: the snapshot
   grows by exactly the lines you added, which the review sees in the diff.
4. Extend `ProtoMapping` and its tests, so the new values survive a trip through the bytes.

```bash
./mvnw -pl pipeforge-engine/engine-rpc test -Dpipeforge.protocol.update=true
./mvnw -pl pipeforge-engine/engine-rpc verify
```
