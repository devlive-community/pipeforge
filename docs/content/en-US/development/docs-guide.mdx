## When documentation is required

Every user-visible change updates the documentation site **in the same commit**, in English
(`docs/content/en-US/`) and Chinese (`docs/content/zh-CN/`). Plugins get a plugin page, other
features a feature page, and incompatible changes a migration note. Pure refactoring, tests and
build scripts need no documentation; their commit message says `Docs-Not-Needed: <reason>`.

Which code paths belong to which pages is recorded in `docs-map.yaml` at the repository root.
Register every new module there.

## Page files and frontmatter

A page is an MDX file. Its path below the language directory is its id and its URL:
`development/docs-guide.mdx` is served at `/<language>/next/development/docs-guide/`. The first
directory must be one of `getting-started`, `concepts`, `guides`, `reference`, `plugins`,
`operations` or `development`.

```yaml title="frontmatter"
---
title: Local development environment   # page title, shown as the heading
description: One sentence for search results and link previews.
order: 20                              # position in the section navigation
data: errors                           # optional: generated data the page renders, errors, functions, metrics or api (adds its anchors)
template: feature                      # guide (default), feature or plugin
omit:                                  # template sections that do not apply, with a reason
  performance: The environment is meant for development, not for benchmarks.
---
```

Do not write a level 1 heading; the title comes from the frontmatter.

## Feature page template

Pages with `template: feature` use these level 2 sections, in this order. A section that does
not apply is left out and named in `omit` with the reason.

| Section | Content |
|---|---|
| Overview | The problem the feature solves; when to use it and when not |
| How it works | The mechanism, with a diagram or animation for core mechanisms |
| Quick start | A minimal example that can be copied and run |
| Configuration | Options, DSL fields and settings, taken from generated reference data |
| Examples | At least two complete, realistic examples |
| Behavior | Consistency, behavior on failure, interaction with other features |
| Observability | Metrics, the related `explain` output, alerts |
| Performance and tuning | Parameters that affect performance and recommended values |
| Troubleshooting | Error codes, common problems and their solutions |
| Limitations | What is not supported |
| Version history | Since which version the feature exists and how it changed |

In Chinese the headings are 概述, 原理, 快速上手, 配置, 示例, 行为与语义, 可观测性, 性能与调优,
排障, 限制 and 版本.

## Plugin page template

Plugin pages live at `plugins/<type>/<plugin id>.mdx` and use `template: plugin`. Sections
marked as generated render data exported from the plugin's code and are never written by hand.

| Section | Source |
|---|---|
| Introduction | written |
| Capabilities | generated |
| Verified versions | generated |
| Quick start | written |
| Prerequisites | written |
| Data source configuration | written and generated |
| Node options | generated |
| Native options | generated |
| Type mapping | generated |
| Splits and parallelism | written |
| Consistency | written |
| Examples | written, at least three scenarios |
| Metrics | generated and written |
| Performance and tuning | written |
| Errors and troubleshooting | generated and written |
| Known limitations | written |
| Changelog | generated |

Each generated section contains only the component that renders it, for the plugin the page is
named after; `component` selects one component of a plugin that provides several:

```mdx
## Node options

<PluginOptions plugin="fake" component="source" />
```

| Section | Component | Renders |
|---|---|---|
| Capabilities | `<PluginCapabilities />` | each component with the optional capabilities its factory returns |
| Verified versions | `<PluginVersions />` | the system and versions from `plugin.yaml`, or that the plugin needs no external system |
| Node options | `<PluginOptions />` | every option with type, default, requirement, range, choices, old names and the exclusive and conditional rules |
| Native options | `<PluginNativeOptions />` | the native configuration namespaces |
| Type mapping | `<PluginTypeMapping />` | the read and write mappings of `src/main/plugin/type-mapping.yaml` |
| Changelog | `<PluginChangelog />` | the commits that changed the plugin module, from git |

The data comes from `src/generated/plugin-docs/<id>.json` of the plugin module, which the plugin's
build checks against its code (see [packaging plugins](./plugin-packaging#documentation-data)).

## Components

<Callout type="tip">
  Components are available in every page without an import.
</Callout>

| Component | Use |
|---|---|
| `<Callout type="note">` | Notes; `type` is `note`, `tip`, `warning` or `danger` |
| Code fences | Highlighted code with a copy button; add `title="file.yaml"`, `{2-4}` to highlight lines, or `showLineNumbers` |
| `<Tabs>` with `<Tab label="...">` | Alternatives such as YAML, SQL and CLI |
| `<Steps>` with `<Step title="...">` | Step-by-step procedures |
| `<ErrorList />` | Every registered error code with search and category filters, generated from the error registry; the page declares `data: errors` in its frontmatter so that links to `#pf-conf-0001` anchors are checked |
| `<FunctionList />` | Every built-in function with its signatures, NULL behavior and examples, with search and category filters, generated from the function catalog; the page declares `data: functions` so that links to `#substring` anchors are checked |
| `<ApiList />` | Every endpoint of the REST API with parameters, request and response schemas, generated from `pipeforge-server/openapi.json`; the page declares `data: api` so that links to `#validatejob` and `#schema-errorinfo` anchors are checked |
| `<MetricList />` | Every engine metric with its type, unit and meaning, one table for job metrics and one for node metrics, generated from the metric catalog `pipeforge-engine/engine-api/src/main/resources/metrics/catalog.yaml`; the page declares `data: metrics` so that links to anchors such as `#job-rowsread` are checked |
| `<CliReference />` | Every command of `pipeforge` with its arguments and options, the global options and the exit codes, generated from `pipeforge-cli/cli.json` (a CLI test keeps it equal to the command definitions); commands have the anchor `cmd-<name>` |
| `<Screenshot name="overview" alt="..." />` | A Web UI screenshot in the page language, light or dark following the site theme; the images are generated by `pnpm --filter @pipeforge/ui screenshots` into `public/screenshots/ui/`, and the build fails when one is missing |

```mdx title="example.mdx"
<Tabs>
  <Tab label="YAML">A job written in YAML.</Tab>
  <Tab label="CLI">The same job started from the command line.</Tab>
</Tabs>
```

## Links

Link to other pages with paths relative to the current page, without language or version:
`[local environment](./local-environment)` or `[plugins](../concepts/plugins#isolation)`. The
same text then works in every language and version, and the build verifies the target page
and anchor. Anchors are the heading text in lower case with spaces replaced by hyphens.

## Checks

```bash
cd docs
pnpm generate    # search index and data exported from the code
pnpm check       # structure, translations, links, the UI scan and plugin pages
pnpm build       # static export to docs/out
pnpm dev         # preview with live reload
```

| Check | Fails when |
|---|---|
| structure | frontmatter is incomplete, a template section is missing or empty, the page contains `TODO` |
| i18n | a page is missing in one language, or the two languages differ in template, order, omitted sections, heading structure or number of code blocks |
| links | a link points to a page or anchor that does not exist, or uses a site-absolute path |
| ui | site code uses raw palette colors, `dark:` variants, inline colors, native controls outside `components/ui`, title tooltips or browser dialogs; the rules are shared with the Web UI and live in `@pipeforge/design-tokens/ui-scan` |
| plugins | a generated section of a plugin page holds anything but its component, names another plugin, or the plugin has no documentation data |
| Lighthouse | performance, accessibility, best practices or SEO score below 95 |

## Documentation coverage

Every pull request runs `docs/scripts/check-docs-coverage.sh <base> <head>`. For each commit
in the pull request:

- a `feat` or `perf` commit, or a breaking commit (`type!:` or a `BREAKING CHANGE:` footer),
  that changes a path listed in `docs-map.yaml` must also change every page mapped to that
  path, in both `en-US` and `zh-CN`;
- a commit that ends with `Docs-Not-Needed: <reason>` is exempt; an empty reason is rejected;
- other commit types are not checked.

Independently, every module (each `pipeforge-*` directory and its Maven submodules) must be
covered by an entry in `docs-map.yaml`, and every page listed there must exist in both languages.

```yaml title="docs-map.yaml"
- paths: ["pipeforge-cli/**"]
  docs: ["reference/cli"]
- paths: ["pipeforge-engine/engine-worker/src/main/**"]
  docs: ["concepts/execution", "reference/metrics"]
```

In paths, `**` spans directories and `*` matches within one directory. Run the check locally
before you push:

```bash
docs/scripts/check-docs-coverage.sh origin/main HEAD
```
