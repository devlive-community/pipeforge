## Overview

A **checkpoint** is a consistent picture of a running job: where every source is in its input, what
every sink has prepared to commit, and the splits the source has not handed out yet. It is written
to the [checkpoint storage](../operations/checkpoint-storage) and recorded in the
[metastore](../operations/metastore), so that a run that fails can go on from its last checkpoint
instead of starting over, and a sink commits exactly what a recorded checkpoint covers.

Checkpoints are taken on a cluster whose `checkpoint.dir` is set; jobs control how often and how
many with `env.checkpoint.*`.

## How it works

The master coordinates each checkpoint of a run:

1. It takes the state of the source's split enumerator, then asks the tasks that read the source to
   take part in checkpoint *n*.
2. Each of them takes its state and sends a **barrier** downstream with the rows; every other task
   takes its state when the barrier of *n* has reached it on all its inputs. The barrier is a marker
   in the data stream, so the rows before it are in the checkpoint and the rows after it are not.
3. Every task acknowledges its part to the master, with where its state is.
4. Once all tasks acknowledged, the master writes the checkpoint's `_metadata`, records the
   checkpoint as completed in the metastore, and **only then** tells the tasks that it is complete,
   which is when sinks commit what they prepared for it.

The order of step 4 matters: the latest completed checkpoint in the metastore is never older than
data a sink committed, so a run that starts again from it does not commit the same data twice.

A checkpoint **fails** when a task declines it, when it is not complete within
`env.checkpoint.timeout`, or when the master cannot write or record it. What was written of it is
deleted and the next one is tried at the next interval. After more failures in a row than
`env.checkpoint.tolerable-failures`, the run fails, since a failure would then lose more progress
than the job allows.

### Barriers and alignment

A source task takes its reader's state, which is its splits and how far it read each, on its own thread between
two reads, and then sends the barrier on: every row read before the snapshot is before the
barrier. Tasks chained together pass the barrier along at once. A task that reads from several
upstream tasks, such as a writer behind a hash exchange, **aligns**: once the barrier of *n*
arrived on one input channel, it stops reading that channel and goes on reading the others until
their barriers arrive too; only then does it take its state and pass the barrier on. A channel that
ended does not hold the alignment back. While a channel waits it takes no more buffers, so its
upstream task slows down rather than the rows piling up.

Splits keep their place too. The source's enumerator hands out splits while the job runs, so a
split could be assigned after the enumerator's state was taken and reach its reader after the
reader's state was taken: it would be in neither. The master prevents it. Once it took the
enumerator's state it waits until the splits sent before have reached their readers, and only then
triggers them; splits assigned after the enumerator's state wait at the master until their reader
took its state, and then go out in order. Every split is in exactly one of the two.

Taking a state only copies it; writing it to the checkpoint storage happens on threads of the
worker while the task reads on, and the task acknowledges once its states are written. States up to
16 KB travel in the acknowledgement and end up inside `_metadata`.

### Savepoints

A **savepoint** is a checkpoint taken on request and kept until it is deleted by hand. It is
written to `<run>/savepoints/<name>-<time>/` of the checkpoint storage; the name has letters,
digits, `_`, `-` and `.`, and is `savepoint` when none is given. Taking it does not stop the run,
and its sinks commit what they prepared for it as for any checkpoint. In this version a savepoint
is taken through the master's `TriggerSavepoint` call (see
[engine protocol](../development/engine-protocol)); the command line and the REST API follow.

A **run can start from a savepoint or a completed checkpoint**, given its directory (`restore.path`
of the run). The master reads its `_metadata`, restores the source's enumerator and every task with
its states, and first commits again what the sinks prepared for that point, which committers take
as committed already. The job must be the one that took it, unless another job is allowed
(`allow_other_job`); every node with state must still exist, unless states may be left out
(`allow_non_restored_state`); and nodes with state keep their parallelism. Restarted tasks restore
that point until the run completes a checkpoint of its own, and its checkpoints are numbered after
it.

## Quick start

Give the cluster a checkpoint storage and the master its metastore, in `conf/pipeforge.yaml` and
`conf/master.yaml`:

```yaml
checkpoint.dir: s3://my-bucket/pipeforge
master.metastore.url: jdbc:postgresql://db:5432/pipeforge
```

Jobs take a checkpoint every minute (streaming) or five (batch) by default; set another interval in
the job:

```yaml
env:
  checkpoint.interval: 30s
```

## Configuration

| Option | Default | Meaning |
|---|---|---|
| `env.checkpoint.enabled` | `true` | Take checkpoints at all |
| `env.checkpoint.interval` | `1min` streaming, `5min` batch | The time from one checkpoint to the next; for batch jobs it bounds what a failed run reads again |
| `env.checkpoint.timeout` | `10min` | How long a checkpoint may take before it fails |
| `env.checkpoint.min-pause` | `0` | The least time from the end of one checkpoint to the start of the next |
| `env.checkpoint.max-concurrent` | `1` | The checkpoints that may be in progress at once |
| `env.checkpoint.tolerable-failures` | `3` | The checkpoints that may fail in a row before the run fails |
| `env.checkpoint.retained` | `3` | The completed checkpoints kept; older ones are deleted |
| `env.checkpoint.externalized` | `RETAIN_ON_CANCELLATION` | Keep (`RETAIN_ON_CANCELLATION`) or delete (`DELETE_ON_CANCELLATION`) the checkpoints of a cancelled run |
| `env.checkpoint.on-finish` | `true` | Record a last checkpoint, with what the sinks prepared, before a bounded run commits it and finishes |

The cluster side is `checkpoint.dir` with `checkpoint.s3.*` (see
[checkpoint storage](../operations/checkpoint-storage)) and `master.metastore.*` (see
[metastore](../operations/metastore#the-master)); the [configuration reference](../reference/configuration)
lists them all.

## Examples

A streaming job that tolerates no failed checkpoint and keeps the last ten:

```yaml
env:
  mode: streaming
  checkpoint.interval: 20s
  checkpoint.timeout: 2min
  checkpoint.tolerable-failures: 0
  checkpoint.retained: 10
```

A job that takes no checkpoints, for a preview:

```yaml
env:
  checkpoint.enabled: false
```

## Behavior

| Guarantee | Needs |
|---|---|
| at-least-once | checkpoints and a source that can read again from a position |
| exactly-once in effect | at-least-once and a sink that writes idempotently by key |
| exactly-once | at-least-once and a sink that commits in two phases |
| exactly-once after a failure | at-least-once, a source that resumes at a position and a sink that records it with the rows ([progress table](../plugins/sink/jdbc#progress-table)), in one task |
| none | checkpoints turned off: a failed run starts over |

- Checkpoint numbers grow within a run and never repeat, also across restarts.
- Checkpoints start only while every task of the run runs.
- Savepoints are taken by hand and are never deleted automatically; they do not count toward
  `retained` or the failures a job tolerates.
- When every task of a bounded run has finished, the master records a **last checkpoint**
  (`env.checkpoint.on-finish`): it holds what the sinks prepared at the end of their input and had
  not committed yet, is written with its `_metadata` and recorded as completed, and only then is
  its content committed. The checkpoints in progress are given up, and no others are taken. With
  `on-finish: false` the master commits what the sinks prepared without recording it first.
- When a run ends, checkpoints in progress are given up. A run that **succeeded** deletes its
  checkpoints, the last one included, a **failed** run keeps them to go on from, and a
  **cancelled** run follows `env.checkpoint.externalized`.

## Observability

| Metric | Meaning |
|---|---|
| `lastCompletedCheckpointId` | The last completed checkpoint, 0 before the first |
| `lastCheckpointDurationMs` | How long it took from its trigger to being recorded |
| `lastCheckpointSize` | The size of its state |
| `checkpointFailures` | Checkpoints that failed in a row; a completed one resets it |

They are part of the run's metrics (see the [metrics reference](../reference/metrics)); the
metastore table `checkpoint` keeps each checkpoint with its status, size, directory, error and each
task's part. The master logs every checkpoint that completes or fails.

## Performance and tuning

- Taking a state copies it on the task's thread; writing it happens while the task goes on, so a
  checkpoint costs the throughput of the copy only.
- A shorter interval loses less progress on a failure and writes more often; for batch jobs the
  interval bounds what a failed run reads again.
- Backpressure holds barriers back: when checkpoints time out, look at the run's backpressure
  before raising `env.checkpoint.timeout`.

## Troubleshooting

| Error | Cause and fix |
|---|---|
| [`PF-CKPT-0001`](../reference/errors#pf-ckpt-0001) | A checkpoint timed out; the message lists the tasks that did not finish |
| [`PF-CKPT-0005`](../reference/errors#pf-ckpt-0005) | A task declined, for the reason in the message |
| [`PF-CKPT-0006`](../reference/errors#pf-ckpt-0006) | The master could not write the checkpoint or record it in the metastore |
| [`PF-CKPT-0007`](../reference/errors#pf-ckpt-0007) | More checkpoints failed in a row than the job tolerates; the run failed with the last cause |
| [`PF-CONF-0011`](../reference/errors#pf-conf-0011) `master.metastore.url` | `checkpoint.dir` is set without the master's metastore |
| [`PF-CKPT-0002`](../reference/errors#pf-ckpt-0002) | The directory a run starts from is not a completed checkpoint or savepoint, or a file of it is damaged |
| [`PF-CKPT-0003`](../reference/errors#pf-ckpt-0003) | A run cannot start from that point: another job took it, a node with state is gone, or a node changed its parallelism |

## Limitations

- Transforms keep no state. Sinks commit per checkpoint on the master (see
  [sink state and commits](../development/api-overview#sink-state-and-commits)).
- Savepoints are taken, and runs started from them, only through the master's protocol yet: the
  command line, the REST API and the Web UI follow. A worker declines to stop a run with a
  savepoint, and a node with state cannot change its parallelism when a run starts from a point.
- A task that waited longer than 30 seconds for the barriers of a checkpoint logs a warning about
  backpressure; the limit cannot be changed yet.
- Only aligned checkpoints: a task waits for the barrier on all its inputs.
