## Overview

When a task of a run fails, the job master decides what happens next. The **kind** of the error
decides whether a restart could help, and the job's **restart strategy** (`env.restart`) decides
whether the run may restart once more and how long it waits first. A restart touches only the
**region** of the failed task, which starts again from the last completed
[checkpoint](./checkpoint); the rest of the run goes on.

## How it works

Every error carries a registered [error code](./errors), and every code has a kind:

| Kind | Examples | What the run does |
|---|---|---|
| transient | lost connections (`CONN`), missing resources (`RES`), lost workers (`CLUS`), source or sink errors a plugin marked as transient | asks the restart strategy |
| data | conversion failures, constraint violations, too many bad rows (`DATA`) | fails: bad rows are handled by the [dirty data policy](./dirty-data) inside the task, and a run that reached the master with one would read the same rows again |
| fatal | configuration, plans, plugins, authentication, metadata, internal errors; source and sink errors nobody classified | fails: retrying cannot help |

The kind comes from the code's registry entry or its category. A plugin can set it for a single
error, and a plugin whose library throws its own exceptions classifies them with an
`ErrorClassifier` (see [errors of a library](../development/api-overview#errors-of-a-library)), for
example a MySQL sink that maps vendor error 1045 to `PF-AUTH-0001` (fatal) and a deadlock to a
transient `PF-SINK-0001`. An exception nobody classifies becomes `PF-SRC-0001`, `PF-SINK-0001` or
`PF-PLUG-0007`, which are fatal.

Only transient failures go to the restart strategy, and only they count against it:

| Strategy | Restarts |
|---|---|
| `fixed-delay` (default) | `restart.attempts` times in all, each after `restart.delay` |
| `exponential-backoff` | without a limit; the first wait is `restart.initial`, each later one `restart.multiplier` times longer up to `restart.max`. A failure more than `restart.reset-after` after the one before starts again at `restart.initial` |
| `failure-rate` | after `restart.delay`, as long as no more than `restart.max-failures` failures happened within the last `restart.interval`, this one included |
| `none` | never |

### Region restarts

A region is a set of tasks that exchange rows. In the most common batch job, a chain from source to
sink per subtask, every subtask is a region of its own; tasks on both sides of a hash or rebalance
exchange form one region. When the strategy allows a restart and the run takes checkpoints:

1. The job master cancels the tasks of the failed regions and gives up the checkpoints in
   progress, which can no longer complete. The other regions keep running.
2. The splits their readers got after the last completed checkpoint go back to the enumerator,
   which hands them out again.
3. After the strategy's wait (for tasks of a lost worker, at least twice the cancel timeout, so that
   the worker has [fenced](./cluster) them), once every task of the regions has stopped, it deploys
   them again: on new slots where their worker was lost, each with its state from that checkpoint. Readers
   continue their splits where the checkpoint left them; writers get their state, and abort what
   they prepared after it.

What sinks committed stays committed: a checkpoint's committables are committed when it completes,
and what a sink prepared for a checkpoint that failed is committed with the next one. A sink that
commits in two phases therefore writes every row exactly once across restarts; other sinks write the
rows after the checkpoint again (at least once). Without checkpoints, or before the first one
completed, the regions start from the beginning of their splits.

### Retrying runs

When a run fails as a whole — its restarts are used up, its failure was not one of tasks, or it
takes no checkpoints — the server may start a **new attempt** of it (`env.retry`), under the same
run ID, with the same variables, scheduled time and plugin versions. A failure is retried when its
error is one of `retry.on` (error categories such as `CONN`, error codes, or `TRANSIENT` for every
error whose kind is transient), the run has retries left (`retry.attempts`, 0 by default) and it
was submitted no longer than `retry.within` ago. The run then waits in **`RETRY_WAIT`** for the
backoff — `retry.backoff.initial`, then `multiplier` times longer each time, at most
`retry.backoff.max` — and is queued again.

| `retry.resume` | Where the new attempt starts |
|---|---|
| `auto` (default) | For a job delivered exactly once — every sink commits in two phases or writes idempotently — from the run's last completed checkpoint, or from the start without one: neither writes a row twice. A job delivered at least once is not retried, since both could; set `checkpoint` or `restart`, or retry it by hand |
| `checkpoint` | From the last completed checkpoint, or from the start without one |
| `restart` | From the start |

A run that failed, timed out or was cancelled can also be **retried by hand**, whatever `env.retry`
says: `POST /api/v1/runs/{id}/retry` starts its next attempt with `{"from": "CHECKPOINT"}` from its
last completed checkpoint (refused with `PF-CONF-0007` without one), with `{"from": "SCRATCH"}` from
the start, and without a body from the checkpoint when there is one. A running or succeeded run
cannot be retried.

Every attempt is recorded with its state, times, error and the checkpoint it started from, and every
change of state names its attempt. The run's counters — rows read, written, skipped as bad, failed,
and its elapsed time — add up over its attempts; each sample keeps the metrics of its attempt.

## Quick start

A job against a flaky target that may restart any number of times, waiting longer each time:

```yaml
env:
  restart:
    strategy: exponential-backoff
    initial: 10s
    max: 5m
```

## Configuration

| Option | Default | Meaning |
|---|---|---|
| `env.restart.strategy` | `fixed-delay` | `none`, `fixed-delay`, `exponential-backoff` or `failure-rate` |
| `env.restart.attempts` | `3` | `fixed-delay`: the restarts in all |
| `env.restart.delay` | `10s` | `fixed-delay` and `failure-rate`: the wait before each restart |
| `env.restart.initial` | `1s` | `exponential-backoff`: the wait before the first restart |
| `env.restart.max` | `5min` | `exponential-backoff`: the longest wait |
| `env.restart.multiplier` | `2` | `exponential-backoff`: how much longer each wait is than the one before |
| `env.restart.reset-after` | `1h` | `exponential-backoff`: after this long without a failure the wait starts over |
| `env.restart.max-failures` | `3` | `failure-rate`: the failures allowed within the window |
| `env.restart.interval` | `5min` | `failure-rate`: the window |

The [job DSL reference](../reference/job-dsl#env) lists the values each option accepts. A
`restart.*` option the chosen strategy does not use is reported as a warning when the job is
planned.

## Examples

At most five failures in ten minutes, a minute apart:

```yaml
env:
  restart:
    strategy: failure-rate
    max-failures: 5
    interval: 10m
    delay: 1m
```

Fail at the first error, for a job that someone watches and reruns by hand:

```yaml
env:
  restart:
    strategy: none
```

## Behavior

- Each failure of a task counts once; the errors the other tasks of its region report while they
  stop are not classified again. A failure that fails the run cancels every task.
- Failures of the job master, the enumerator or a commit fail the run: only tasks restart.
- A run without checkpoints does not restart tasks: a transient failure fails it.
- Fatal and data errors fail the run at once and do not use up any restarts.
- `fixed-delay` attempts never come back during a run; `failure-rate` forgets failures that left
  its window; `exponential-backoff` never runs out.

## Observability

The job master logs every decision: the error, its kind, and whether the strategy allows a restart
and after how long, or allows no more. A restart logs the tasks it restarts, the splits that go
back to the enumerator and the checkpoint the tasks restore.

## Troubleshooting

| Problem | Cause and solution |
|---|---|
| A connection error fails the run although restarts are left | The plugin reported it as `PF-SRC-0001` or `PF-SINK-0001` without marking it transient. The plugin's `ErrorClassifier` should map that exception |
| A worker was lost or a connection broke, restarts are left, and the run failed anyway | The run takes no checkpoints: set `checkpoint.dir` on the cluster and keep `env.checkpoint.enabled` |
| `has no effect with restart.strategy` warning | An option of another strategy is set; remove it or change the strategy |
| [`PF-CONF-0002`](../reference/errors#pf-conf-0002) `restart.max` | `restart.max` is shorter than `restart.initial` |

## Limitations

- The counters of a restarted task start again from zero, so the run's row counts leave out what
  its earlier attempt read and wrote.
- A task that ignores its cancel for longer than twice the cancel timeout is given up, but its
  thread may still run while the region's new attempt writes.
- Rolling back what a failed run wrote is not available yet.
- Whether `TRANSIENT` matches is decided by the error code's registered kind, not by a kind a plugin
  set for one error.
