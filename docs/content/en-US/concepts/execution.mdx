## Overview

Once a job is [planned](./plan-and-explain), the engine runs it. This page explains what happens at
run time: which threads exist, how a row travels from the source to the sink, how reading and
writing overlap, how a job is cancelled and how failures are reported.

The same runtime runs in local mode (one process) and on a cluster: local mode uses in-process
implementations of the interfaces that a cluster implements with RPC, so a job behaves the same in
both. Tasks receive their description in the same binary format that a worker receives from the
master, written and read back, so every local run also checks that format. In this version the
engine runs in local mode.

## How it works

### Operator chains and tasks

Most integration jobs need no shuffle: the source, its transforms and the sink are connected one to
one with the same parallelism. The engine merges them into one **operator chain** and runs one
**task** per parallel instance. Inside a task the operators call each other directly: a row goes
through the whole chain before the reader emits the next one, and nothing is serialized between
operators.

```text
job: src (p=2) → map (p=2) → out (p=2)

task src-0:  reader → map → writer        thread task-src-0 (+ writer-src-0)
task src-1:  reader → map → writer        thread task-src-1 (+ writer-src-1)
```

### Execution graph and partitioning

On a cluster, a job is not always one straight chain. The master turns the plan into a **job
graph**: a node joins the chain of the node before it when it is that node's only consumer, reads
from nothing else, has the same parallelism and receives its rows one to one. Where a chain ends,
an edge decides how rows are distributed over the instances of the next chain:

| Partitioning | When the engine chooses it |
|---|---|
| `forward` | Same parallelism on both sides: instance i sends to instance i |
| `rebalance` | The parallelism changes: rows go round robin to all instances |
| `hash(keys)` | A sink with a parallelism above 1 may receive updates or deletes: the changes of one primary key, or of one table and primary key when there are several tables, always reach the same writer, in order |
| `table`, `broadcast` | The engine can run them (`table`: every table to one instance, by the hash of its name; `broadcast`: every row to every instance); no rule chooses them yet |

The hash of `hash` and `table` depends only on the values, so the same key reaches the same
instance on every worker and every run.

The **execution graph** expands every chain by its parallelism into tasks. Tasks connected by
edges form a **region**; tasks that exchange no rows are in separate regions, so a failure of one
does not touch the others. Chains share slots: instance i of every chain runs in slot i, so a job
needs as many slots as its largest parallelism. On a cluster, every task runs in a slot that the
scheduler reserved for the job on its worker.

```text
cdc (p=1) → route (p=1) → doris (p=4), with updates

chain cdc+route (p=1) ──hash(id)──► chain doris (p=4)
tasks: cdc[0]  doris[0] doris[1] doris[2] doris[3]    one region, 4 slots
```

Until the planner derives which nodes emit updates or deletes, an unbounded source counts as one
that may, and so do the nodes after it: an unneeded `hash` costs throughput, a missing one would
reorder the changes of a key.

Each task of a chain that does not start with a source reads its rows from the tasks of the chain
before it, and each task of a chain that does not end with a sink writes them to the tasks of the
next one — in memory when both run on the same worker, over the network otherwise (see below).
Local runs use the same graph; all their tasks are in one process, so they exchange rows in
memory.

### Splits are pulled

The source's split enumerator runs in the job master. A reader asks for a split when it starts and
again whenever it finishes one; the enumerator answers with the next split or with "no more splits".
Fast readers therefore take more splits, which evens out skew. Splits travel to the task serialized
with the source's split serializer, exactly as they would between machines.

### The mailbox

Each task has one thread and a **mailbox**. The thread alternates between handling mail (split
assignments, cancellation, later checkpoints and timers) and reading data:

```text
loop:
  run the pending mail
  reader.pollNext → transforms → sink
  nothing to read? wait for mail, 1 ms doubling up to 100 ms
```

Because events and data are handled on the same thread, operators need no locks, and a snapshot of
their state is always consistent.

### Asynchronous write buffer

With the write buffer (on by default) the sink writes on its own thread, so that reading and
writing overlap:

```text
task thread: … → batch ──► bounded queue ──► write thread: SinkWriter
                     blocks when full
```

When the target is slower than the source, the queue fills and the task thread blocks: this is the
backpressure that slows the reader down. When the input ends, the task waits until every batch is
written, then asks the writer to prepare its commit.

### Data exchange and backpressure

When tasks of different chains are connected, the upstream task writes its rows into an **output**
with one subpartition per downstream subtask, and each downstream task reads an **input** with one
channel per upstream subpartition.

- Rows are packed into network buffers of 32 KB from the worker's network memory. A buffer is sent
  when it is full, after the buffer timeout (100 ms) when traffic is low, or before an event. A row
  larger than a buffer gets a buffer of its own; a row above `task.max-row-bytes` fails with
  [`PF-DATA-0007`](../reference/errors#pf-data-0007).
- Events — the end of a subpartition, the end of a bounded input, a table that changed — travel in
  the same stream as the rows, so they arrive exactly between the rows written before and after them.
- **Credit**: each input channel owns 2 buffers and may borrow from 8 floating buffers of its input
  when the producer reports a backlog. A producer sends a data buffer only when the channel has
  credit; events need none.
- **Backpressure**: a slow consumer stops giving credit, its producer's buffers fill up, and writing
  the next row waits until one is free. The wait reaches the source, which stops reading. Only that
  output is held back: other channels on the same connection keep flowing.
- Tasks on the same worker hand buffers over in memory, with the same credit and order. Tasks on
  different workers use one TCP connection per pair of workers, shared by all their channels; an idle
  connection sends a ping every 30 seconds, and one silent for three intervals is closed.
- If a connection breaks, the tasks on both ends fail with
  [`PF-CLUS-0010`](../reference/errors#pf-clus-0010).

### Commit at the end of the input

A sink that commits in two phases returns a committable from `prepareCommit`. When every task has
finished, the job master commits them with the sink's committer and then its global committer, and
only then reports `SUCCESS`. A run without checkpoints commits once, as checkpoint 1.

### Job states

| Status | Meaning |
|---|---|
| `CREATED` | Accepted; waiting for slots, then deploying the tasks |
| `RUNNING` | Tasks are running |
| `CANCELLING` | A cancel was requested; tasks are stopping |
| `SUCCESS` | Every source ended and every sink wrote and committed its data |
| `FAILED` | A task, the enumerator or the commit failed; the result carries the error |
| `CANCELLED` | Stopped on request |

On a cluster the master's dispatcher accepts runs from the server and follows them through these
states (the subset of this version):

| From | To |
|---|---|
| `QUEUE` (waiting for slots) | `RUNNING`, `CANCELLING`, `FAILED` |
| `RUNNING` | `SUCCESS`, `FAILED`, `CANCELLING` |
| `CANCELLING` | `CANCELLED`, `FAILED`, `TIMEOUT` (cancelled for running past its timeout) |

Every transition is checked and recorded with its time and reason; a transition that is not in
the table is refused. Submitting a run ID that the master knows already returns that run, so a
retried submission never starts a second run. The master plans the definition again with the
plugin versions the server chose; a version it does not have fails the submission with
[`PF-PLUG-0009`](../reference/errors#pf-plug-0009), and an unknown run ID is
[`PF-CONF-0010`](../reference/errors#pf-conf-0010).

Every run has a **job master** that drives it from start to end:

1. It gets the slots of the run: on a cluster the [scheduler](./cluster) reserves them on the
   workers; in one process the local task executor runs every task.
2. It starts the split enumerator and deploys one task per subtask into its slot.
3. It follows the states the tasks report. The first failure cancels the other tasks and becomes
   the error of the run; a [lost worker](./cluster) fails the run with `PF-CLUS-0001`, scoped to
   the node and subtask that ran there.
4. When every task has finished, it commits what the sinks prepared and the run succeeds.
5. Whatever the end, it gives the slots back. A run cancelled while it waits for slots ends at once;
   slots that arrive later go back too.

## Quick start

The engine is embedded through `pipeforge-engine-local`; the `pipeforge run --local` command of
the command line uses the same API.

```java
JobPlan plan = new Planner(components).plan(JobParser.parse(yaml, VariableContext.builder().build()));
try (Engine engine = new LocalEngine()) {
    JobHandle handle = engine.submit(plan);
    JobResult result = handle.result().get();
    System.out.println(result.status());          // SUCCESS
}
```

## Configuration

Engine settings are given per submission with `SubmitOptions`:

| Setting | Default | Effect |
|---|---|---|
| `asyncWriteBuffer` | `true` | Write on a separate thread behind a bounded queue; `false` writes on the task thread |
| `writeBatchSize` | `1024` | Rows per batch handed to the write thread |
| `writeQueueCapacity` | `4` | Batches the queue holds before the task thread blocks |
| `cancelTimeout` | `30s` | Time a cancelled task gets before its thread is interrupted; after twice this time it is given up |
| `enumeratorTimeout` | `60s` | Time one call of the split enumerator may take; longer fails the job with `PF-SRC-0004` |
| `metricsInterval` | `1s` | How often tasks report their metrics and the job metrics and rates are refreshed |

The parallelism of each task comes from the job: `env.parallelism` or the node's `parallelism`.

The data exchange is configured per worker; the settings are read once workers run as their own
processes, with the cluster distribution:

| Setting | Default | Effect |
|---|---|---|
| `worker.memory.network` | 10% of the memory (64 MB–1 GB) | Memory for network buffers |
| `network.buffer-size` | `32KB` | Size of a network buffer |
| `network.buffers-per-channel` | `2` | Buffers each input channel owns |
| `network.floating-buffers-per-gate` | `8` | Buffers an input shares among its channels when producers report a backlog |
| `network.buffer-timeout` | `100ms` | When a buffer that is not full is sent anyway |
| `task.max-row-bytes` | `64MB` | Largest row |

An input needs `buffer-size × (buffers-per-channel × channels + floating-buffers-per-gate)`, and
the channels of an edge are the upstream times the downstream parallelism.

## Examples

### Four parallel readers

```yaml
version: 1
name: orders-copy
env:
  parallelism: 4
source:
  - { id: src, type: jdbc, table: demo.orders }
transform:
  - { id: map, type: field-mapper }
sink:
  - { id: out, type: jdbc, table: dw.orders }
```

The engine runs four tasks, `src-0` to `src-3`, each with its own reader, mapper and writer. The
enumerator splits the table into key ranges; whichever reader is free takes the next range.

### Cancelling a job

```java
JobHandle handle = engine.submit(plan);
handle.cancel();
handle.result().get().status();   // CANCELLED
```

`cancel` returns at once. Each task is woken up, the reader's `cancel()` and an interrupt of the write
thread stop blocking calls, and the job ends with `CANCELLED` once every task has stopped. Nothing is
committed. A worker that loses its [master](./cluster) cancels all its tasks in the same way.

## Behavior

- **One final state per task.** A task reports `FINISHED` with its committable, `FAILED` with its
  error, or `CANCELED`; the job master decides the job's status from them.
- **The first failure wins.** It cancels the other tasks and becomes the job's error. Local mode does
  not restart tasks; region restarts come with checkpoints in the distributed engine.
- **Cancellation escalates.** The reader's cancel hook and the write thread's interrupt come first;
  after `cancelTimeout` the task thread is interrupted; after twice `cancelTimeout` the task is given
  up with `PF-RES-0005` and the job fails.
- **Plugin code is isolated.** Every call into a plugin runs with the plugin's class loader as the
  context class loader, and what it throws is turned into an error with a code (see Troubleshooting).
- **One run start time.** The job master fixes when the run started and hands it to every task, so
  `RUN_START_TIME()` in expressions is the same in all of them.
- **Ordering.** Within a task, rows and schema changes reach the sink in the order the reader emitted
  them, with or without the write buffer.

## Observability

The result of a job carries its final status, the error with its code and scope (job, run, node,
subtask) and its [metrics](../reference/metrics); `JobHandle.metrics()` returns them while the job
runs, refreshed every `metricsInterval`.

- **Collection.** Each operator counts its rows with one `LongAdder` increment per row and counter.
  Every task sends a snapshot of its counters to the job master once per `metricsInterval`, and a
  final one with its final state; the job master sums them per node and for the job.
- **Rows.** `rowsRead` is what the source emitted, `rowsWritten` what the sink wrote (for sinks that
  commit in two phases: what was committed), `rowsFiltered` and `rowsExpanded` what transforms
  dropped or added, `rowsInFlight` what was read but not yet taken by the sink, mostly rows in the
  write queue. A failed or cancelled job counts the rows that never reached the target as
  `rowsFailed`. The counters always reconcile, also while the job runs:
  `rowsRead + rowsExpanded = rowsWritten + rowsFiltered + rowsFailed + rowsInFlight`.
- **Rates.** Read and write rates are sampled once per interval: the current rate over the last
  5 seconds, the average since the start and the peak over one second.
- **Self time.** `selfTimeRatio` is the share of the running time a node spends in its own code,
  without the nodes after it. It is measured on every 16th read, so that the hot path does not read
  the clock for every row; for a sink with the write buffer it is the busy time of the write thread.
- **Waiting.** `readerWaitMs` is the time tasks blocked on a full write queue or on full network
  buffers (something downstream is slow), `writerWaitMs` the time write threads waited for rows
  (the source is slow).

`AnalyzeText` prints the metrics the way `explain --analyze` shows a run:

```text
Job orders-copy  SUCCESS 12.4s  parallelism 4
Rows   read 1,000,000  written 999,000  filtered 1,000  in-flight 0  failed 0   reconcile OK
Rate   read 0 r/s (avg 80,645, peak 91,200)   write 0 r/s (avg 80,564, peak 91,000)
Wait   reader 1.2s (target slow)  writer 300ms (source slow)

Node  kind       in rows    out rows   sel.  self%
src   source     1,000,000  1,000,000  -     21%
map   transform  1,000,000  999,000    1.00  4%
out   sink       999,000    999,000    -     68%
```

Each task logs when it starts running and when it fails; the job master logs the job's start,
commit and end.

## Performance and tuning

- Keep the write buffer on: reading and writing then overlap, and a slow target throttles the source
  instead of stalling it row by row.
- Raise `writeBatchSize` for targets that write efficiently in large batches; lower it to reduce the
  memory a task holds (`writeBatchSize × writeQueueCapacity` rows at most).
- A larger `writeQueueCapacity` absorbs short slow-downs of the target; it does not help when the
  target is slower on average.
- More parallelism means more tasks and threads; the source's splits must be fine-grained enough to
  keep them busy.
- A high `readerWaitMs` with a high `selfTimeRatio` of the sink means the target is the limit; a
  high `writerWaitMs` means the source is.
- Between tasks, the time an output waits for buffers (`backpressuredMs`) shows that something
  downstream is slower; the input wait time of the next task shows that it waits for upstream. More
  floating buffers absorb bursts; they do not help a consumer that is slower on average.

## Troubleshooting

| Error | Meaning |
|---|---|
| `PF-SRC-0001` | The source's reader or enumerator threw an error it did not classify; the reason names the operation, e.g. `read` or `start the enumerator` |
| `PF-SINK-0001` | The sink's writer threw an error it did not classify, e.g. while writing a row or flushing |
| `PF-SINK-0003` | The data was written but the commit failed or was still refused after 3 attempts |
| `PF-PLUG-0007` | A transform failed while processing a row |
| `PF-RES-0005` | A cancelled task ignored cancellation and interrupts; give the connector a socket or query timeout |
| `PF-PLAN-0012` | The job has a shape this version cannot run, or a schema change reached a data exchange (see Limitations) |
| `PF-CLUS-0010` | The data connection between two workers broke; the tasks on both ends fail |
| `PF-CLUS-0011` | A task asked for the output of an upstream task that did not appear on its worker in time; look for the first error of the run |
| `PF-RES-0008` | The worker's network memory cannot hold the buffers an input needs; raise `worker.memory.network` or lower the parallelism |
| `PF-DATA-0007` | A row is larger than `task.max-row-bytes` |

Errors that a connector reports with its own code keep that code; the engine adds the node and
subtask to their scope. The full list is in the [error reference](../reference/errors).

## Limitations

- Jobs are pipelines: one source, its transforms and one sink, each node reading from the one
  before; the parallelism may change from node to node. Several sources or sinks, a node whose
  output goes to several nodes and nodes that read from several nodes fail with `PF-PLAN-0012`.
- Schema changes cannot cross a data exchange yet: a schema change that reaches the end of a chain
  whose rows go to another chain fails the task with `PF-PLAN-0012`. Jobs whose nodes all have the
  same parallelism run in one chain and are not affected.
- No checkpoints: a failed or cancelled job starts from the beginning when it is run again, and
  two-phase sinks commit once at the end of the input.
- No restarts: the first task failure fails the job.
- Streaming jobs run until they are cancelled.
